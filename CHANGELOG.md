# Changelog

All notable changes to Craftly are listed here. The format follows [Keep a Changelog](https://keepachangelog.com/en/1.1.0/).

## Unreleased production-readiness fixes

- Editor saves compare revisions in one transaction. Stale tabs can recover their drafts without overwriting newer work or recreating a deleted design. The document commits before thumbnail rendering. Navigation and updates handle failed saves explicitly, and updates also wait for confirmed writes.
- Live sharing uses a separate owner key. The server rejects malformed request targets, applies default room and peer limits, persists edits before acknowledging them, and checks whether room storage is writable. Same-tab reloads retain queued edits, rejected edits get recovery copies, and collaborators can load shared uploads.
- Portable project files and library backups omit live links. Project import stages images before committing the design, and export reports missing images. Service-worker cleanup preserves unrelated same-origin caches.
- See [verification](docs/VERIFICATION.md#production-readiness-regressions) for the 16 regression cases and remaining release checks.
- **Comments: pin a note to a place of the page, answer it, resolve it.** The Comment tool (last in the Tools palette, key `M`) places a pin where the page is clicked, on the element there if there is one so that the pin follows it (and stays where the element was when it is deleted), and opens a small editor: Enter or Post posts, Esc cancels. Pins are numbered per page, in the author's colour, hidden once resolved unless "Show resolved pins" is on, and are real buttons that open their thread. The **Comments** button in the top bar, with the number of open comments, opens a panel with the threads of this page first and then of the others, filtered by Open, Resolved or All, with replies, Resolve and Reopen, and Edit and Delete for one's own messages (Delete asks first). Comments are an optional field of the design, `comments`, so the format version did not change; they travel in project files and backups (checked as strictly as on the wire, what is not usable left out and counted), are kept by Make a copy, go with a page that is deleted, are never drawn into an export, the presenter or a thumbnail, and are no steps of undo. In a live session they are shared as operations that each touch one comment or one reply, so two people who comment, answer or resolve at the same moment both keep what they did. The two sides agree on it the way presence does with `peer`: a browser says `features: ["comments"]` in its join, a server of this version answers with the same in its welcome, sends comment operations only to browsers that said so (an older browser in the room gets each batch without them and a welcome without comments, and is not ended), and keeps comments in the room's design, inside `maxDesignBytes`. With a server from before comments they stay on this person's copy and the panel says "This server does not share comments". Editors comment, viewers read and are told why they cannot. Texts are plain text everywhere, checked by one table beside the element check (`src/core/comments.ts`), and an author's colour is a place in the presence list, never a colour from the wire. Not covered: a browser journey (`e2e/live.cjs` is unchanged), a real screen reader, mentions, and a check on the server that only the author changes a comment ([`docs/COLLABORATION.md`](docs/COLLABORATION.md), "Comments").

## Unreleased work of the night of 2026-11-13 (branch `overnight-2026-11-13`, see docs/OVERNIGHT-PLAN.md)

- (items are added below this line as they are finished)
- **Two people in one text box no longer lose text: one person types in a box at a time.** Editing is last-writer-wins per property, and the text of a box is one value, so when two people typed in the same box each key of one replaced what the other had typed. A merge of rich text is not built; the honest fix is. While somebody has a text box open for typing, everybody else sees a dashed outline in that person's colour with "Name is typing…", and a double click, Enter or a key on that box does not open it and says who has it. What that person types still arrives live. The lock is advisory and lives only in presence: nothing is stored, the server refuses no edit, and it ends when the person closes the box, leaves, or is not heard of for 10 seconds, so it cannot get stuck. When two people open the same box in the same instant, the server decides by the order in which it heard them: it passes on only the first as typing there. The second hears that, has its box closed, and is told why; what it had typed until then is the last write at that moment, and an emptied box is not removed by being closed this way. Tables are not covered: their cells are edited in a side panel by another mechanism, and two people in one table still overwrite each other. `e2e/live.cjs` has a step for it with the real pointer.
- **Dragging stays smooth on heavy pages.** Measured first (`e2e/perf-drag.cjs`, a production build, a laptop of 2018): every pointer move repainted the whole page, and a drag on a page of 150 text boxes, of 40 filtered photos or of 60 blended shapes ran at 18 to 28 frames a second, with 70 to 140 ms for a frame at the 95th percentile; the store commit, which a review had suspected as well, took 0.3 to 2.8 ms a move and was left alone. Now the elements that do not change are painted once when a pointer gesture begins and kept as two pictures, one under and one over what moves, and a frame paints only what moves between them; the page strip leaves its thumbnail alone until the gesture ends (it was the stutter on the text page). All the measured pages are at the full frame rate, headless and in a window. A kept picture is used only while every element on it is the same object as when it was painted and the zoom, scroll position, canvas, background and loaded fonts and pictures are the same; with a blend mode over the moving element nothing over it is kept; when the gesture ends the page is painted from nothing, so the picture at rest, every export and the history (one step a drag) are as before. During a drag the elements over the moving one can differ from the page at rest by one or two levels of 255 on their soft edges. The numbers, the rules and what was not measured are in [`docs/PERFORMANCE.md`](docs/PERFORMANCE.md).
- **People in a live session see each other.** Everybody has a name and a colour: the others' pointers follow their mice on the page, what they have selected has an outline with their name on it, and beside the "Live" mark in the top bar is a row of initials with a count. The name is asked for in Share > Work together and on the page of a link ("Your name", kept on this device, "Guest 3" when left empty). It travels as a new kind of message, `presence`, that is passed on and stored nowhere: no revision, no acknowledgement, nothing in a room's file. It is checked on both ends as strictly as edits are (a name is 40 characters of plain text, a pointer two finite numbers, a selection at most 50 ids, no other field), there is no colour on the wire (one of twelve fixed colours by the number the server gives a connection, which a browser cannot choose), and the server gives presence an allowance of its own (`PRESENCE_BURST`, `PRESENCE_PER_SECOND`: 30, then 15 a second): within it a moving pointer costs nothing of what a person may send in edits, over it messages are dropped and counted (`craftly_live_presence_dropped_total`) and the connection stays, and a flood is still closed. People with the view link are seen and see; their selection is not passed on. The layer on the page takes no pointer events and is hidden from screen readers, which get a plain list of who is here and no announcement per movement; with reduced motion pointers do not glide. A server or a browser from before this ignores the new messages, so either may be older than the other. `e2e/live.cjs` has a new step in which two real Chrome windows see each other.
- **The live server can be watched.** With `METRICS_KEY` set (off by default; without it the address answers 404), `GET /metrics` gives its numbers in the text format Prometheus reads, to a request that shows the key as a bearer token: how long the process has run, rooms in memory and on disk, connections and people who have joined, messages and bytes received, edits applied and refused, saves, failed saves and how long saves took, rooms made, removed and expired, connections closed by each limit (a slow reader, too many messages, too many joins, a message too big, no answer to pings, too many at a door), connections refused before they were made, and HTTP answers by class. A key was chosen over "only from this machine", because behind a reverse proxy every request comes from this machine. It is a key of its own, so a scraper cannot remove rooms; a request from a page is refused, there are no CORS headers, and ten wrong keys in an hour lock an address out. No number names a room, a person, an address or a path: every label takes its values from a fixed list. No new package: the format is written by hand. The docs have an example scrape configuration and a few alerts worth setting. Not checked: a real Prometheus has not scraped it; the tests read the text back with a small parser of their own (`src/server/metrics.ts`, `live.ts`, [`docs/DEPLOY.md`](docs/DEPLOY.md) section 2.8).
- **Thirty more templates, in the categories that had few: 102 templates in 175 pages now.** Posters go from 5 to 9 (a talk series on a grid, a plant swap, a travel poster, a jazz night), flyers from 4 to 8 (a class schedule, a street clean-up, a software meetup, lessons with tear-off tabs), documents from 3 to 6 (a research report, a team newsletter, a one-page proposal), resumes from 4 to 7 (editorial serif, banded header with a monogram, a grid of cards for a student), logos from 4 to 8 (boxed wordmark, app tile, script signature, scalloped sticker), invitations from 4 to 7 (housewarming, a supper with a photo, a graduation ticket), cards from 4 to 7 (a business card with an appointment box, a thank-you card and a winter card, each with an inside), banners from 4 to 6 (a reading festival, a podcast cover), certificates from 3 to 5 (a modern one with a side panel, a reading award for children) and menus from 3 to 5 (a food truck, a tasting menu). All are drawn from what the editor already has: the bundled fonts, the built-in photos, the illustration library, shapes and lines. For the first time templates carry a real table (the class schedule and the proposal's costs), a real chart (the report) and groups (a record, a waveform, a barcode, a pattern of tiles: eleven in all), so those open as one editable thing instead of loose shapes. Every name, person, street and town in them is made up, and web and mail addresses are `example.com`. `src/data/templates/templates.test.ts` now pins the count of templates and pages per category, and checks groups, tables and charts. The counts in the README, the roadmap and the investor notes are corrected; the reports under `reports/` and `research_notes/` are dated and still say 72. Each page was looked at rendered on the dev contact sheets and passed their lint; none was opened in the editor, exported or printed.
- **Upload your own fonts and use them like the bundled ones.** Brand kit > Your fonts (on the dashboard and in the editor's Brand tab) takes `.ttf`, `.otf`, `.woff` and `.woff2` files of up to 10 MB, with the reminder to upload only fonts you have the right to use. A file is known by its first bytes, never by its name or type, and is then loaded with the browser's `FontFace` from those bytes, which parses it and runs nothing; what does not load is refused in plain words ("This is not a font file…", "This file could not be read as a font…"), and a font collection is told apart. The family, weight and style are read from the `name`, `OS/2`, `head` and `fvar` tables of a TrueType or OpenType file by a small reader that checks every offset against the length of the file; a WOFF or WOFF2 file is compressed, so there they come from the file name ("AcmeSans-BoldItalic.woff2") and the toast says so. Several files with one family name form one family with its real bold and italic; a family can be renamed and deleted (it asks first and says what happens to the designs). The files are records of the existing `meta` store (`customFont:<id>`), so the database has no new version. Uploaded families are in the font catalogue (`src/render/fonts.ts`) beside the bundled ones, so the canvas, thumbnails, Present and the PNG / JPG / PDF / GIF / video exports draw them through the code that already waits for a font, and an export that starts while the fonts are still being read waits for that too. They are registered under a name the app makes up from letters and digits ("Craftly Upload 40a7…"), never under the text a person typed and never under the name of a bundled family ("Inter" becomes "Inter (uploaded)"); a family name in a canvas `font` string or a style can no longer end its quotes with a line break. The Font panel lists them first under "Your fonts", the Text tab finds them by name, and the Brand kit can hold them as brand fonts. **A design that names a font this device does not have is not changed**: its text draws in a substitute font, the Font panel marks the name "Not on this device", and the editor says once which font is missing. A `.craftly` project file carries the font files of the uploaded families its design uses, and a backup carries all of them (`fonts/<id>.<ext>`); on the way in each is checked exactly as an upload is, and one that fails, or has the name of a bundled family, is left out while the design still opens. An SVG with embedded fonts embeds them with their own type. Fixed on the way: text edited in place gave a run the registered name of its font instead of the family name. Not done: font files are not sent through a live session (the other person is told which font is missing); the delete dialog does not count the designs that use a font; fonts uploaded in another tab need a reload. Not tried in a real browser or with a real font file.
- **What people send each other in a shared design is checked as strictly as a file, and a room no longer remembers every tab that ever edited it.** An editor of a shared design could add a shape with `x: "a"` or set `paragraphs: 5` on a text, for everybody in the room and for good, and the renderer throws on that for all of them: the live check looked only at an element's id and kind, where the file importer always asked for more. Both now use one table (`src/core/usableElement.ts`): the place and size of every element are numbers, and each kind has what it cannot be drawn without. That holds for an element that is added (alone, in a group, with a page), for a design that makes a room and for the design a browser is welcomed with; and after a change of properties the server asks the same of every element the batch touched, so `stroke: null` passes for a shape and is refused for a line. A batch that fails is refused as a whole and nothing of it is saved or passed on; a browser ends the session with a server that sends such a thing. Everything the editor makes passes: a test checks one element of each kind, the design with every field, and every template of the catalogue. A room that already holds a damaged element (possible only through a tampered editor before today) can no longer be joined with this version. Second: the list of "last batch per client" in a room record grew by an entry for every page load that edited, for ever, and was written with every save. A client that stayed away for 30 days is now forgotten (and above 1,000 clients the ones seen longest ago), never one that is in the room. So that a forgotten tab that comes back cannot have an old edit applied twice, the room keeps the highest number it ever forgot and counts every client it does not know from there; such a tab loses what it had sent and not heard back about. A browser new to the room loses nothing: it renumbers what it made before the room first answered. A browser that still runs older code may lose edits made before its first welcome in a room that has forgotten somebody (`src/collab/protocol.ts`, `room.ts`, `session.ts`, [`docs/COLLABORATION.md`](docs/COLLABORATION.md)).
- **An operator can see which rooms a live server holds, and remove one.** With `ADMIN_KEY` set (without it there is no such interface), `GET /api/admin/rooms` lists the rooms a page at a time: id, title, when it was made and last used, the size of its design and of its images, and how many people are in it now. `DELETE /api/admin/rooms/<id>` removes a room the way "Stop sharing" does, through the same function and queue: whoever is in it is sent away and its images go with it. It also removes a room whose file is damaged, which until now only deleting the file by hand could. Both want the key in the header `x-craftly-admin-key`, compared in constant time and never logged. They are for a terminal and not for a page: a request that names an `Origin` is refused whatever the origin, and these answers never carry CORS headers. An address that shows ten wrong keys in an hour is not listened to for the rest of it, also not with the right key. No key of a room is listed, and no hash of one. `npm run server:rooms -- list` and `-- delete <id>` (`scripts/rooms.mjs`) are the two calls with a table around them; they read the address and the key from the environment. The script was run by hand against the built server (list, delete, a wrong key, no key, no server) and has no test of its own (`src/server/live.ts`, `address.ts`, [`docs/DEPLOY.md`](docs/DEPLOY.md) section 2.7).
- **The Pen can be used without a pointer.** With the Pen in hand (`P`), an arrow key shows a cross on the page, in the middle of what is in view or on the last point of the path; the arrows move it by 1 px (`Shift`: 10 px, the steps of nudging an element), it stops at the edges of the page and the view follows it. `Enter` is its click and goes through the same code as a click: a corner point, the end of the path when pressed again on the point just placed, the closing of the path on its first point, where `Home` takes the cross. `Shift+Enter` places a smooth point (its curve goes on in the direction the path came in, a third as long as the side before), and `Alt` with the arrows pulls the curve of the last point by 1 or 10 px. `Space` was not taken for placing because holding it pans the canvas, and `C` not for closing because it adds a circle. For the pointer nothing changes: the cross only appears with an arrow key, hides (and is remembered) when the pointer moves, and while it is hidden `Enter` finishes the path as before, which is what the browser journey of the Pen does. The place of the cross is shown in numbers beside it and said in a polite status once it has rested for 0.3 s, so a held key says one thing. Point editing could already be done from the keyboard (Tab through the points, arrows move them with one undo step for a run of presses, Delete removes them) and was left as it is. Not tried in a real browser or with a screen reader; that the view follows the cross rests on `scrollIntoView`, which the tests can only see being called (`src/editor/canvas/penTool.ts`, `PenCursor.tsx`, `penKeyboard.test.tsx`, [the Pen tool](README.md#the-pen-tool), [`docs/ACCESSIBILITY.md`](docs/ACCESSIBILITY.md)).
- **A server can ask for a key before it lets somebody start to share.** With `ROOM_CREATE_KEY` set (off by default), `POST /api/rooms` makes a room only for a request that shows the key in the header `x-craftly-create-key`: without it the answer is 401, with a wrong one 403, and the design is not read for either. The key is compared in constant time, never taken from the address, never written to the log, and every attempt counts towards the rooms an address may make in an hour, which is what limits guessing. In the editor nothing changes for a server without a key. When a server wants one, the Share panel shows a password field, **Key to start sharing**, with the sentence "This server asks for a key to start sharing. Whoever runs it can give it to you.", and a wrong key is said there in plain words. The key is not remembered on the device: a page could keep it only as plain text in `localStorage`, and it is the operator's secret, so it is typed (or filled in by a password manager) each time a design is shared; changing the server address clears it, so it is never shown to another server. People who are given a link join, edit and look without it. It is one key for everybody the operator lets share, not an account. Not seen in a real browser: the field, its focus and a password manager's offer (`src/server/live.ts`, `src/editor/live/connection.ts`, `LiveSection.tsx`, [`docs/DEPLOY.md`](docs/DEPLOY.md)).
- **A design can be downloaded as a web page for people who do not have Craftly.** The last entry of the file type list of **Share > Download**, **Web page (HTML)**, writes one `.html` file that shows the chosen pages as a slideshow in any browser: next and back with two buttons, the left and right arrow keys, Page Up and Page Down, Space, Home and End, a click on the page or a swipe; a page counter; a full screen button (and F). The pages are pictures (JPEG at quality 0.9, about 1920 px on the longer side and at most twice the design), not inline SVG: a picture comes from the editor's own painter and so looks like the editor, while the SVG writer only mirrors it, several SVGs in one document would share one space of ids, and embedded fonts would need the policy opened for them. The picture of a page has the alt texts of what is on that page as its alt text ("Page 3: name" where there are none), the file has the title of the design as its `<title>` and a `lang` attribute. Speaker notes are private and stay out unless **Include speaker notes** is switched on (off again at every visit); then they stand under each page. The file is inert: everything that comes from the design (title, page names, alt texts, notes) is escaped, a picture is accepted only as a PNG or JPEG data URL in base64, and a Content-Security-Policy in the file (`default-src 'none'; img-src data:; style-src 'unsafe-inline'; script-src 'sha256-...'; base-uri 'none'; form-action 'none'`) allows its own pictures, its inline style and its one script, named by its hash, and nothing else; it asks the network for nothing and uses the fonts of the device for its few words. The script is the same in every file, which is why the hash can be a constant that a test recomputes; without script the pages stand one under the other. The editor's animations, page transitions and links are not carried over: pages change with a cross-fade of 0.3 s, and not at all for someone who asked the system for less motion. Buttons have names, the keyboard focus is visible, the page that is not shown is hidden from screen readers too. One file holds 40 MB; beyond that the download stops as soon as that is certain and says to choose fewer pages. Not opened in a real browser: that the policy lets the script run by its hash, the look of the page, the swipe on a phone and the full screen were not seen; the tests parse the file and run its script in jsdom, which does not enforce a policy (`src/export/webPage.ts`, `webPageExport.ts`).
- **A drawing can be taken apart into shapes.** **Convert to shapes** in the right-click menu (and the "..." menu of the toolbar) replaces a graphic, an icon or an uploaded SVG picture by the shapes it is drawn from, where it was and in one undo step: a group of paths with their own fills and outlines (the path itself when there is one), and a path in one piece opens with Edit points. It reads `path` with every command (arcs and quadratic curves as cubic curves), `rect` with rounded corners, `circle`, `ellipse`, `line`, `polyline`, `polygon`, groups and nested drawings, every transform (worked into the points), the view box with `preserveAspectRatio`, colours by name, hex, `rgb()`, `hsl()` and `currentColor`, opacities, line width, ends and corners, the even-odd rule for holes, and linear and radial gradients as fills; a graphic keeps the colours and line width it was given in the editor. Approximated without a word: a gradient keeps its direction or centre and its colours but runs from edge to edge of the shape as every gradient of the editor does, dashes become the editor's dashed or dotted line, and a group's opacity goes to each of its shapes. Dropped and counted in the message: clipping, masks, filters, markers, a gradient on an outline (its first colour is used), and parts painted with a pattern or with data that cannot be read. Pieces of one path that lie apart become shapes of their own; pieces that touch or lie in one another stay one shape, which keeps its hole but cannot be edited point by point. Text, `<use>`, embedded pictures and style sheets are not read: such an SVG is a PNG from the moment it is uploaded. Over 500 shapes, 20,000 points or 2 million characters nothing is changed and a message says so; a picture inside a group has to be taken out first; the crop, mask and filter of a picture are not carried over. The menu offers it for every uploaded picture, since only the file says whether it is a drawing, and says so for a photo. Checked in Chrome through the dev server that was already running: all 161 illustrations and all 2,309 icons were drawn once as pictures and once from their converted shapes with the editor's own paint code and compared pixel by pixel at 240 px; 153 illustrations differ in under 0.2 % of the pixels; the five that differ most (1 to 8 %, the two grain textures most) do so in their dashes and dots, three more between 0.2 and 0.4 % were not looked at, and the icons differ by a line of one pixel along their edges (under 2 %). The action itself was not clicked in the editor, and no uploaded file went through a real library (`src/core/svgImport.ts`, `svgGeometry.ts`, `svgColor.ts`, `src/editor/toolbar/svgShapes.ts`).
- **An edit in a shared design no longer writes the room's images to the disk again.** The uploaded images of a room were inside its record, and the server wrote and flushed the whole record for every edit: up to 48 MiB of pictures for moving one box. Each image is now a file of its own in a folder beside the room (`<room>.assets`), written once when it is uploaded; an upload no longer writes the design either. A room that an older server saved is still read, and its images are moved out the first time it is saved. Removing a room, by its owner or by expiry, removes its images. The design is also turned into text once for a save and not twice. Not done: an edit still writes the whole design with a flush of its own, and edits that arrive while a save runs are not saved together yet. A backup of the server needs the `.assets` folders as well as the room files.
- **Backups you do not have to remember.** The dashboard shows one quiet line when the last backup is old: "Your last backup is 3 weeks old. 12 designs changed since.", with **Back up now** (opens Back up & restore and starts the backup) and **Remind me later** (a week of quiet). It appears when the last backup is at least as old as the interval (2 weeks to begin with; 1 week, 1 month or Never in the dialog) and a design was made or edited since; a browser that never made a backup is reminded once its oldest design is 3 days old or it holds 5 designs, so a library that was just started is left alone. It is never a dialog, never in the editor, shown at most once per visit, and a polite status region that does not take the focus. In Chrome and Edge the dialog also has **Keep a backup file up to date**: choose a file once, and **Back up now** replaces what is in it with a new backup, with no download. The browser decides about permission and lets a page ask only right after a click, so Craftly writes when the button is pressed and never on a timer; the reminder's button writes straight away while the browser still allows it and asks for one more click when it does not. A write that fails or is cancelled leaves the backup that was in the file (the browser swaps the file only when the stream is closed, and a failed stream is never closed), and the person is told which it was: the file is gone, the browser said no, the disk is full, or the write did not finish. The card shows the file's name and when it was written, and **Stop using this file** forgets it. Firefox and Safari have no such API: nothing new is shown there and the download works as before. What is remembered (the interval, the snooze, the file) is in the library's `meta` store and is not part of a backup. Not tried in a real browser: the file was a stand-in object in the tests, so the "Save as" dialog, the permission question, the stored handle after a restart and the look of the notice and the card are unseen (`src/dashboard/backupReminder.ts`, `backupReminderState.ts`, `BackupReminderNotice.tsx`, `backupFile.ts`, [`docs/BACKUP.md`](docs/BACKUP.md)).
- **One design can be downloaded in several sizes at once.** The file type list of **Share > Download** ends with **Several sizes**: a list of the formats the dashboard and the Resize dialog know, each with its size in pixels, the size of the design first and its own family (social, print ...) before the others; the size of the design and up to three popular formats of its family are ticked to begin with. Every file is PNG, JPG (with the quality last chosen) or PDF (the one for screens, one PDF per size), and all of them come in one ZIP named `Title - 4 sizes.zip`, flat, each file named `Title - Instagram Story 1080x1920 - 2.png` (the page number only when several pages are exported); the pixel size is in every name, and a size is offered once even when four formats share it, so no two files have one name. Each size is made from a copy of the design that is refitted in memory exactly as Resize with "Scale content to fit" does it and then goes through the ordinary exporter: the open design, its undo history and the library are not written to. The choice of pages works as for every download; progress counts pictures over all sizes, and Cancel stops between two of them. One download holds 10 sizes and 250 million pixels over all sizes and pages; beyond that the panel says which of the two it is and what to change, and Download is off. A picture is exactly as many pixels as its size says (no size multiplier and no transparency here). The copy of one size is dropped before the next is made, but the encoded files are all held until the ZIP is written. Nothing is refitted more cleverly than Resize does: a wide design in a tall format is small in the middle. Not tried in a real browser: no ZIP was downloaded and opened, and the list was not looked at in the panel (`src/export/multiSizePlan.ts`, `multiSize.ts`).
- **The live server can remove rooms that nobody uses, and does not unless it is told to.** Rooms lived for ever, so a thousand rooms that nobody opens again filled a server for good. With `ROOM_TTL_DAYS` set, a room that nobody has edited, added an image to or joined (also only to look) for that many days is removed the way "stop sharing" removes it; the server looks once when it starts and then every hour. "Last used" is the time of the room's file, which a join sets at most once a day, so looking for old rooms reads none that has not expired. A room with somebody in it is never removed. Not set or `0` keeps every room, as before. Nobody loses a design by it: each person who opened a shared design has a copy in their own library, and only the link stops working. `docs/DEPLOY.md` suggests 30 days for a public server.
- **The print PDF can have a bleed and crop marks.** A printer cuts the sheet down to the page, and a page that ends exactly at its edge shows a white sliver wherever the cut is a fraction off. In **Share > Download**, the print PDF now has a **Bleed** switch (3 mm when switched on, 0 to 10 mm) and a **Crop marks** switch; a PDF for screens has neither. With a bleed the page is painted larger by the bleed on every side (`renderPage` has a `bleed` option): the background is stretched over it, elements keep their place, and one that hangs over the edge of the page shows in the bleed. The PDF page (`/MediaBox`) grows by the bleed, the `/TrimBox` is the design and the `/BleedBox` the design with its bleed. Crop marks are eight lines of 0.25 pt in registration colour (`/Separation /All`), two at each corner in line with the edges of the design, starting 6 pt beyond the bleed so they never touch it; the page grows by 27 pt more on every side to hold them. The links and the invisible text layer move with the design. Still RGB: no CMYK and no colour profile. Not sent to a printer and not opened in a PDF reader or a prepress program: the boxes, the marks and the offsets are checked by the tests, and the panel was looked at in the browser.
- **With a list of origins the live server turns the pages of other sites away, and one address may make ten rooms an hour.** `ALLOW_ORIGIN` only decided which page may read an answer: a page of any site could still make rooms (that request needs no permission beforehand) and open a WebSocket (which is not subject to CORS at all). With a list, the upgrade and every `POST`, `PUT` and `DELETE` that names an origin which is not on it is now refused with 403; a request that names no origin (curl, a server) is not, and `*` or no setting ask nothing, as before. Making rooms is limited per address: `ROOM_CREATE_PER_HOUR` (10; 0 for no limit) and then `429` with `Retry-After`, before the body is read; an IPv6 address counts by its /64, and what is remembered is at most an hour old. Behind a reverse proxy set `TRUST_PROXY=1`: the address is then the last entry of `X-Forwarded-For`, the one the proxy wrote, and exactly one proxy is trusted; when it is off the header is never read. An `ALLOW_ORIGIN` that is set to nothing counts as not set. The environment table of `docs/DEPLOY.md` now holds every variable the server reads.
- **Tables and charts can be filled from data.** The Data panel of a table and of a chart has a block "Import data": a field to paste into (cells copied from a spreadsheet, or CSV text) and a button to choose a `.csv`, `.tsv` or `.txt` file of at most 2 MB. A table takes the rows as its cells, grows or shrinks to fit, and keeps its look and its width (columns that are still there keep their share, and the table gets taller only when its rows would be lower than their text). A chart takes the first column as labels, the first row as the names of the series when it holds no number, and the rest as numbers: "1,234.5", "1.234,5", "12,34,567", "12%", "$5", "5 €" and "(123)" for -123 are read, one decimal mark for the whole paste, decided by the numbers that can only be read one way; a cell that is empty or not a number becomes 0 and the message says how many. A pie or donut still shows the first series only, and the message says so. Each import is one undo step and tells what came in and what was left out: a table holds 200 rows by 50 columns, a chart 100 rows by 12 series, a cell 1,000 characters, and text is read up to 2 million characters, so a huge paste cannot freeze the editor. Two shortcuts: a paste on the canvas while one table or chart is selected fills it when the text is plainly a table (two rows and two columns at least, every row alike; anything else is a text box as before), and a paste of cells into one cell of the Data panel spreads from that cell on, adding rows and columns. The reader finds comma, semicolon or tab by itself and knows quoted cells, doubled quotes, line breaks in quotes, Windows line ends and a byte order mark. What is imported is text and numbers only; nothing of it is run or fetched. A paste of a table on the canvas with nothing selected is still a text box: offering a table there would surprise people who paste ordinary text with tabs. Files in UTF-16 (the "Unicode text" of some spreadsheet programs) are refused as not plain text. Not tried in a real browser (`src/core/delimited.ts`, `src/editor/panels/context/dataImport.ts`, `ImportData.tsx`).
- **The live server warns when other machines can reach it.** It speaks plain HTTP and WebSocket and has no TLS of its own, which is right behind a reverse proxy and wrong on its own, and it started on `HOST=0.0.0.0` without a word. Now it prints a warning at its start whenever `HOST` is not an address of the machine itself (127.x.x.x, `::1`, `localhost`): links, designs and pictures are not encrypted on the way, a page loaded over `https://` cannot connect, put a proxy that terminates TLS in front (docs/DEPLOY.md, section 2.4) or set `HOST=127.0.0.1`. The server still starts; the Docker image, which sets `HOST=0.0.0.0`, prints it at every start. The decision is `listenWarning` in `src/server/listenWarning.ts`.
- **The text of a PDF can be selected, searched and copied.** A PDF page was one picture and nothing else. It is still that picture, byte for byte, and over it now lies the page's text in a layer that is never painted (text rendering mode 3, the way a scanned and recognised document is written). The lines are those of `layoutText`, the layout the canvas paints, so breaks and order are the page's; every word is put at its own place and stretched to the width it has in the picture, turned with its element and its groups (`src/export/pdfText.ts`). Text elements, list markers, table cells and curved text (word by word along the arc) are written; chart labels, hidden or fully transparent elements and lines wholly outside the page are not. No font is embedded: the layer uses the standard Helvetica in WinAnsi, and a character WinAnsi does not have (Cyrillic, Greek, CJK, emoji ...) gets a place in an extra font with an encoding of its own, 223 characters to a font and as many fonts as the document needs; every font has a `/ToUnicode` map, so what is copied is what was typed (`src/export/pdfFonts.ts`). A page without text is written exactly as before. On for both PDF presets, with no switch in the panel (`pdfText: false` in the export options turns it off). Not tried in a PDF reader: there is none on the machine this was written on, so the files are checked by the tests' parser (offsets, lengths, operators, maps) and not by selecting text in Acrobat, Chrome or Preview.
- **A production build carries its Content-Security-Policy in the page.** Only Netlify and Cloudflare Pages read `public/_headers`, so a build on any other host had no policy unless its operator wrote one. The build now writes the policy into `index.html` as a `<meta http-equiv="Content-Security-Policy">` tag, right after the charset line (`cspMeta` in `vite.config.ts`). The text is read from the line in `public/_headers`, which stays the one place the policy is written down, less `frame-ancestors`, `report-uri` and `sandbox`, which a browser ignores in a meta tag; so a frame around Craftly can still only be refused by a header. The development server has no tag. A site with a live server or a mirror of the models builds with `VITE_CRAFTLY_CSP_CONNECT="https://live.example.org wss://live.example.org"`, which adds the hosts to `connect-src` in the tag and in the `_headers` file of the build, so the two agree; a value that is not a list of hosts stops the build. A browser that gets both a header and a tag enforces both. Because every production build now has a policy, the production run of the journeys in CI names the port of its live server in the build (`LIVE_PORT=8788`); that run has not been made yet.
- **A room that the server cannot read is no longer reported as gone.** A disk that failed and a damaged room file were both answered as "not found", so people were told that their shared design is no longer there, and nothing was written to the log. Only a file that does not exist means that now (`FileStorage.load`); anything else is logged with the id of the room, a connection is turned away with the new reason `server-error` ("The server has a problem and could not open this shared design. The design may still be there: try again later."), and an HTTP request is answered 500, which the browser asks again later for an image. Every request the server answers with an error of its own is logged now. `GET /api/health` keeps its answer for five seconds, where it wrote a file and waited for the disk for every anonymous request (`healthCacheMs`). Told to stop, the server waits no longer than `SHUTDOWN_TIMEOUT_MS` (10 seconds) for saves and requests that are at work, and leaves with exit code 1 and a line in the log when that runs out or closing fails, where it used to wait for ever and let a failure go by unseen. An older browser does not know the reason `server-error` and reports it as something it does not accept from the server.
- **A slow image upload can no longer undo newer edits or bring back a deleted room.** The server kept its copy of the room in hand while the body of an upload arrived, which may take minutes, but a room with no connection leaves memory after a minute. When it was read again meanwhile (somebody joined and edited, or the owner stopped sharing), the upload saved its old copy over what had happened since: the edits were gone, and a room that had been deleted was back with its old keys valid. A room now stays in memory while an HTTP request is at work on it, and an upload is saved only into the room that is in memory at that moment; into a room that was stopped meanwhile it is answered with 404 (`src/server/live.ts`).
- **An uploaded SVG is checked before it is stored.** An upload is shown through a `blob:` address, and a browser that is sent to such an address ("Open image in new tab") runs what it finds there as a page of the site; an SVG with a script in it was stored as it came. Now an SVG that is plain drawing (`svgProblem`) is kept as it is, and any other, one with a style sheet, a comment, an XML declaration, a script, a handler or a link, is drawn through an image element onto a canvas and stored as a PNG (twice its size, between 1024 and 2048 pixels on the longest side), and the person is told once: "This SVG had parts Craftly does not keep, so it was added as a picture." One that cannot be drawn is refused. The rule is in one place (`checkUpload` in `src/core/assets.ts`) and holds for the upload field, a drop, the clipboard, a project file, a backup and a picture from somebody else in a shared design. A file that comes with a type that is no picture type (a `.png` called `text/html`) is stored as a PNG and never under that type. Many SVG files from drawing programs carry a style sheet or a comment, so they now arrive as pictures and no longer as vectors. Uploads that were stored before are not checked again.
- **The live server limits what one visitor may cost it.** Anyone can make a room and so hold an edit key, and one connection could stall the server for everybody. A connection that does not read what it is sent is dropped when more than twice the size of a design waits for it in memory (`maxBufferedBytes`); the browser comes back by itself. A `join` is answered with the whole design, so it has a small allowance of its own (four, then one every two seconds; `joinRate`). Bytes are counted beside messages (8 MiB, then 1 MiB a second; `byteRate`). A message of more than 8 KiB from a connection that has not shown its key is not parsed (`maxUnjoinedMessageBytes`). The server holds at most 5,000 connections (`maxConnections`: the next upgrade is answered with 503) and lets at most 20 wait at one room without a key (`maxWaitingPerRoom`: the next is asked to come back, close code 1013). All are options with these defaults and settings of the environment (`MAX_CONNECTIONS`, `MAX_WAITING_PER_ROOM`, `MAX_BUFFERED_BYTES`, `MAX_UNJOINED_MESSAGE_BYTES`, `BYTE_BURST`, `BYTES_PER_SECOND`, `JOIN_BURST`, `JOIN_EVERY_MS`; the table is in docs/COLLABORATION.md). And a batch that adds elements no longer walks the whole design once for each of them: `applyOps` counts the ids once for a batch (`src/collab/ops.ts`).
- **Two fingers on the canvas zoom and move the view.** On a touch screen the distance between two fingers changes the zoom (within 5 % and 400 %) and the point between them moves the view; the point of the design they met on stays between them, as with Ctrl + wheel. A pinch changes nothing in the design, leaves no undo step and keeps the selection: a press of the first finger that had not moved anything yet is dropped and what it selected is put back, while a move, resize, rotation, marquee or drawing that was already under way goes on and the second finger is ignored, as before. The pinch ends when either finger lifts, is cancelled or loses its capture, and the finger that stays does nothing until it has lifted. One finger, the mouse, the pen and the wheel work as they did. The workspace and its scroller have `touch-action: none`, so the browser no longer zooms the page or scrolls the canvas under the fingers (panels beside the canvas scroll with one finger as before). Tested with made-up pointer events; not tried on a real touch screen (`src/editor/canvas/pinch.ts`, `controller.ts`).
- **A Dockerfile for the live server and a deploy guide, and the image has not been built.** `Dockerfile.server` builds the bundle in one stage and runs it in a second that holds only Node, the bundle and `ws` at the version and checksum of the project's lock file (`scripts/server-runtime-package.mjs` writes the two package files from what the bundle imports), as the user `node`, with the rooms in a volume, and a health check on `/api/health`. There is no Docker on the machine it was written on: its steps were run by hand outside a container, and no image has been built from it. [`docs/DEPLOY.md`](docs/DEPLOY.md) covers the editor on a static host, the server with and without Docker, every environment variable in one table, a reverse proxy for TLS (Caddy and nginx, with the WebSocket upgrade, `X-Forwarded-For` and the body size nginx needs), where the data lives and how to back it up, what to add to `connect-src`, and a list of what is not there yet (a built image, a real host, metrics, more than one server, a load test).
- **The actions of the CI workflow are pinned to commits.** `uses: actions/checkout@v4` runs whatever the tag `v4` points to on the day, and a tag can be moved. The three actions (`checkout` 4.4.0, `setup-node` 4.4.0, `upload-artifact` 4.6.2: the latest releases of the major version in use, which are the commits `v4` pointed to on 2026-11-13) are now named by their full commit, with the version in a comment. Dependabot already watches `github-actions` weekly and keeps such pins up to date. The workflow was not run after the change, because nothing is pushed.
- **CI builds the bundle of the live server and starts it.** Nothing ran `dist-server/live.mjs` before, so a bundle that did not start would have been found by the first person to deploy it. `npm run server:smoke` (`scripts/server-smoke.mjs`) builds the bundle, starts it on a free port with a temporary data folder, waits for `GET /api/health` to answer 200, makes a room with `POST /api/rooms`, sends SIGTERM and requires exit code 0; CI runs it after the production build. On Windows a process cannot be asked to stop, so the clean exit is checked on Linux and macOS only. The README now says that `server:build` uses the esbuild that Vite brings along, which is not named in `package.json`.

## Unreleased fixes from a second review of the code (2026-11-13)

- **The live server no longer drops every connection after a minute.** The server pings each connection and drops one that did not answer by the next round, but it listened for the answers in a place that an upgrade handled by hand never reaches, so no answer was ever seen: every browser lost its connection after 30 to 60 seconds, came back, and was sent the whole design again. The answer is now listened for on the connection itself (`src/server/live.ts`; the interval is the new option `heartbeatMs`).
- **A room leaves the server's memory when its connection went away while the room was being read.** Such a room had nobody in it and nothing that would ever take it out again, so a visitor who opened and closed a connection to each room kept them all in memory.
- **A copy of a shared design is a design of its own.** "Make a copy" and "Resize a copy" copied the room and its keys with the design, so the copy opened as the shared design and every change to it went to everybody in the room (`duplicateDesign` in `src/core/library.ts`).
- **An SVG download writes only the line ends and corners SVG knows.** The two words of a stroke went into the markup as they were, and a design from a file is not checked that far down: text with a quote in it ended the attribute and began markup of its own, a script included, in every SVG a person downloaded from that design.
- **Resizing a selection with no height or no width keeps real numbers.** Two lines side by side make a selection without height; dragging a handle divided by it, and positions and sizes that are no number were written into the elements and saved (`scaleOf` in `src/editor/canvas/resize.ts`). A side that had no length is now left as it is.
- **What is dropped on the canvas is checked like a file.** Any page can put data of Craftly's type on a drag. It went onto the page as it was; now only elements the renderer can draw are kept, without pictures from the web, a dropped picture must be one of the editor's own kinds and have a size, and a background must be a fill (`readDragPayload` in `src/editor/insert.ts`).
- **A graphic is plain drawing or it is left out.** The markup of a graphic was only checked to be text where a design comes in, and an SVG download cleaned it with a list of things to take out, which could be walked around (a script behind a prefix, a page in another namespace, an address written with an escape). A graphic whose markup is anything but plain drawing (`svgProblem`) is now not accepted from a project file, a backup, the clipboard or a drop, and counted with what was left out; an SVG download writes a graphic only when all of it is plain drawing and leaves it out with a warning otherwise. Every graphic the app makes passes. The ids of a graphic are renamed with a function, because an id such as ``$` `` stood for the markup around it.
- **Working together: an image the server will never take no longer stops everything.** A failed upload closed the connection and tried again about twice a second for good, with every later edit waiting behind it. An image the server refuses (too big, the room is full of images, gone) is now given up like an edit the server refused, with a recovery copy and a message, and the rest goes on; a failure that may pass is tried again with waits that grow to ten seconds.
- **Working together: edits that never reached the server are not lost without a word.** The edits that wait are kept for a reload of the same tab only. A tab that was closed with edits waiting now leaves a mark, and when the design is opened again the version on the device is kept as a recovery copy in Projects, and said so, before the shared version is shown.
- **Working together: a duplicated tab goes on under a name of its own.** A tab duplicated while it had edits waiting shared its name and batch numbers with the first: the two closed each other's connection for good, and the server took a batch of one for a batch of the other. A tab that is told another connection took its place takes a new name and sends its waiting edits under it.
- **Working together: one recovery copy for refused edits.** A room that is full refuses every edit, and each one added another copy of the design to the library and another message. There is one copy for a design in a tab, brought up to date each time, and one message.
- **Working together, smaller things.** An operation that moves an element into something that is not a group leaves it where it was (it was deleted). A yes to connecting to a new server is for one link, not for the next one opened in the same tab. A design larger than one batch may carry can be shared (its size in bytes is the limit).
- **After an update, an offline start opens the new version.** The service worker asked every cache for the app's page and got the one of the build before, which cannot open a database the new build has upgraded. It asks its own cache first. On a host that sends `/index.html` on to `/`, the page is stored as an answer of its own, so the first offline reload works.
- **An upload is saved when the browser has stored it.** Single writes to the library were reported done when the write was taken, but a browser without room says so only when the transaction ends: a picture could be on the page and not in storage. Writes and deletions now wait for the transaction and always fail with an error, so the "out of room" message is shown where it was lost before.
- **A backup brings back only uploads that are pictures.** A backup made by hand could store any file under any type in the app's storage.
- **A drag ends, whatever happens to the pointer.** A second finger on the canvas during a drag took the drag over and left the undo step open, which switched undo off until the design was opened again; it is ignored now. A drag that loses its pointer ends like a cancelled one, and so does the drag of a guide.
- **Copy, cut and paste stand back where the keys do.** With a dialog open or while presenting, Ctrl+X deleted the selection behind it and Ctrl+V pasted into the page underneath; they are left to the browser there.
- **Space no longer counts as held after the window lost focus**, so clicks do not pan after coming back.
- **An edit made while a save was running is written when the editor closes** (it was dropped when the editor closed before that save ended).
- **Zooming while editing text keeps the caret and the selection**: the sizes are changed where they are, and the text is not built again.

## Unreleased fixes from testing by hand (2026-11-11)

- **Text wraps at the edge of the page.** A text box that grows as wide as its text used to keep growing past the page: a sentence typed into a new text box ran off the right edge, with the handle to make it narrower out of reach. A server that does not answer with the part that was asked for is asked for the whole again; a cancelled download and a wrong file keep nothing; the file is still checked as a whole against its pinned size and SHA-256 (`src/ml/download.ts`).
- **Working together: a person is told when the text they are typing in is deleted by someone else.** The editing box used to close without a word and the next keys ran shortcuts of the canvas.
- **On a phone the side panel folds away when something is added from it**, so that what was added can be seen (`src/editor/foldPanelOnInsert.ts`). A panel of options for the selection stays open.
- **Small things.** A rotation beyond a full turn is the turn that is left over (725° is 5°, it used to become 0°). Paper sizes are named as the paper is ("210 × 297 mm" for A4, which is stored as 794 × 1123 px and was shown as "210.08 × 297.13 mm"). The table picker says "1 row by 1 column". The chart panel says that a negative number gets no slice in a pie or donut.
- **A double click on a table or a chart opens its data.** For a table the keyboard goes into the cell that was double-clicked, with its text selected. Before, a double click did nothing and what was typed next ran the one-key shortcuts of the canvas (a circle, a line, a text box).

- **Pen tool**: vector paths made of points and curves (the "vector gaps" item of [`reports/Craftly versus Figma.md`](reports/Craftly%20versus%20Figma.md)). Choose **Pen** in Tools or press `P`. A click places a corner point; a press that is dragged pulls a curve out of the point (a handle on each side; a drag of under 3 px stays a corner); a click on the first point of a path of three or more points closes it, and a click on the last point, `Enter`, `Esc` or choosing another tool ends it open; `Shift` keeps a side at a multiple of 45 degrees and `Backspace` takes the last point back. Undo belongs to the path while it is placed: `Ctrl+Z` and the Undo button take the last point back too and never reach into the design under it (Redo is off until the path is finished), and choosing another page in the middle of a path finishes it on the page it was drawn on, leaving the new page, the Pen and the selection as they were. While it is placed the path is drawn as a preview (the path so far, the side the next click would make, the handles of the last point and a mark on the first point when a click would close the path), and it becomes one undo step. An open path is a line in the colour and width of the Draw options, a closed one is filled with that colour and has no outline. Editing changes the element's box to fit the new curve while every point stays where it is on the page, also when the element is turned or mirrored, and each gesture (or run of arrow presses) is one step to undo. A path with arcs, relative commands or several pieces has no Edit points button, and a locked path is not opened (a lock that is set while its points are open closes them).

- **Live editing, the core and a server** (`docs/COLLABORATION.md`): `src/collab/` holds what several people editing one design at the same time need, as pure code that a server will run too.
