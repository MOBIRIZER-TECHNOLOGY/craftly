# Security policy

## Supported versions

Only the latest version on the main branch is supported.

## Reporting a vulnerability

Please do not open a public issue for a vulnerability.

Report it privately instead. On GitHub, use **Security > Report a vulnerability** on this repository (the maintainers need to have private vulnerability reporting switched on in the repository settings); if that button is missing, contact the maintainers privately through the address on their GitHub profile.

Please include what you found, the steps to reproduce it, the version or commit, and what an attacker could do with it. The maintainers will acknowledge the report, keep you informed about the fix, and credit you in the changelog if you want that.

## What counts

The local editor runs in the browser. Its security concerns include:

- script injection through an imported `.craftly` project file, an uploaded SVG, or template or catalogue data. An uploaded picture is shown through a `blob:` address, and a browser that is sent to such an address runs what it finds there as a page of the site, so what is stored is checked first (`checkUpload` in `src/core/assets.ts`), wherever it comes from: the upload field, a drop, the clipboard, a project file, a backup, somebody else in a shared design. An SVG that is plain drawing (`src/core/svgSafety.ts`) is kept as it is. Any other SVG (a style sheet, a comment, a script, a handler, a link) is drawn through an image element onto a canvas and stored as a PNG, and the person is told; one that cannot be drawn is refused. Nothing is stored under a type that is not a picture type. Uploads stored by an earlier version are not checked again
- data leaving the device when it should not, or an on-device model downloaded without the person agreeing
- a model file accepted although its size or SHA-256 differs from the one pinned in `src/ml/registry.ts`, or a model added from a file (File > On-device models > Add from a file) that is used unchecked
- a crafted backup file (a ZIP chosen under Back up & restore) that crashes the restore, brings in an id that breaks a link or a file name, stores something that is not a design, or makes the app use unbounded memory or time (the reader refuses encrypted and ZIP64 archives, checks every file's CRC-32, limits what a compressed file may unpack to, and treats the manifest and every design as untrusted; see `docs/BACKUP.md`)
- the service worker or its caches serving something other than the app
- weaknesses in how designs and uploads are stored in the browser
- a known vulnerability in a package that ships in the app (see `THIRD-PARTY-NOTICES.md`)
- a shared design, or a live server that a link leads to, that makes the editor run code, load something it should not, or accept a design that is not safe to draw (see "Live editing" below)

Out of scope: problems that need a modified browser or a malicious extension, running out of memory by opening a very large file on your own device, and findings in development-only tools.

## Live editing (optional)

Craftly runs locally by default. Optional live editing uses a self-hosted Craftly server. Starting or joining a live session sends shared design content and uploads to the selected server. See the [collaboration deployment guide](docs/COLLABORATION.md).

- **Treat invite links as passwords.** A link carries the room ID and an edit or view key in its fragment. The socket URL names the room, and the first WebSocket message presents the key. The server stores SHA-256 hashes of the edit, view and owner keys. Project files and library backups omit live links and credentials. Handle older files that contain these fields as secrets.
- **Everything that arrives is checked, on both ends** (`src/collab/protocol.ts`). The server checks what a browser sends, and the browser checks what the server sends, because a link names the server and anybody can make a link. The checks: the form of every operation, depth, lengths and counts, that every element has what its kind cannot be drawn without and of the right kind (numbers for its place and size, a list of paragraphs for a text: the same table a project file is read with, `src/core/usableElement.ts`, asked of elements that are added and of elements whose properties a batch changed), no property that changes what an object is (`__proto__` and others), pictures and links that may only point to the editor's pictures, the web, mail or a phone (never script), the colours a graphic is recoloured with (plain `#hex`, `rgb()` or a name, because they are put into its markup as they are), the blend mode of an element (one of fifteen names, because the name goes to a canvas and into a `style` of an exported SVG as it is), and the markup of a graphic, which must be plain drawing: a short list of shapes, gradients and masks written as strictly as XML (`src/core/svgSafety.ts`). That check is a list of what is allowed and not a pattern for what to keep out, so `<svg/onload=…>`, an attribute without quotes and a character reference that spells `javascript:` do not get through; its tests have the XML and HTML parsers of a test browser read thousands of damaged drawings, and whatever the check accepts must come out of both as nothing but drawing. A browser ends the session at the first message it cannot use, closes the connection, keeps the design as it was and says why; nothing of that message is used. Messages, designs, rooms, people per room and messages per second are limited.
- **Seeing each other is not stored and cannot carry code.** Pointers, selections and names (`presence`, `src/collab/presence.ts`) are passed on by the server and kept nowhere, not in a room's file either. They are checked on both ends like everything else: a name is at most 40 characters of plain text (no control characters, no marks that turn text around) and is put into the page as text; a pointer is two finite numbers; a selection is at most 50 short ids; any other field makes the message invalid. There is no colour, address or markup in it at all: a person's colour comes from a fixed list in the editor, chosen by the number the server gave their connection, and a browser cannot choose that number, so nobody can speak for another person in the room. The server limits how often a connection may say where it is and drops the rest. A person's name and pointer are seen by everybody in the room, also by people with the view link, and by the server.
- **Comments are plain text, and only those who said they understand them are sent any.** A comment and a reply (`src/core/comments.ts`) are checked field by field on both ends and in project files and backups: ids that look like ids, finite numbers, a text of at most 2,000 characters of plain text (no control characters but a tab and a line break, no marks that turn text around), a name of at most 40, an author's colour that is a place in the fixed list of twelve and never a colour, at most 500 comments and 200 replies to one, and no field that a comment does not have. What people wrote is put into the page as text, never as markup, and goes into no address and no CSS. Comments are stored in the room's design and count against its size. A browser receives comment operations only when its join said that it understands them, so a browser from before comments is never sent a kind of message it would take for an attack. Comments are seen by everybody in the room, people with the view link included, and by the server; who wrote a comment is not proven (there are no accounts), and the server does not check that only its author changes or deletes it.
- **Join rooms on servers you trust.** A joined room becomes a local copy. Its server can see shared content, edits and uploads, and the browser may fetch images referenced by the room. Use the deployment policy to restrict permitted server and image origins.
- **Deployment limits.** Room creation is anonymous unless the server is given a key for it (`ROOM_CREATE_KEY`: one shared secret, sent in a header, compared in constant time, never logged; the editor asks for it and does not store it). Set network and rate limits at a TLS reverse proxy before public hosting. The server has no TLS of its own: it listens on 127.0.0.1 unless `HOST` says otherwise, and then prints a warning at its start that links, designs and pictures cross the network unencrypted unless a proxy that terminates TLS is in front. The server caps document size at creation and on edit, and limits shared uploads to 9 MiB per image and 36 MiB per room. The SVG exporter sanitizes graphic markup separately from the project and backup readers.
- **Permissions.** An edit key grants editing and image uploads. A view key grants read access to the design and its room images. A separate owner key authorizes deleting the room. Older rooms lack this key and require operator cleanup or recreation. An operator key (`ADMIN_KEY`, off unless set) lists rooms (titles, sizes, times, never a key or a hash of one) and removes them; it is refused for any request with an `Origin` header, has no CORS headers, and ten wrong keys in an hour lock an address out. Counters for a scraper (`METRICS_KEY`, off unless set, `GET /metrics` with a bearer token) are guarded the same way and name no room, person or address. The server has no accounts or per-person audit trail.
- **Content-Security-Policy.** A page that uses live editing needs the server's origin in `connect-src` (README).
