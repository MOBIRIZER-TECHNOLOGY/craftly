# Live editing: the core and the server (built 2026-11-09), and what is left

Several people editing one design at the same time is the headline feature of [`INVESTOR-READINESS.md`](INVESTOR-READINESS.md) (milestone M2) and Phase C of [`PLAN-DIAGRAMS-AND-COLLABORATION.md`](PLAN-DIAGRAMS-AND-COLLABORATION.md). This document describes what exists, why it is built the way it is, how it is checked, how to run the server, and what is still to build. **Without a server nothing changes for people who use Craftly:** the static, serverless editor is as it was, and a design that is not shared never touches this code. What exists: the pure core (`src/collab/`), the connection a browser uses (`src/collab/live.ts`), a server (`src/server/`), the store's part (a shared design has its own undo and takes in what others did), and the interface (the Share panel, a status mark in the top bar, the link page), checked together over real sockets and in three real browsers.

## The model, in one page

**What is shared.** The title, type, size, unit and guides of the design (`DESIGN_KEYS`), its pages and their elements, groups included. The id, the dates, the folder, the star and the trash of a design belong to each person's own library and are never sent (`withShared` lays the shared parts over a person's own record).

**Operations are id-addressed and property-level.** `el.set` carries the new value of every property that changed (and the names of those removed), so two people who change different properties of one element both keep their change; for the same property the batch the server applied last wins. `el.add` / `el.del` / `el.move` and `page.add` / `page.del` / `page.move` / `page.set` / `design` complete the set. Nested values (a fill, a table's cells) are replaced as a whole; the characters of a text go as a splice that is merged with what others type (`el.text`, see "Two people typing in one text box").

**`diffDesign(prev, next)`** follows the objects that did not change by reference (the store's structural sharing), compares the rest property by property (`jsonEqual`, so a new object with the same content sends nothing) and emits deletions first, then property changes, then moves, then additions, so that an id is never twice in the design while a batch is replayed (an element that goes into a new group is a deletion at the top and an addition inside the group, in that order). An id that changes its kind is a deletion and an addition. Moves are as few as it takes (not a rewrite of the list); additions come in the order of their final index.

**`applyOps(design, ops)`** is deterministic, pure, shares what it did not change, and never throws on what it cannot place: an operation for a missing element is ignored, an id that is already in use (or that appears twice in what is added) is not added again (so the same batch twice does no harm and a duplicate id cannot get in), an index out of range is clamped, the last page is never deleted, a group cannot be moved into itself or into a group that is not there, `id` / `type` / `children` of an element and `id` / `elements` of a page cannot be set, and `__proto__`, `constructor` and `prototype` are never set.

**What may arrive (`checkOps`).** Every operation must have its proper form (kinds, ids of 1 to 200 characters, finite indexes, objects where objects belong, at most 10,000 operations per batch, at most 200 properties per `set`, groups at most 32 deep), and every value in it is walked: at most 32 levels deep, texts at most 1,000,000 characters, lists at most 100,000 long, objects at most 2,000 keys, numbers finite, no property called `__proto__`, `constructor` or `prototype`, at most 300,000 values in one batch; an address (`src`, `originalSrc`, `link`, `href`, `url`) must start with `asset:`, `builtin:`, `https://`, `http://`, `mailto:`, `tel:`, `#`, `/`, `blob:` or be a `data:image/…` (so never `javascript:` or a page); the markup of a graphic (`svg`) must be plain drawing by `svgProblem` (below); and the colours a graphic is recoloured with (`colors`) must be written plainly (`isPlainColor`: `#hex`, `rgb()` or `rgba()` with numbers, `black`, `white`, `transparent`), because `recolorSvg` puts them into the markup as they are; and a property called `blend` must be one of the fifteen blend modes of `src/core/blend.ts` (`isBlendMode`) or nothing (`null` or left out), because the name goes to a canvas and into the `style` of an exported SVG as it is (`"normal"` is refused too: Normal is the absence of the property, and the editor sends the removal as `unset: ["blend"]`). Every template page and every graphic of the app passes (`content.test.ts`); that test is what found that pictures also use `builtin:`.

**Markup is plain drawing or it is refused (`svgProblem`).** The first version of this check was a pattern for what to keep out (`<script`, `on…=`, `javascript:`), and a pattern can be walked around: a browser reads `<svg/onload=…>` as an event handler and an attribute without quotes as one too, and a character reference can spell `javascript:`. It is now a list of what is allowed, read with a tokenizer of its own as strictly as XML is read (no DOM, so the server runs it too): the elements are shapes, paints, masks and filter primitives (`svg g defs symbol path rect circle ellipse line polyline polygon linearGradient radialGradient stop clipPath mask pattern marker title desc filter` and the `fe…` primitives that draw); the attributes have plain names and quoted values, none starts with `on`, there is no `style` and no `xml:base`, `xmlns` can only be the drawing's own and `xlink`; `href` can only point to `#something` and any `url(…)` can only refer to `#something`; a character reference can only be one of the five that XML names; there is no comment, declaration, instruction, CDATA, script, link, style sheet, picture or animation; tags nest and close, one drawing, at most 100 deep, 100 attributes to an element. Everything it lets through is the same thing to an XML parser and to the HTML parser of a browser, which is what makes it safe to draw, to put into a page and to write into an exported file; `svgSafety.dom.test.ts` has the parsers of the test browser read 4,000 damaged drawings and requires that whatever is accepted comes out of both as nothing but drawing. What the app ships (288 graphics, templates, QR codes, icons) uses 14 elements and about 40 attributes, all on the list; a graphic that needs something more means a line on the list and a test.

**An element is checked as strictly as one of a file (`elementProblem`, `checkSets`).** The checks above look at the form of an operation and at the content of its values, and until 2026-11-14 an element that arrived whole needed only an id, a kind and, for a group, its children: an editor could add a shape with `x: "a"` or set `paragraphs: 5` on a text for everybody in the room, and the renderer throws on that for all of them. The file importer always asked more (`isUsableElement`). Both now ask the same, from one table (`REQUIRED_PROPERTIES` in `src/core/usableElement.ts`, which `projectFormat.ts` hands on and the server bundles; it imports only the markup check): the place and size of every element (`x`, `y`, `width`, `height`, `rotation`, `opacity`) are finite numbers, and each kind has what it cannot be drawn without (a text its `paragraphs` as a list, `fontFamily`, `fontSize`, `fontWeight`, `lineHeight` and `effect`; a shape its `shape`; a line a `stroke` with a `width`; a picture `crop`, `filter`, `mask` and a `src` that is text or null; a graphic `svg` that is plain drawing, `viewW`, `viewH` and `colors`; a table `cells`, `colWidths`, `rowHeights` and `fontFamily`; a chart `labels`, `series` and a `palette` that is not empty). A property that is not in the table passes as before. This holds for every element that arrives whole: `el.add`, the elements of `page.add` (groups walked to the bottom), a design that makes a room, and a design that is a welcome. A change of properties (`el.set`) cannot be judged from the operation, which names an element by id and not by kind (`stroke: null` is fine for a shape and fatal for a line). So the server applies the batch to a copy first, which is safe whatever it holds, and then asks the same question of every element the batch set or unset a property of, as the whole batch leaves it (`checkSets`); a batch that leaves one unusable is `rejected` as a whole, with the name of the property, and nothing of it is saved or passed on. A browser asks the same of the operations a server sends, and ends the session (`invalid`) with a server that sends such a thing. An element that was not usable before a batch is not held against that batch: a room made before this check may hold one, and refusing every later change to it would not mend it. **Such a room cannot be joined by a browser with this check, though**: its welcome is refused as `invalid`. Nothing the editor itself makes is affected: a test puts one element of each kind from the factory, the design that has every field (`src/test/schema/complete.ts`) and every template of the catalogue through the check. What is not checked: the properties of a page (a page without a background can still be added), and what is inside the lists and objects the table names (a run of a paragraph, a cell of a table).

**What a browser believes (`parseServerMsg`, `checkDesign`).** A link names the server and anybody can make a link, so the browser does not take for granted what comes back. Every message is read by `parseServerMsg` before any of it is used: its kind, the form of every field (counts are whole numbers, a role is `edit` or `view`), and its content. A `welcome` carries a whole design, which must pass `checkDesign`: a title, a size, at least one page, elements that are elements, and every value in it walked like the values of a batch, but without the limit of what one batch may carry (a design that many batches have built up can hold more than one) and with a deeper allowance (pages and groups inside groups). The `ops` of a message must pass `checkOps`, the same check the server applied when it took them in. A message of a kind that this version does not know is ignored, because a newer server may send more. The first message that cannot be used ends the session: nothing of it is applied, the design that is shown stays as it was, the connection is closed and not tried again, and the status is `denied` with the reason `invalid`, which the Share panel and the page of a link say in words ("The server sent something that Craftly does not accept ..."). Nothing that a browser had made while it was away is sent to a server that has shown what it is.

**The server decides the order.** `Room.receive` checks each batch from a person who may edit, persists the new revision, answers the sender with `ack` and sends the same operations to everyone else as `ops`. Every copy therefore applies the same batches in the same order from the same start and ends the same. A batch carries a number from its sender; a number the server has seen is acknowledged and not applied again (`lastSeq` per client name, saved with the room; see below for how long). A batch that `checkOps` or `checkSets` refuses is answered with `rejected`; a viewer's batch is always refused.

**What a room remembers of its clients, and how it forgets (`seqs`, `seqSeen`, `seqFloor`).** The last number per client grew by one entry for every page load that ever edited a room, was never pruned, and is written with every save. It is bounded now (`src/collab/room.ts`): a client that is not in the room and was last seen (joined, or had a batch applied) more than 30 days ago is forgotten when the next batch is applied, and above 1,000 clients those seen longest ago go first. A client that is in the room is never forgotten. Forgetting must not let a batch count twice: a forgotten client may come back and send again a batch that was applied but whose `ack` it never heard, and a room with no entry for it would take the batch for new. So the room keeps one number more, the **floor**: the highest last number of any client it ever forgot (`seqFloor` in the record; `seqSeen` holds the times). A client the room has no entry for is treated as one whose last applied batch was the floor: its welcome says `lastSeq: floor`, and a batch of its numbered at or below the floor is acknowledged and not applied. Everything a forgotten client had applied is numbered at or below its own last number, which is at or below the floor; the floor never goes down and is saved by the same write that drops the entry. So no batch of a forgotten client is ever applied a second time, also after a restart. The price: a batch that a forgotten client had sent and that was **not** applied before it stayed away for a month is dropped as well, because the room cannot tell the two apart. A client the room has never seen pays nothing, with a browser of this version: the session keeps the highest number it ever handed to a connection (`sent`, kept for a reload with the rest), and at a welcome it gives up only batches at or below `lastSeq` that were sent; batches that never left the browser (made before the first welcome, or waiting when the tab went on under a new name after close code 4000) get the numbers after `lastSeq`. **A browser with older code in a room that has forgotten somebody** drops what it made before its first welcome, without a word, when those batches are numbered at or below the floor; the service worker keeps an old editor around for a while, so this can happen until it has updated. A record from an older server has no times: its clients count as seen when the room is opened. If the server stops in the moment between the save that forgets a client and that client's next batch, a client that had come back during that save is welcomed with the floor after the restart, like any forgotten one.

**Seeing each other (presence).** People in a room see each other's pointers and selections, each with a name and a colour, and a short list of who is here in the top bar. This is a message kind of its own, `presence`, and it is **ephemeral**: it is passed on and kept nowhere. It is no part of the design, has no revision and no batch number, is never acknowledged, never saved (a room record holds nothing of it) and may be dropped whenever there is too much of it; whoever misses one hears the next.

- **A browser says** `{ t: "presence", name, page, pointer, selection, editing }`, all five always: `name` is plain text of at most 40 UTF-16 units with no control characters, line separators or marks that turn the direction of text around (`""` for a person who gave none); `page` is the id of the page they have open, or `null`; `pointer` is `{ x, y }` in design pixels from the corner of that page, finite numbers held to ±1,000,000, or `null` when the pointer is not over the canvas or the tab is hidden; `selection` is at most 50 ids; `editing` is the id of the text box they are typing in, or `null`. An id is 1 to 64 characters. Any other field makes the message invalid (`checkPresence`); the server drops an invalid one without a word and the connection stays.
- **The server passes it on** to everybody else in the room (never back to the sender) as `{ t: "presence", peer, name, page, pointer, selection, editing }`, where `peer` is the number it gave the sender's connection when it joined. A browser cannot choose that number, and a message that names one is invalid, so nobody speaks for anybody else. The number is in the `welcome` (`peer`). A connection that asks for the design again keeps its number; a client that comes back on a new connection gets a new one. When a connection that ever said where it is closes or is replaced, the others are sent `{ t: "presence", peer, gone: true }`. The room keeps each person's last word in memory and sends it to whoever comes in later, right after their welcome.
- **A name the server fixes.** In a room bound to a team's design, a member joined with a session is heard under their account's name, whatever their browser says. Their `welcome` then carries that name (`name`), and the editor shows the person to themselves under it too ("Val Owner (you)"). A seat joined with a key gets no `name` and names itself. A browser cleans the name as it cleans any presence name; one of more than 40 units, or not text, makes the welcome invalid. A browser from before `name` ignores it.
- **There is no colour on the wire.** A person's colour is chosen by their number from a fixed list of twelve in the editor (`PRESENCE_COLORS`), so nothing that arrives is ever used as CSS. A name is put into the page as text.
- **Who may say what.** Everybody in the room, also somebody with the view key: a viewer's name and pointer are passed on, and their `selection` and `editing` are emptied by the server (a viewer selects nothing and types in nothing). Viewers hear the presence of everybody.
- **A browser reads it as strictly as everything else** (`parseServerMsg`, then `parsePresence`): a presence message with a field it does not have, a name that is too long, a pointer that is no place, more than 50 ids, or a `peer` that is not a count ends the session as `invalid`, like any other message that cannot be used. A hostile server can therefore put text of at most 40 characters and rectangles in one of twelve colours on the page, and nothing else: no markup, no address, no style.
- **How often.** The editor says where its person is at most every 80 ms (12 a second) and only when something changed, says at once when its person starts or stops typing in a text box, and repeats the last word every 3 seconds; somebody not heard of for 10 seconds is taken off the list (`PRESENCE_STALE_MS`). The server has an allowance for presence beside the one for messages (`presenceRate`: a burst of 30, then 15 a second for a connection). Within it a presence message does **not** count against `rate`, so a pointer that moves never uses up what a person may send in edits. Over it the message is dropped, the connection stays, the drop is counted (`presence_dropped_total`), and the message does count against `rate`: a connection that floods presence is closed with 1008 like any other that floods. Its bytes always count (`byteRate`); a presence message is at most a few kilobytes and usually about 150 bytes.
- **Old and new.** A server from before presence ignores the kind (it ignores every kind it does not know, and a test pins that) and sends no `peer` in its welcome, and a browser that was given no number says nothing about where it is. A browser from before presence ignores the kind too (`parseServerMsg` answers `null` for a kind it does not know) and takes no notice of `peer`. So either may be older than the other; the older side simply sees nobody.
- **The name.** Asked for in the Share panel ("Your name") and on the page of a link that asks before it joins, with "Guest" and the person's number as what the others see when it is left empty; kept in `localStorage` (`craftly.live.name`), cleaned when it is read back, and changed in the Share panel at any time.
- **For a screen reader** the pointers and outlines are hidden (`aria-hidden`): they move all the time. Who is here is a plain list in the top bar with the count in its name ("3 people here") and each person's name in it. It is not a live region. With reduced motion a pointer does not glide between two places.

**Comments (2026-11-14).** A comment is a note pinned to a place of a page, with a thread of replies. Unlike presence it is part of the design and is stored: `design.comments`, a list of `{ id, pageId, anchor, author: { name, colorIndex }, createdAt, editedAt?, text, resolved, replies }`, a reply `{ id, author, createdAt, editedAt?, text }`. The anchor is `{ x, y }` in design pixels from the corner of the page, or `{ x, y, elementId, dx, dy }` for a pin on an element at the top of the page, which then follows that element; `x`, `y` is where it was last known to be and where it stays when the element is gone (a browser of this version that deletes the element writes the element's last place into the pin in the same step; one from before comments cannot, and the pin then stays where it was put).

- **Operations, one comment or one reply each.** `comment.add { comment, index }`, `comment.set { id, set?: { text?, editedAt?, resolved?, anchor? }, unset?: ["editedAt"] }`, `comment.del { id }`, `reply.add { comment, reply, index }`, `reply.set { comment, id, set?: { text?, editedAt? }, unset?: ["editedAt"] }`, `reply.del { comment, id }`. `diffDesign` makes them from two versions of the design, after the operations of the pages (so a page that comes back is there before its comments), and `applyOps` replays them like the others: a comment whose id is there already, one on a page that is not there, one past 500, a reply past 200 or with an id its thread has, and a change of a comment or reply that is not there do nothing. Two people who comment at the same moment both keep their comment; a reply and a resolve made at the same moment both stay; two changes of the same text: the one the server applied last wins, as everywhere. `page.del` takes the comments of the page with it on every copy.
- **What may arrive.** Every comment operation is read field by field by `src/core/comments.ts`, the one check that a file, a backup, a room that is made and a welcome also go through (`checkDesign` asks it of `design.comments`): ids of comments and replies are `[A-Za-z0-9_-]{1,64}`, page and element ids 1 to 200 characters, times finite and not negative, places finite and within ±1,000,000 (refused beyond on the wire, held there in a file), a text of 1 to 2,000 UTF-16 units of plain text (no control characters but a tab and a line break, no line or paragraph separators, no marks that turn the direction of text around), an author's name of at most 40 such characters on one line, `colorIndex` a whole number from 0 to 11, at most 500 comments and 200 replies to one, no id twice, and **no field that a comment, a reply, an author, a pin or the operation does not have**. A text is put into the page as text and never as markup, and is used in no address and no CSS; an author's colour is the place of a colour in the fixed list of presence colours, never a colour from the wire. A server that sends text that looks like code is shown that text; one that sends a comment of 2,001 characters or an id that is not one ends the session (`invalid`).
- **Who understands comments: negotiated, as presence is with `peer`.** A browser from before comments takes a kind of operation it does not know for a server that cannot be trusted and ends its session, and the whole-design operation would lose comments made at the same moment, so the two ends say what they understand. A browser of this version says `features: ["comments"]` in its `join` (an optional field: a short list of short names; a join without it, or with it in another form, understands nothing more). A server of this version answers in its `welcome` with `features: ["comments"]` to such a browser, and with no `features` to any other (it names only what was asked for and what it supports). A browser sends comment operations only when its welcome said so, and takes none from a server that did not (`Session.sharesComments`).
- **An older browser in a room with newer ones.** The server passes comment operations on only to members whose join named the feature: an older member is sent each batch without them, as an empty batch when nothing else was in it, so its revision moves on in step and nothing it would refuse reaches it. Its welcome has the design without `comments`. That is not needed for it to accept the welcome: run against the build before this one, `parseServerMsg` and `Session` accept a welcome whose design has comments and `features` (`checkDesign` walks an unknown top-level field with the generic value check, and none of the names in a comment is one it treats specially; `withShared` of that build takes only the fields of `DESIGN_KEYS` and the pages), and it refuses a comment operation as `unknown operation comment.add`. The comments are left out of its welcome all the same, so that it never keeps a copy in its library that it can never bring up to date. Its own edits reach everybody as before; it cannot change or delete comments (its `diffDesign` does not see them).
- **A newer browser with an older server.** The welcome names no features, so comments are this person's own: they are made and kept in the local design (and saved with it, in project files and backups, as they are), none is sent (the operations are taken out of every batch, and a batch that was only comments is not sent at all; what was made while the connection was away is taken out at the welcome), the comments that such a server holds (from the design that made its room) are not shown, and what arrives never replaces this person's own (`withShared(local, shared, false)`). The Comments panel says "This server does not share comments. The comments you add stay in your copy of the design; the others do not see them." **When such a design is later shared on a server that does support comments**, its comments are in the design that makes the new room, like everything else in it, and are shared from then on.
- **Stored with the design.** A room's record holds the comments in its design, so they count against `maxDesignBytes` like everything else (a comment that would take the design past it is refused with "The server could not save this edit."). Undo: comments are **no steps of undo**, alone or in a shared design. In a shared design undo is made of this person's own steps as operations, and taking back a comment would take the replies of others with it, bringing one back would bring an old copy of them; so adding, answering, editing, resolving and deleting are told to the others and recorded nowhere, and undo of the steps around them leaves them as they are (`carryComments`; a page that comes back with an undo brings its comments back). Delete therefore asks first.
- **Who may comment.** Whoever may edit: a viewer's batch is refused as before, the panel says "This link only lets you look: you can read the comments, but not add or answer them", and offers no box to write in. Viewers see every comment. Edit and Delete are offered for one's own messages: the ids of what this person wrote are kept on this device (`craftly.comments.mine`, the latest 2,000), because there are no accounts and a name proves nothing; in a design that is not shared every message is one's own. The server does not check who wrote what: any editor may change or delete any comment by sending the operation, which the interface does not offer.
- **The name and the colour.** The author's name is the one given for working together ("Your name" in the Share panel, kept on this device), "Guest" with the number of the connection inside a shared design when none was given, and "You" outside one; the colour is that of the connection's presence in a shared design and one chosen by the name outside it.
- **Not drawn anywhere but in the editor.** Comments are no part of a page: PNG, JPG, PDF, SVG, GIF, WebM, the web page, the presenter, thumbnails and print draw pages, and a test pins that a page with comments exports as the same drawing. "Make a copy" keeps them, on the copies of their pages and elements; deleting a page deletes its comments.
- **The format.** `comments` is an optional field that older code ignores, so the design format version did not change (`docs/MIGRATIONS.md`: "an optional field is added"); it is listed as added in `persistedShapes.test.ts`, and the design with every field (`src/test/schema/complete.ts`) has one comment with a reply. A project file and a backup are read with `usableComments`: what is not usable is left out and counted, and the import says so ("2 comments in the file could not be read and were left out.").

**When two people change the same thing.** Different properties of one element: both changes stay. The same property: the batch the server applied last wins, the same for everybody. A deleted element stays deleted whatever else was done to it. That would leave one case in which last-writer-wins loses work that a person can see being lost: **text typed into one text box by two people**, which is one value (`paragraphs`), so that every key one of them pressed would replace what the other had typed. Since 2026-11-28 that text is merged instead, letter by letter (next).

**Two people typing in one text box** (`src/collab/text.ts`, `el.text` in `ops.ts`).

- **A text is a line of positions.** Each paragraph is a mark (one position, carrying its alignment and list) followed by its characters, in UTF-16 units (`flatText`). A change to the characters is one splice of that line: from `at`, take `del` positions away and put `ins` there, a list of pieces (paragraph marks and runs of styled characters). `diffDesign(prev, next, { text: true })` makes it from two versions of a text (`textSplice`: what is the same at the start and at the end is kept, never between the two halves of a character outside the basic plane), as `{ k: "el.text", page, id, base, at, del, ins }`, where `base` is the plain line of the text the change was made on. The other properties of the element still go in an `el.set` beside it.
- **The server moves it onto the text as it is.** When the text has changed since `base` (somebody else's letters were applied first), the two plain lines are compared (Myers' algorithm on what lies between their common start and end, `editScript`), and `at` and `at + del` are found in the text as it is now (`rebase`): the start goes after what others put in at the same place, the end before it. So where both type in the same place, the one the server applied first comes first; letters typed next to a deletion stay; what one person deletes goes, also letters the other typed inside it at that moment. A comparison that would find more than 1,000 differences or look at more than 4,000,000 characters settles for one replaced stretch between the common ends, and the work counts towards the batch's (`MAX_BATCH_WORK`), so a text of a million characters that has nothing in common with its `base` takes milliseconds and a batch of many such splices is refused.
- **Everybody ends with the same text.** The server applies the splice and passes on the text it made as an `el.set` of the paragraphs, which every browser understands, so no browser has to merge what it is told. A browser shows the server's text with its own unconfirmed splices moved onto it the same way (`Session.design`), which is what the server will make of them.
- **The open box takes in the others' letters** (`TextEditorOverlay.tsx`). When the text of the box changes in the store while it is open, the box is built again from it, with the caret and the selection behind the same letters as before. Letters this person typed that the box had not passed on yet are made on the new text the way the server makes them (`mergeText`). While a word is being composed with an input method nothing is built again; the letters join it when it is done. A panel that changes the text while the box is open is taken in the same way (before, the next key put the old text back).
- **Undo takes back only this person's letters.** In a shared design undo and redo are this person's own steps as operations; a step of typing is a splice, so undoing it on a text that others have typed in since takes away this person's letters and leaves theirs.
- **Who is told.** "Name is typing…" still shows on a box that somebody types in, but it no longer keeps the box closed: double-click it and type.
- **A browser from before this.** A browser says in its join that it merges text (`features: ["text"]`), and a server that does says so in its welcome; only then are splices sent. To a server that does not, the paragraphs are set whole as before, and a splice made before the welcome is turned into the paragraphs it leaves (`plainText`). A browser from before this sets the paragraphs whole and would take the other's letters away with each key, so **where one of the two people in a box has such a browser, one person at a time types in it**, as before: the server passes on the second person as typing in nothing, and tells a second person whose browser merges in words (`{ t: "taken", id, peer }`, a kind of message that a browser from before does not know and ignores): their box closes and they read "Name is typing in this text with an older version of Craftly…". A browser from before that is second hears that the first types there and closes its own box, as it always did.
- **The lock is advisory and lives in presence only.** Nothing of it is in the design or in a room's record, and the server refuses no edit for it. It ends when the person closes the box, leaves, loses the connection, or is not heard of for 10 seconds (a browser that types repeats itself every 3; a tab that has been in the background for minutes may be slowed down by the browser enough to lose a box that way). So it cannot get stuck.
- **Two people who open the same box in the same moment**, before either has heard of the other: both say so, and the server decides by the order in which it heard them. `Room.present` passes the first one on as typing there, and passes on (and remembers) every later one as somebody who types in nothing, for as long as the first holds the box. So everybody, the two included, hears of exactly one person typing there. The first never hears of the second's attempt and types on. The second hears that the first types in the box it has open itself, which can only mean that the other was first: its editor closes the box and says why ("Ana started typing in this text a moment before you, so it was closed here. One person at a time types in a text box."). What the second had typed until then was sent edit by edit, so at that moment it is the last write and is in the text; the first person's next key replaces the text with what their box holds, which is the honest limit of this design: the loss is the keys of one person in the moment of the race, and that person is told. A box that the second person had emptied is not removed when it closes this way (closing an empty text box normally removes it).
- **Not covered:** the data of a table and of a chart is edited in a side panel by another mechanism and is not merged: two people who change cells of one table at once still overwrite each other (`cells` is one value). A style given to a stretch of text (bold, a colour) is a splice that puts those characters back styled: letters the other typed inside that stretch at that moment are lost. A change in two places of a text at once (none of the editor's own, but a panel could make one) is one splice over everything between them.

**Replay and recovery.** The browser shows the server's confirmed revision with its own queued edits applied on top. It stores unconfirmed batches and their client sequence in session storage so they can replay after a reconnect or reload in the same tab. Closing that tab, clearing storage or exhausting its quota can interrupt replay. If the server rejects a batch, the editor explains why and keeps the local draft as a separate recovery copy, with a download fallback if local storage cannot write the copy.

**Why this and not a CRDT.** The editor's data are plain JSON with ids, edits are property-level, and the collaboration mode uses a self-hosted server: a server-authoritative total order with per-property last-writer-wins is far simpler than Yjs or Automerge, needs no change of the model, and is the design of the Driftboard project that this one was ported from (`PLAN-DIAGRAMS-AND-COLLABORATION.md`). Its price: a value that two people change at once is one value, so one wins. The one place where that loses what a person can see being lost, text typed into one box, has its own merge on top (see "Two people typing in one text box"): a splice with the text it was made on, moved by the server onto the text as it is, which needs no change of the model because the server's order decides and everybody is sent the result. And a concurrent deletion and addition of the same id can leave an empty group behind. Both are conflicts that every copy resolves the same way.

## The server

Run it (Node 22 or newer; the one dependency is `ws`):

```bash
npm run server                       # builds dist-server/live.mjs with esbuild, then runs it
PORT=8787 HOST=127.0.0.1 DATA_DIR=live-data ALLOW_ORIGIN=http://127.0.0.1:5173 node dist-server/live.mjs
```

Settings (environment): `PORT` (8787), `HOST` (127.0.0.1; `0.0.0.0` to be reachable from other machines, then put TLS in front of it: browsers need `wss://` from an `https://` page, and the server, which speaks plain HTTP and WebSocket, prints a warning at its start whenever `HOST` is not an address of the machine itself, `listenWarning` in `src/server/listenWarning.ts`), `DATA_DIR` (live-data), `ALLOW_ORIGIN` (the origin of the editor, a comma separated list, or `*`; none by default, which omits cross-origin response headers), `MAX_ROOMS` (1000), `MAX_PEERS_PER_ROOM` (50), `SHUTDOWN_TIMEOUT_MS` (10000: told to stop with SIGINT or SIGTERM, the server waits for the saves and requests that are at work and closes every connection, but no longer than this; it then leaves with exit code 1 and a line in the log, as it does when closing fails, and a second signal ends it at once. Nothing acknowledged is lost by that: an edit is saved before it is acknowledged). In code (`createLiveServer`): `maxMessageBytes` (4 MiB per WebSocket message; more closes the connection with 1009), `maxDesignBytes` (16 MiB for the room’s design, checked on creation and before an edit is committed), `idleCloseMs` (a room with nobody in it leaves memory after 60 s and is loaded again by the next visitor), `joinWaitMs` (a connection has ten seconds to show its key in its first message, then it is sent away with `bad-request`), `rate` (a burst of 200 messages, then 100 a second per connection; more closes the connection with 1008).

**What one visitor may cost (admission control).** Each of these is an option of `createLiveServer` with a default, and a setting of the environment that `main.ts` reads; what is not set keeps the default.

| Environment | Option | Default | What it does |
| --- | --- | --- | --- |
| `MAX_CONNECTIONS` | `maxConnections` | 5000 | The most WebSocket connections at one time, to all rooms together. Beyond it the upgrade is answered with `503` and never becomes a connection; a browser tries again by itself. |
| `MAX_WAITING_PER_ROOM` | `maxWaitingPerRoom` | 20 | The most connections to one room that have not shown their key yet. The next is closed with 1013 ("try again later"), not with `denied`, which a browser takes as final. |
| `MAX_QUEUED_BATCHES`, `MAX_QUEUED_BYTES` | `maxQueuedBatches`, `maxQueuedBytes` | 1000, 64 MiB | The most edits, and bytes of them, that wait in one room for their write. One more closes its connection with 1013: the browser comes back and sends again what was not acknowledged. |
| `MAX_GROUP` | `maxGroup` | 100 | Group commit: edits that arrive while a room's write runs wait in its inbox, and the next write saves up to this many at once (`Room.receiveOps`). They are applied in order, each checked against what the ones before it leave, and answered and passed on only after that write, each with the revision it would have had alone. When the write fails the room is as it was and every edit of the group is refused. |
| `MAX_BUFFERED_BYTES` | `maxBufferedBytes` | twice `maxDesignBytes` (32 MiB) | The most that may wait in memory to be sent to one connection. A connection that reads slower than that is dropped at once (the browser sees 1006, comes back, and is sent the design as it is then). Keep it above the size of one design, or nobody can be welcomed. |
| `MAX_UNJOINED_MESSAGE_BYTES` | `maxUnjoinedMessageBytes` | 8 KiB | The most a message may be before the connection has shown its key. A bigger one is not parsed and closes the connection with 1009. A join is about a hundred bytes. |
| `BYTE_BURST`, `BYTES_PER_SECOND` | `byteRate` | 8 MiB, then 1 MiB a second | Bytes a connection may send, counted beside its messages (`rate`); more closes the connection with 1008. |
| `JOIN_BURST`, `JOIN_EVERY_MS` | `joinRate` (`burst`, `perSecond`) | 4, then one every 2000 ms | How often one connection may send `join`. Every join is answered with the whole design, so a connection that keeps asking is closed with 1008. |
| `PRESENCE_BURST`, `PRESENCE_PER_SECOND` | `presenceRate` | 30, then 15 a second | How often one connection may say where its person is (`presence`). What is more is dropped and counted, and the connection stays; see "Seeing each other" for how this stands beside `rate`. |

**Who may ask, and how often an address may make a room.** Also options of `createLiveServer` that `main.ts` reads from the environment.

| Environment | Option | Default | What it does |
| --- | --- | --- | --- |
| `ALLOW_ORIGIN` | `allowOrigin` | none | With a list of origins, the server refuses the WebSocket upgrade and every `POST`, `PUT` and `DELETE` that names an `Origin` which is not on the list, with `403`. The CORS headers alone never did that: they stop a page from reading an answer, not from sending the request (making a room needs no preflight, because its body has no content type that would ask for one), and a WebSocket is not subject to CORS. A request with no `Origin` header (curl, another server) is not refused by this, so it keeps the pages of other sites out and nobody else. With `*`, or with nothing set, no origin is asked for, as before. |
| `ROOM_CREATE_PER_HOUR` | `roomCreatePerHour` | 10 | How many rooms one address may make in any hour; 0 for no limit. Every `POST /api/rooms` counts, also one that is then refused for another reason. Beyond it the answer is `429` with `Retry-After` (seconds), given before the body is read. An IPv6 address is counted by its first half (its /64), because one visitor is given all the addresses of one. What is remembered is at most an hour old (`src/server/address.ts`). |
| `ROOM_CREATE_KEY` | `roomCreateKey` | none (anybody may make rooms) | A secret that whoever starts to share must show, in the header `x-craftly-create-key` of `POST /api/rooms`. Without it the answer is `401 { error, code: "create-key-needed" }`, with a wrong one `403 { error, code: "create-key-wrong" }`; the body is not read for either. It is compared in constant time, never taken from the address and never written to the log, and the preflight answer names the header for the origins that are allowed. Every attempt counts towards `ROOM_CREATE_PER_HOUR`, which is what limits guessing (so do not set that to 0 on a server with a key). It is one secret for everybody the operator lets share, not an account: it cannot be taken back from one person without changing it for all. Joining, editing and stopping a room never ask for it. `main.ts` refuses a key of fewer than 8 characters, or with spaces or characters outside printable ASCII. |
| `ADMIN_KEY` | `adminKey` | none (no operator interface) | The operator's key. Only with it does anything answer under `/api/admin/` (see "The operator's interface" below); without it those addresses are `404` like any other that does not exist. `main.ts` refuses a key of fewer than 16 characters, or with spaces or characters outside printable ASCII. In code, `wrongKeysPerHour` (10) is how many wrong keys one address may show in an hour before it is not listened to at all. |
| `METRICS_KEY` | `metricsKey` | none (no metrics) | The key of whatever collects the server's numbers. Only with it does `GET /metrics` answer (see "Metrics" below); without it the address is `404`. Shown as `Authorization: Bearer <key>`. `main.ts` refuses a key of fewer than 16 characters, or with spaces or characters outside printable ASCII. |
| `TRUST_PROXY` | `trustProxy` | off | Set it to `1` when exactly one reverse proxy stands in front of the server and the server can be reached through it alone. The address of a visitor is then the **last** entry of `X-Forwarded-For`, the one that proxy added; entries before it were sent by the visitor and are not believed, so two proxies in a row are not supported (the second would be counted as the visitor). A header that is missing or does not end in an address counts as the proxy's own address. When it is off the header is never read, and behind a proxy every visitor then shares the proxy's address and its ten rooms an hour. |

**Rooms that nobody uses (expiry, off by default).** `ROOM_TTL_DAYS` (option `roomTtlMs`, in milliseconds; not set or 0: never) is how long a room may go unused before the server removes it. A room is used when it is saved (an edit, an image) and when somebody joins it, also with the key that only looks. "Last used" is the time of the room's file, so the sweep (`sweepEveryMs` in code: once when the server starts to listen, then every hour) asks the storage for a list with times (`LiveStorage.list`) and reads no room that has not expired. A join sets the time of the file (`LiveStorage.touch`, which does not read or write the room) at most once a day for a room in memory, or every quarter of the time rooms live when that is less than four days; it does so whether or not expiry is on, so that turning it on later finds true times. A room with a connection or a request at it is never removed: when the sweep finds such a room past its time, it notes it as used now. Removing is what "stop sharing" does (through the room's queue: whoever is at the door at that moment is sent away with `not-found`, close 4004). A room that cannot be read or removed is written to the log and left, and tried again in the next round. For a public server set it (30 days, say): without it `MAX_ROOMS` rooms that nobody uses fill the server for good. Nobody loses a design to it, because every person who opened a shared design keeps a copy in their own library; the link stops working.

**What a save writes.** An accepted edit is saved before it is acknowledged, and a save writes the record of the room whole: the design, the revision, the batch numbers and the hashes of the keys. The images of the room are not part of that any more. Each is a file of its own (`FileStorage`: `<room>.assets/<SHA-256 of the image's id>.json`, written whole and renamed into place like a room; the name is a hash because ids may differ only in capitals or be a name a file may not have), written once when it is uploaded and not again; an upload does not write the design either. Before, every edit wrote and flushed every image of the room again, up to 48 MiB of them. A record that an older server wrote, with the images inside it (`RoomRecord.assets`), is still read: its images are served from the record, and the first save of such a room (an edit or an upload) writes each image to its own file and then the record without them. If that stops halfway the record still holds them and the next save does it again. Removing a room (stop sharing, expiry) removes its folder of images. The design is turned into text once for a save: the text that is measured against `maxDesignBytes` is the text that is written (`LiveStorage.save` takes it as a third argument). The limit for the images of one room (`maxRoomAssetBytes` in code, 48 MiB) counts what they take in the storage, which is the base64 text and about thirty bytes around each. **Not done:** every edit still writes the whole design (up to 16 MiB) with a flush of its own; edits that arrive while a save runs are not yet saved together, and the queue of a room has no limit of its own beyond what each connection may send (HANDOFF, stage 1, item 6, third and fourth part).

Applying a batch no longer walks the whole design for every element it adds: `applyOps` counts the ids of the design once for a batch and keeps the count right as the batch adds and deletes (`src/collab/ops.ts`).

**Clips and sounds.** A shared design carries its clips and its sounds (`Design.audio`) as well as its pictures (2026-11-27). They do not travel like pictures, as base64 inside JSON: a clip may be a hundred megabytes. `PUT /api/rooms/:id/media/:assetId` takes the file as it is, with its type in `Content-Type` (`MEDIA_TYPE` in `src/server/http.ts`: `video/mp4`, `video/webm`, `video/ogg`, and `audio/mpeg`, `mp4`, `aac`, `wav`, `ogg`, `webm`, `flac`; anything else is `415`) and its size in `Content-Length` (none is `411`). The size is weighed before a byte is read: more than `maxMediaBytes` (`MAX_MEDIA_MB`, 100 MiB) or more than the room may still hold (`maxRoomMediaBytes`, `MAX_ROOM_MEDIA_MB`, 500 MiB) is `413` with the limit in the answer, and the connection is dropped. The bytes are then streamed to a temporary file in the room's folder of clips (`FileStorage`: `<room>.media/`), counted and hashed as they come; one that is longer than it said is refused, and only a file that came whole is put in place (`<SHA-256 of the id>.bin`, then `<…>.json` with its type, size and SHA-256), in the room's queue, after the room's allowance is weighed again. The same id again with the same bytes is `200`; with other bytes `409`. `GET` and `HEAD` give it back under its type, with `Content-Disposition: attachment` and `X-Content-Type-Options: nosniff`, streamed from the file. The keys and sessions are those of the pictures (an edit key to put, either key to get). Removing a room removes its folder of clips. The operator's list of rooms has `mediaBytes` beside `imageBytes`.

In the editor (`src/editor/live/media.ts`) a clip never holds up an edit: the edit that adds it goes at once, and the clip is sent beside it in the background, one at a time (`sendClips`, after each edit of one's own and when the connection becomes live, by whoever may edit). The others see the clip's element as an empty box until the file has come: whoever lacks a clip or a sound of the design asks the room for it (`fetchClips`, on every change of the shared design), and asks again every five seconds for up to ten minutes while it is not there yet. A file that came is checked as an upload is (`prepareAssetFromFile`: a clip or a sound that this browser plays), kept under its id, and the posters, players and sound shapes that had found nothing are told. A clip the room refuses (too large, the room full) stays on the device that added it, and the person is told once, in words that say the others see an empty box. The sounds themselves travel as a design property: `audio` is one of `DESIGN_KEYS` (`src/collab/ops.ts`), set whole, and checked like a project file's (`readAudioTracks`); a browser from before it leaves it alone. A room bound to a team's design (accounts) checks the members' sessions on this route with the same code as on the pictures' route (`e2e/accounts.cjs` adds a clip in such a room and the other member gets it). When such a room writes its design back to the team's space, it brings the pictures, clips and sounds the design uses that the space has not got, so a member who was not in the room gets them by sync; one the space refuses (full, too large) stays the room's and is counted in `write_back_files_refused_total` (docs/ACCOUNTS.md). A team's own sync (the account server's spaces) carries them too, by a route of its own (docs/ACCOUNTS.md, "Clips and sounds").

**Interface.** `POST /api/rooms` with `{ "design": <Design> }` returns `201 { room, editKey, viewKey, ownerKey }`; the keys are shown once, the server keeps only their SHA-256 (a copy of `live-data` cannot be used to edit or to look). The design is accepted when it could be added to an empty one by `checkOps` (so the content checks apply to it) and has a title and a size; its library fields are replaced (the room's id is its id). `DELETE /api/rooms/:id` with the owner key in `x-craftly-key` sends everybody away (`denied`, then close 4004) and forgets the room. `GET /api/health` checks that room storage is writable. It returns `503` when storage is unavailable. The check writes a file, so its answer is kept for five seconds (`healthCacheMs` in code) and given to everybody who asks meanwhile. A room whose file is there and cannot be read (the disk fails, or the file is damaged) is not reported as missing: a connection is sent `denied` with the reason `server-error`, which the editor shows as a problem of the server and not as a design that is gone, an HTTP request is answered `500` (the browser asks again later for an image, where it takes `404` as final), and the error is written to the log (`console.error`) with the id of the room. The file is left as it is; it still counts towards `MAX_ROOMS` until the operator mends or removes it. The room image endpoint accepts authenticated reads and editor uploads, with per-image and per-room limits. A room stays in memory for as long as a request for one of its images is at work (the body of an upload may take minutes), and an upload is saved only into the room that is in memory then: one that was stopped meanwhile answers `404`. The WebSocket is `/ws?room=<id>`, and **the key is not in the address**, which every server and proxy that it passes writes in a log: the first message is `{ t: "join", client, key }`. `denied` with a reason (`not-found`, `no-access`, `server-full`, `bad-request`, `server-error`) and close 4003 when the room is not there, the room is there and cannot be read (`server-error`), the key is missing or wrong (the edit key gives `edit`, the view key `view`; a key that is no text, or is longer than 200 characters, allows nothing), the room is full, the client name is not `[A-Za-z0-9._-]{1,64}`, or no join comes within `joinWaitMs` (`bad-request`); then the messages of `protocol.ts`. What is said before the join is ignored and not answered, not even a ping. A connection that has not shown its key belongs to the room only so that the room stays in memory for it and is closed with it when sharing stops; it does not count against `MAX_PEERS_PER_ROOM`, and gets its place with the join. A client that joins again under the same name on another connection replaces the old one (closed with 4000). A room id is 16 random bytes in base64url; a link with a room and a key is a capability, so treat it as a secret.

**A member of a team joins without a key (with `ACCOUNTS=1`; [ACCOUNTS.md](ACCOUNTS.md#as-built-step-14-server)).** A team's design is opened live with `POST /api/spaces/<team>/designs/<id>/live` and the person's session as `Authorization: Bearer <token>`, which answers `{ room, ws: "/ws?room=<room>", role }`. That room is **bound** to the design (`RoomRecord.bound`): made from the design's current revision when it is not in memory, with an id derived from the team and the design, and key hashes of random keys that nobody was ever given. The browser connects to `ws` on the same server and its first message is `{ t: "join", client, session: <token>, features? }`: the token in the message, never in the address, like a key. The server looks up the session and the person's role in the team at that moment: owner and editor get `edit`, viewer `view`, anybody else (and a session that is expired, ended, malformed or of a disabled account) `denied no-access` and close 4003, as a wrong key does. A join has a `key` or a `session`, never both (`joinCredential` in `protocol.ts`); a join without `session` is what it always was, so browsers from before accounts are unaffected. A bound room takes no key at all, and a room of a link takes no session. From the welcome on, everything is the protocol above. While the room is in memory the team's space refuses to write that design (`409 live`); when the room leaves memory (`idleCloseMs` after the last person left) or the server stops, its design is written back to the space as the next revision, comments included, and the room is removed (when that fails, the room keeps its copy on the disk and tries again the next time). Removing a member, lowering an editor to viewer, deleting the team, disabling the account or ending the person's sessions sends their sockets in the team's bound rooms `denied no-access` with close 4003; one who may still look joins again as a viewer. The room's pictures take the session as a bearer token too.

**The operator's interface (off unless `ADMIN_KEY` is set).** Two calls, both with the key in the header `x-craftly-admin-key`, for a terminal and never for a page. `GET /api/admin/rooms?limit=<n>&after=<id>` answers `{ rooms, total, next }`: the rooms in the order of their ids, 100 to a page unless `limit` says otherwise and never more than 500; `next` is the id to give as `after` for the page that follows, or `null`. A room is `{ id, title, createdAt, usedAt, designBytes, imageBytes, people }`: the times in milliseconds (`usedAt` is the time of the room's file, as for expiry), `designBytes` the design as JSON, `imageBytes` what its images take in the storage, `people` the connections that have shown a key and are in it now. A room that cannot be read is listed as `{ id, usedAt, people, error }` and written to the log. Each room of a page is read for this, so a page of big rooms is work. No key is listed (the server has none) and no hash of one. `DELETE /api/admin/rooms/<id>` removes a room through the same function and the same queue as "stop sharing" and expiry (`forget`): whoever is in it or at its door is sent `denied` with `not-found` and closed with 4004, and its images go with it; `404` when there is no such room. A room that cannot be read is removed too, straight from the storage, which nothing else can do. Who may: a request that names an `Origin` is refused with `403` whatever the origin and whatever `ALLOW_ORIGIN` says, and nothing under `/api/admin/` is ever answered with a CORS header, so a page can neither act nor read. The key is compared in constant time, taken from its header only, and never logged. An address that shows ten wrong keys within an hour (`wrongKeysPerHour`) is answered `429` with `Retry-After` until the oldest is an hour old, **also for the right key**: otherwise only the failed guesses would be slowed down. A right key is not counted. Behind a proxy without `TRUST_PROXY` all callers share the proxy's address and so this allowance; the script below is meant to ask the server directly. `scripts/rooms.mjs` (`npm run server:rooms -- list`, `-- delete <id>`) is these two calls with a table around them; [`DEPLOY.md`](DEPLOY.md) section 2.7 says how to use it.

**Metrics (off unless `METRICS_KEY` is set).** `GET /metrics` answers in the text format of Prometheus (`text/plain; version=0.0.4`), written by hand in `src/server/metrics.ts`; no package. The rule for who may read it is the simplest one that is safe behind a proxy: a key, and nothing without it. "Only from this machine" was the other candidate and was not chosen, because behind a reverse proxy every request comes from this machine. The key is shown as a bearer token, which every scraper can be told to send; it goes through the same guard as the operator's interface (constant-time compare, `403` for any request with an `Origin`, never a CORS header, ten wrong keys an hour for an address and then `429` also for the right one; the count is shared with `ADMIN_KEY` guesses), and it is a different key from `ADMIN_KEY`, so a scraper cannot remove rooms. All names start with `craftly_live_`. Gauges, read when asked: `uptime_seconds` (of the process), `rooms_in_memory`, `rooms_stored` (the storage is asked at most once in `healthCacheMs`, five seconds; when it cannot say, the last number is given, and none if there never was one), `connections`, `peers_joined` (connections that have shown a key), `bound_rooms_in_memory` (rooms bound to a team's design). Counters since the start: `bound_rooms_made_total`, `session_joins_total`, `session_joins_refused_total`, `write_backs_total` and `write_back_failures_total` (bound rooms, see "A member of a team joins without a key"), `messages_received_total` and `bytes_received_total` (WebSocket, every message that arrives), `batches_applied_total`, `batches_rejected_total` (refused for any reason: its form, a viewer's, one that could not be saved), `saves_total`, `save_failures_total` (records of rooms written, room creation included; images are not counted), `save_duration_seconds_sum` and `_count` (every write of a record, failed ones too), `rooms_created_total`, `rooms_removed_total` (by an owner or the operator), `rooms_expired_total`, `presence_dropped_total` (presence messages that were not passed on because a connection sent them faster than it may), `connections_closed_total{reason=...}` with the reasons `slow_reader`, `rate` (messages or bytes), `join_rate`, `size` (a message too big, before or after the key), `silent` (no answer to pings), `waiting` (too many at the door of a room), `queue` (too many edits waiting in a room) and `revoked` (a session in a bound room that no longer lets its person in, or lets them only look), `upgrades_refused_total{reason="connections"|"origin"}`, and `http_responses_total{class="2xx"|"3xx"|"4xx"|"5xx"}` (the scrapes themselves included). A label takes its value from a list fixed in the code and never from outside: no room id, address or path is ever a label, because such series grow without end and a room id is half of a secret. Every series is there from the start at 0. The numbers are counted whether or not anybody may read them (a handful of additions). Not there: a histogram of save times (sum and count give the mean), anything per room, memory and CPU of the process (ask the system or the container), and counts of image uploads.

**The key in the editor.** The Share panel does not know beforehand whether a server wants a key. The first attempt goes without one; when the answer has the code `create-key-needed`, a field appears ("Key to start sharing", a password field, with the sentence "This server asks for a key to start sharing. Whoever runs it can give it to you.") and the person tries again. A wrong key is said in the field ("That key is not right. Check it with whoever runs the server."). The key is **not remembered**: it lives in the panel while the panel is open, and is asked for again the next time a design is shared. That was chosen over a "remember on this device" box because the only place a page can keep it is `localStorage`, as plain text that every script of the page and every person at the browser can read, and the key is the operator's secret and not the person's own; a password manager may offer to keep it. Changing the server address takes the field and what was typed away, so a key is never shown to another server. The key is not part of the link, of the design or of a project file (`CreateKeyError` and `shareDesign` in `src/editor/live/connection.ts`, `LiveSection.tsx`).

**Not done here (see "Hardening" below):** accounts for rooms of links (accounts, with `ACCOUNTS=1`, give teams rooms of their own, see above; who may create a room of a link is everybody who can reach `POST /api/rooms`, or, with `ROOM_CREATE_KEY`, everybody who has that one key; up to `MAX_ROOMS` and `ROOM_CREATE_PER_HOUR` for an address), logs, a Dockerfile (it is not written, and not tested), SQLite instead of one file per room, TLS (use a reverse proxy).

Rooms created before the owner key was introduced require operator cleanup or recreation. Existing edit and view links retain their room permissions. A room credential is omitted when exporting or importing a portable project or backup.

## Rules for changing this code

- A change to `ops.ts` or `protocol.ts` is a change of the wire format: keep old and new browsers talking, or bump a protocol version (not there yet) and refuse the old.
- A new field on an element needs nothing here (properties are generic, and `diffDesign` and `applyOp` replay a mode that is set or taken away: `blend` is the example); a new **kind of container** (something that holds elements, as a group does) needs `diffElements` and `edit` in `ops.ts` to learn about it, plus the checks in `protocol.ts`. A new property that holds an address needs its name in `ADDRESS_KEYS` of `protocol.ts`, or it is not checked; a new property that holds markup, or text that is put into markup or handed to a canvas as it is (as `svg`, `colors` and `blend` are), needs the same care in `checkValue`. A graphic that needs an element or an attribute that `svgSafety.ts` does not allow means a line on its list, the reason, and a test in `svgSafety.test.ts` (and the content test will tell if something that ships is refused).
- Keep `applyOp` total: never throw, return the same object when nothing changes.
- Every change to this code is checked by `ops.store.test.ts` (real actions), `content.test.ts` (everything the app ships) and `sync.sim.test.ts` (bad weather); add a step to the first when the editor gets a new action that touches the design in a new way.
