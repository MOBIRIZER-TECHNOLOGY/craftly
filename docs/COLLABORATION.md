# Live editing: the core and the server (built 2026-11-09), and what is left

Several people editing one design at the same time is the headline feature of [`INVESTOR-READINESS.md`](INVESTOR-READINESS.md) (milestone M2) and Phase C of [`PLAN-DIAGRAMS-AND-COLLABORATION.md`](PLAN-DIAGRAMS-AND-COLLABORATION.md). This document describes what exists, why it is built the way it is, how it is checked, how to run the server, and what is still to build. **Without a server nothing changes for people who use Craftly:** the static, serverless editor is as it was, and a design that is not shared never touches this code. What exists: the pure core (`src/collab/`), the connection a browser uses (`src/collab/live.ts`), a server (`src/server/`), the store's part (a shared design has its own undo and takes in what others did), and the interface (the Share panel, a status mark in the top bar, the link page), checked together over real sockets and in three real browsers.

## The model, in one page

**What is shared.** The title, type, size, unit and guides of the design (`DESIGN_KEYS`), its pages and their elements, groups included. The id, the dates, the folder, the star and the trash of a design belong to each person's own library and are never sent (`withShared` lays the shared parts over a person's own record).

**Operations are id-addressed and property-level.** `el.set` carries the new value of every property that changed (and the names of those removed), so two people who change different properties of one element both keep their change; for the same property the batch the server applied last wins. `el.add` / `el.del` / `el.move` and `page.add` / `page.del` / `page.move` / `page.set` / `design` complete the set. Nested values (a fill, the paragraphs of a text, a table's cells) are replaced as a whole.

**`diffDesign(prev, next)`** follows the objects that did not change by reference (the store's structural sharing), compares the rest property by property (`jsonEqual`, so a new object with the same content sends nothing) and emits deletions first, then property changes, then moves, then additions, so that an id is never twice in the design while a batch is replayed (an element that goes into a new group is a deletion at the top and an addition inside the group, in that order). An id that changes its kind is a deletion and an addition. Moves are as few as it takes (not a rewrite of the list); additions come in the order of their final index.

**`applyOps(design, ops)`** is deterministic, pure, shares what it did not change, and never throws on what it cannot place: an operation for a missing element is ignored, an id that is already in use (or that appears twice in what is added) is not added again (so the same batch twice does no harm and a duplicate id cannot get in), an index out of range is clamped, the last page is never deleted, a group cannot be moved into itself or into a group that is not there, `id` / `type` / `children` of an element and `id` / `elements` of a page cannot be set, and `__proto__`, `constructor` and `prototype` are never set.

**What may arrive (`checkOps`).** Every operation must have its proper form (kinds, ids of 1 to 200 characters, finite indexes, objects where objects belong, at most 10,000 operations per batch, at most 200 properties per `set`, groups at most 32 deep), and every value in it is walked: at most 32 levels deep, texts at most 1,000,000 characters, lists at most 100,000 long, objects at most 2,000 keys, numbers finite, no property called `__proto__`, `constructor` or `prototype`, at most 300,000 values in one batch; an address (`src`, `originalSrc`, `link`, `href`, `url`) must start with `asset:`, `builtin:`, `https://`, `http://`, `mailto:`, `tel:`, `#`, `/`, `blob:` or be a `data:image/…` (so never `javascript:` or a page); the markup of a graphic (`svg`) must be plain drawing by `svgProblem` (below); and the colours a graphic is recoloured with (`colors`) must be written plainly (`isPlainColor`: `#hex`, `rgb()` or `rgba()` with numbers, `black`, `white`, `transparent`), because `recolorSvg` puts them into the markup as they are. Every template page and every graphic of the app passes (`content.test.ts`); that test is what found that pictures also use `builtin:`.

**Markup is plain drawing or it is refused (`svgProblem`).** The first version of this check was a pattern for what to keep out (`<script`, `on…=`, `javascript:`), and a pattern can be walked around: a browser reads `<svg/onload=…>` as an event handler and an attribute without quotes as one too, and a character reference can spell `javascript:`. It is now a list of what is allowed, read with a tokenizer of its own as strictly as XML is read (no DOM, so the server runs it too): the elements are shapes, paints, masks and filter primitives (`svg g defs symbol path rect circle ellipse line polyline polygon linearGradient radialGradient stop clipPath mask pattern marker title desc filter` and the `fe…` primitives that draw); the attributes have plain names and quoted values, none starts with `on`, there is no `style` and no `xml:base`, `xmlns` can only be the drawing's own and `xlink`; `href` can only point to `#something` and any `url(…)` can only refer to `#something`; a character reference can only be one of the five that XML names; there is no comment, declaration, instruction, CDATA, script, link, style sheet, picture or animation; tags nest and close, one drawing, at most 100 deep, 100 attributes to an element. Everything it lets through is the same thing to an XML parser and to the HTML parser of a browser, which is what makes it safe to draw, to put into a page and to write into an exported file; `svgSafety.dom.test.ts` has the parsers of the test browser read 4,000 damaged drawings and requires that whatever is accepted comes out of both as nothing but drawing. What the app ships (288 graphics, templates, QR codes, icons) uses 14 elements and about 40 attributes, all on the list; a graphic that needs something more means a line on the list and a test.

**What a browser believes (`parseServerMsg`, `checkDesign`).** A link names the server and anybody can make a link, so the browser does not take for granted what comes back. Every message is read by `parseServerMsg` before any of it is used: its kind, the form of every field (counts are whole numbers, a role is `edit` or `view`), and its content. A `welcome` carries a whole design, which must pass `checkDesign`: a title, a size, at least one page, elements that are elements, and every value in it walked like the values of a batch, but without the limit of what one batch may carry (a design that many batches have built up can hold more than one) and with a deeper allowance (pages and groups inside groups). The `ops` of a message must pass `checkOps`, the same check the server applied when it took them in. A message of a kind that this version does not know is ignored, because a newer server may send more. The first message that cannot be used ends the session: nothing of it is applied, the design that is shown stays as it was, the connection is closed and not tried again, and the status is `denied` with the reason `invalid`, which the Share panel and the page of a link say in words ("The server sent something that Craftly does not accept ..."). Nothing that a browser had made while it was away is sent to a server that has shown what it is.

**The server decides the order.** `Room.receive` applies each batch from a person who may edit, bumps the revision, answers the sender with `ack` and sends the same operations to everyone else as `ops`. Every copy therefore applies the same batches in the same order from the same start and ends the same. A batch carries a number from its sender; a number the server has seen is acknowledged and not applied again (`lastSeq` per client name, saved with the room). A batch that `checkOps` refuses is answered with `rejected`; a viewer's batch is always refused.

**The browser replays, it does not merge.** `Session` keeps `server` (the design as the server has it, at `rev`), `queue` (its own batches the server has not confirmed, numbered) and `design` = `server` with `queue` replayed on top. A change of someone else arrives, `server` moves on, and the queue is replayed on the new `server`: the person's own work stays on screen and lands on top of the news. A refused batch leaves the queue and its effect disappears from the screen. A confirmation joins the batch to `server` (what is shown does not change). A message that is not the next revision, or an answer that does not add up, makes the session ask for the design again (`join`), and what the server sends then (`welcome`: the design, the revision, and the last number of this client that it applied) replaces `server`; the batches after that number are sent again, in order. A lost connection loses nothing: the queue is kept, and the same happens when the connection comes back (`Live` does the waiting).

**Why this and not a CRDT.** The editor's data are plain JSON with ids, edits are property-level, and a server is acceptable for the collaboration mode (an owner decision, still open): a server-authoritative total order with per-property last-writer-wins is far simpler than Yjs or Automerge, needs no change of the model, and is the design of the Driftboard project that this one was ported from (`PLAN-DIAGRAMS-AND-COLLABORATION.md`). Its price: text typed into the same text box by two people at once is one value, so one wins (the plan calls for an "X is editing" lock), and a concurrent deletion and addition of the same id can leave an empty group behind. Both are conflicts that every copy resolves the same way.

## The server

Run it (Node 22 or newer; the one dependency is `ws`):

```bash
npm run server                       # builds dist-server/live.mjs with esbuild, then runs it
PORT=8787 HOST=127.0.0.1 DATA_DIR=live-data ALLOW_ORIGIN=http://127.0.0.1:5173 node dist-server/live.mjs
```

Settings (environment): `PORT` (8787), `HOST` (127.0.0.1; `0.0.0.0` to be reachable from other machines, then put TLS in front of it: browsers need `wss://` from an `https://` page), `DATA_DIR` (live-data), `ALLOW_ORIGIN` (the origin of the editor, a comma separated list, or `*`; none by default, which refuses cross-origin calls), `MAX_ROOMS` (1000), `MAX_PEERS_PER_ROOM` (50). In code (`createLiveServer`): `maxMessageBytes` (4 MiB per WebSocket message; more closes the connection with 1009), `maxDesignBytes` (16 MiB for the design that makes a room), `saveDelayMs` (a room is saved 300 ms after a change, and when it empties and when the server stops), `idleCloseMs` (a room with nobody in it leaves memory after 60 s and is loaded again by the next visitor), `rate` (a burst of 200 messages, then 100 a second per connection; more closes the connection with 1008).

**Interface.** `POST /api/rooms` with `{ "design": <Design> }` returns `201 { room, editKey, viewKey }`; the keys are shown once, the server keeps only their SHA-256 (a copy of `live-data` cannot be used to edit or to look). The design is accepted when it could be added to an empty one by `checkOps` (so the content checks apply to it) and has a title and a size; its library fields are replaced (the room's id is its id). `DELETE /api/rooms/:id` with the edit key in `x-craftly-key` sends everybody away (`denied`, then close 4004) and forgets the room. `GET /api/health` answers `{ ok, rooms }`. The WebSocket is `/ws?room=<id>&key=<key>`: `denied` with a reason (`not-found`, `no-access`, `server-full`, `bad-request`) and close 4003 when the room is not there, the key is wrong (the edit key gives `edit`, the view key `view`), the room is full or the client name is not `[A-Za-z0-9._-]{1,64}`; then the messages of `protocol.ts`, starting with `{ t: "join", client }` (what is said before it is ignored). A client that joins again under the same name on another connection replaces the old one (closed with 4000). A room id is 16 random bytes in base64url; a link with a room and a key is a capability, so treat it as a secret.

**Not done here (see "Hardening" below):** accounts and who may create rooms (anyone who can reach `POST /api/rooms` can, up to `MAX_ROOMS`), a cap on the size a design may grow to after creation, per-address limits, logs and metrics, a Dockerfile (it is not written, and not tested), SQLite instead of one file per room, TLS (use a reverse proxy).

## How it is checked

- `ops.test.ts` (31 tests): every kind of operation, what is sent and what is not, the order of the operations, replaying on a copy that has changed, hostile input (ids already in use, `__proto__`, an element moved into a group that is not there).
- `ops.store.test.ts` (3): **the real editor** (`useEditor` actions: add, move, resize, delete, duplicate, group, ungroup, reorder, align, flip, connect, copy, cut, paste, pages, title, resize design, undo, redo, 27 kinds of step) runs 40 random sequences of 60 steps; for every step the operations of the change, sent through JSON, replayed on the design before give the design after, and the operations the other way give the design before. It also pins that moving one element is one small operation, and that the lines attached to a shape travel in the same batch as the shape.
- `protocol.test.ts` (134) and `content.test.ts` (4): the form of every operation that is accepted, a table of what is refused (shape, sizes, depth, counts), the content rules (accepted and refused addresses, markup and recolourings, limits), `checkDesign` (a design as the editor makes it, groups 32 deep, a design with more in it than one batch may carry, 23 kinds of refusal) and `parseServerMsg` (every kind of message, only what a message is made of, a kind that is not known, 25 kinds of refusal), and **every template page, every graphic of the app, every graphic recoloured the way the editor does it and a QR code passes**, both as operations and as one design that arrives whole.
- `sync.test.ts` (27): a room and browsers wired by hand: a change shows at once and is confirmed after the round trip, different properties of one element both survive, the same property goes to the batch the server applied last, a deleted element stays deleted, a refused batch disappears from the screen, a viewer's change is not even sent and is refused when forced, a lost connection loses nothing and nothing is applied twice, a message that went missing makes the browser ask again, answers that are not in order are not trusted, a client that comes back replaces its old connection.
- `sync.sim.test.ts` (3): **bad weather.** 150 seeded runs of 2 to 4 browsers (plus 40 of one and 20 of six) editing at random while messages are delivered in random interleavings, connections drop (everything in flight is lost), come back, and the server restarts from what it saved. After every step: what each browser shows equals what it has confirmed with its own batches on top, and what it has confirmed equals the server's design at that revision. At the end everyone is connected, everything is delivered, and every browser shows exactly the server's design with nothing unconfirmed. The totals are asserted so a quiet run cannot pass (about 4,900 edits, 1,000 dropped connections, 100 server restarts, 1,700 batches sent again).
- `live.test.ts` (12): the browser's connection with a made-up socket and made-up time: joining, sending, the waits (500 ms doubling to 10 s, exactly, back to the start after a welcome), pings, giving up on a silent connection after 45 s, being turned away, being stopped.
- `src/server/live.test.ts` (28): **the real server on a port of its own with real WebSockets and `Live` as the client:** making a room (hashes only, a different room each time, refusals of bad bodies, bad content, too big a design, too many rooms, CORS), getting in (edit key, view key, wrong key, missing room, a room id that is a path, a client name that cannot be one, a full room, messages before joining), two browsers editing through it in both directions and the server's saved copy, a viewer who can look and not touch (also when something that is not the page tries), a client that comes back on a new connection, a room that survives a restart (revision and batch numbers included) and one that leaves memory and comes back, stopping to share, a message that is too big, too many messages, a batch that is refused while the next is accepted. A room id that is a path and a store that fails to read turn a visitor away without bringing the server down. The suite was run three times in a row to check it is not flaky.
- `src/core/storeLive.test.ts` (30): the store in a shared design: what it tells the connection (every change as the design before and after, after the design is set, not what is not for the others), what other people did (shown without a step of undo or an echo, library fields kept, selection and open page kept as far as they exist, lines aimed again), and **undo and redo that take back only the person's own steps** whatever the others did meanwhile (coalesced edits and gestures are one step, a step that others made moot is used up, redo of a joined step restores all of it, the history is as long as the editor's and ends when sharing stops or another design opens).
- `src/editor/live/connection.test.ts` (19): **the real store, the browser's connection and the real server on a real port, with another person on a connection of their own:** starting to share, what arrives and what is sent, per-person undo through the wire, a server that goes away and comes back (what was changed meanwhile reaches the other), a key that only looks, a refusal, stopping, leaving, joining, the wait for a server that never answers. `links.test.ts` (21), `LiveSection.test.tsx` (18), `JoinPage.test.tsx` (7), `EditorLive.test.tsx` (4) and a route test in `App.test.tsx`: the addresses and the link, the Share section and the mark in the top bar, the page of a link, the editor connecting a shared design for as long as it is open.
- `hostile.test.ts` (25): **a server that cannot be trusted.** A welcome that carries code (markup that runs after a slash, a script, a picture that is code, `__proto__`, something that is not a design, a title that is not text) ends the session and none of it is used; so do operations that carry code (the good operations of the same batch are not applied either, `__proto__` reaches nothing), messages of the wrong form and a reason to be turned away that nobody has; a kind of message that a newer server may send is ignored; a session that has ended is not brought back by a good welcome that comes after a bad message, nor after being turned away (a closing socket still delivers what was on its way); the connection is closed for good, says why, shows nothing and is not tried again; an honest server is believed. `connection.test.ts` has the same with the real store: a link that leads to a server that sends code is not joined, and the open design stays as it was.

## What is left (in order)

1. **Offline edits across a reload.** What a person changes while the page is open and the connection is lost is kept and sent when it is back (and works for a design that is opened while the server is down). What was changed in an earlier page load and never sent is not merged: the connection starts from the server's design. Needs the unconfirmed batches saved with the design (Driftboard's `unsynced`), and a decision about a design that was edited offline for days.
2. **Presence**: cursors, selections, who is here, follow a person, "X is editing this text" (a lock), comments.
3. **Pictures**: images are blobs in each browser's IndexedDB (`asset:<id>`); a shared design needs an asset endpoint, upload at insert, fetch on demand into the local store, and garbage collection. Until then a shared design shows a missing picture to everyone but the browser that added it.
4. **Hardening**: `checkDesign` when the server makes a room (it runs `checkOps` on the design as operations today, which looks at the shared fields only, so a room can hold a design that browsers refuse), a confirmation before joining a design from a server this person has not used before, a check of the markup of graphics when a project file is opened or a backup is restored (the exporter cleans it when it writes a file), a cap on the size a room's design may grow to, who may create rooms, per-address limits, the fuzz test on `checkOps`, a load test (200 clients in one room, a 5,000-element design: the plan's exit criteria; today a design of more than about 5,000 elements cannot be shared because one batch may carry 300,000 values), a threat model in `SECURITY.md`, a privacy policy, a Dockerfile, the end date of links.
5. **Smaller improvements**: batch compaction while offline (merge the `el.set` of one element), a catch-up by revision instead of a whole design on every reconnect, an empty group removed when its last child goes, an index that survives other people's concurrent insertions (z-order after concurrent adds is approximate today), a protocol version in `join`.

## Rules for changing this code

- A change to `ops.ts` or `protocol.ts` is a change of the wire format: keep old and new browsers talking, or bump a protocol version (not there yet) and refuse the old.
- A new field on an element needs nothing here (properties are generic); a new **kind of container** (something that holds elements, as a group does) needs `diffElements` and `edit` in `ops.ts` to learn about it, plus the checks in `protocol.ts`. A new property that holds an address needs its name in `ADDRESS_KEYS` of `protocol.ts`, or it is not checked; a new property that holds markup, or text that is put into markup as it is (as `svg` and `colors` are), needs the same care in `checkValue`. A graphic that needs an element or an attribute that `svgSafety.ts` does not allow means a line on its list, the reason, and a test in `svgSafety.test.ts` (and the content test will tell if something that ships is refused).
- Keep `applyOp` total: never throw, return the same object when nothing changes.
- Every change to this code is checked by `ops.store.test.ts` (real actions), `content.test.ts` (everything the app ships) and `sync.sim.test.ts` (bad weather); add a step to the first when the editor gets a new action that touches the design in a new way.
