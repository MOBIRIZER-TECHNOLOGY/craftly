# Live editing: the core and the server (built 2026-11-09), and what is left

Several people editing one design at the same time is the headline feature of [`INVESTOR-READINESS.md`](INVESTOR-READINESS.md) (milestone M2) and Phase C of [`PLAN-DIAGRAMS-AND-COLLABORATION.md`](PLAN-DIAGRAMS-AND-COLLABORATION.md). This document describes what exists, why it is built the way it is, how it is checked, how to run the server, and what is still to build. **Without a server nothing changes for people who use Craftly:** the static, serverless editor is as it was, and a design that is not shared never touches this code. What exists: the pure core (`src/collab/`), the connection a browser uses (`src/collab/live.ts`), a server (`src/server/`), the store's part (a shared design has its own undo and takes in what others did), and the interface (the Share panel, a status mark in the top bar, the link page), checked together over real sockets and in three real browsers.

## The model, in one page

**What is shared.** The title, type, size, unit and guides of the design (`DESIGN_KEYS`), its pages and their elements, groups included. The id, the dates, the folder, the star and the trash of a design belong to each person's own library and are never sent (`withShared` lays the shared parts over a person's own record).

**Operations are id-addressed and property-level.** `el.set` carries the new value of every property that changed (and the names of those removed), so two people who change different properties of one element both keep their change; for the same property the batch the server applied last wins. `el.add` / `el.del` / `el.move` and `page.add` / `page.del` / `page.move` / `page.set` / `design` complete the set. Nested values (a fill, the paragraphs of a text, a table's cells) are replaced as a whole.

**`diffDesign(prev, next)`** follows the objects that did not change by reference (the store's structural sharing), compares the rest property by property (`jsonEqual`, so a new object with the same content sends nothing) and emits deletions first, then property changes, then moves, then additions, so that an id is never twice in the design while a batch is replayed (an element that goes into a new group is a deletion at the top and an addition inside the group, in that order). An id that changes its kind is a deletion and an addition. Moves are as few as it takes (not a rewrite of the list); additions come in the order of their final index.

**`applyOps(design, ops)`** is deterministic, pure, shares what it did not change, and never throws on what it cannot place: an operation for a missing element is ignored, an id that is already in use (or that appears twice in what is added) is not added again (so the same batch twice does no harm and a duplicate id cannot get in), an index out of range is clamped, the last page is never deleted, a group cannot be moved into itself or into a group that is not there, `id` / `type` / `children` of an element and `id` / `elements` of a page cannot be set, and `__proto__`, `constructor` and `prototype` are never set.

**What may arrive (`checkOps`).** Every operation must have its proper form (kinds, ids of 1 to 200 characters, finite indexes, objects where objects belong, at most 10,000 operations per batch, at most 200 properties per `set`, groups at most 32 deep), and every value in it is walked: at most 32 levels deep, texts at most 1,000,000 characters, lists at most 100,000 long, objects at most 2,000 keys, numbers finite, no property called `__proto__`, `constructor` or `prototype`, at most 300,000 values in one batch; an address (`src`, `originalSrc`, `link`, `href`, `url`) must start with `asset:`, `builtin:`, `https://`, `http://`, `mailto:`, `tel:`, `#`, `/`, `blob:` or be a `data:image/…` (so never `javascript:` or a page); the markup of a graphic (`svg`) must be plain drawing by `svgProblem` (below); and the colours a graphic is recoloured with (`colors`) must be written plainly (`isPlainColor`: `#hex`, `rgb()` or `rgba()` with numbers, `black`, `white`, `transparent`), because `recolorSvg` puts them into the markup as they are; and a property called `blend` must be one of the fifteen blend modes of `src/core/blend.ts` (`isBlendMode`) or nothing (`null` or left out), because the name goes to a canvas and into the `style` of an exported SVG as it is (`"normal"` is refused too: Normal is the absence of the property, and the editor sends the removal as `unset: ["blend"]`). Every template page and every graphic of the app passes (`content.test.ts`); that test is what found that pictures also use `builtin:`.

**Markup is plain drawing or it is refused (`svgProblem`).** The first version of this check was a pattern for what to keep out (`<script`, `on…=`, `javascript:`), and a pattern can be walked around: a browser reads `<svg/onload=…>` as an event handler and an attribute without quotes as one too, and a character reference can spell `javascript:`. It is now a list of what is allowed, read with a tokenizer of its own as strictly as XML is read (no DOM, so the server runs it too): the elements are shapes, paints, masks and filter primitives (`svg g defs symbol path rect circle ellipse line polyline polygon linearGradient radialGradient stop clipPath mask pattern marker title desc filter` and the `fe…` primitives that draw); the attributes have plain names and quoted values, none starts with `on`, there is no `style` and no `xml:base`, `xmlns` can only be the drawing's own and `xlink`; `href` can only point to `#something` and any `url(…)` can only refer to `#something`; a character reference can only be one of the five that XML names; there is no comment, declaration, instruction, CDATA, script, link, style sheet, picture or animation; tags nest and close, one drawing, at most 100 deep, 100 attributes to an element. Everything it lets through is the same thing to an XML parser and to the HTML parser of a browser, which is what makes it safe to draw, to put into a page and to write into an exported file; `svgSafety.dom.test.ts` has the parsers of the test browser read 4,000 damaged drawings and requires that whatever is accepted comes out of both as nothing but drawing. What the app ships (288 graphics, templates, QR codes, icons) uses 14 elements and about 40 attributes, all on the list; a graphic that needs something more means a line on the list and a test.

**An element is checked as strictly as one of a file (`elementProblem`, `checkSets`).** The checks above look at the form of an operation and at the content of its values, and until 2026-11-14 an element that arrived whole needed only an id, a kind and, for a group, its children: an editor could add a shape with `x: "a"` or set `paragraphs: 5` on a text for everybody in the room, and the renderer throws on that for all of them. The file importer always asked more (`isUsableElement`). Both now ask the same, from one table (`REQUIRED_PROPERTIES` in `src/core/usableElement.ts`, which `projectFormat.ts` hands on and the server bundles; it imports only the markup check): the place and size of every element (`x`, `y`, `width`, `height`, `rotation`, `opacity`) are finite numbers, and each kind has what it cannot be drawn without (a text its `paragraphs` as a list, `fontFamily`, `fontSize`, `fontWeight`, `lineHeight` and `effect`; a shape its `shape`; a line a `stroke` with a `width`; a picture `crop`, `filter`, `mask` and a `src` that is text or null; a graphic `svg` that is plain drawing, `viewW`, `viewH` and `colors`; a table `cells`, `colWidths`, `rowHeights` and `fontFamily`; a chart `labels`, `series` and a `palette` that is not empty). A property that is not in the table passes as before. This holds for every element that arrives whole: `el.add`, the elements of `page.add` (groups walked to the bottom), a design that makes a room, and a design that is a welcome. A change of properties (`el.set`) cannot be judged from the operation, which names an element by id and not by kind (`stroke: null` is fine for a shape and fatal for a line). So the server applies the batch to a copy first, which is safe whatever it holds, and then asks the same question of every element the batch set or unset a property of, as the whole batch leaves it (`checkSets`); a batch that leaves one unusable is `rejected` as a whole, with the name of the property, and nothing of it is saved or passed on. A browser asks the same of the operations a server sends, and ends the session (`invalid`) with a server that sends such a thing. An element that was not usable before a batch is not held against that batch: a room made before this check may hold one, and refusing every later change to it would not mend it. **Such a room cannot be joined by a browser with this check, though**: its welcome is refused as `invalid`. Nothing the editor itself makes is affected: a test puts one element of each kind from the factory, the design that has every field (`src/test/schema/complete.ts`) and every template of the catalogue through the check. What is not checked: the properties of a page (a page without a background can still be added), and what is inside the lists and objects the table names (a run of a paragraph, a cell of a table).

**What a browser believes (`parseServerMsg`, `checkDesign`).** A link names the server and anybody can make a link, so the browser does not take for granted what comes back. Every message is read by `parseServerMsg` before any of it is used: its kind, the form of every field (counts are whole numbers, a role is `edit` or `view`), and its content. A `welcome` carries a whole design, which must pass `checkDesign`: a title, a size, at least one page, elements that are elements, and every value in it walked like the values of a batch, but without the limit of what one batch may carry (a design that many batches have built up can hold more than one) and with a deeper allowance (pages and groups inside groups). The `ops` of a message must pass `checkOps`, the same check the server applied when it took them in. A message of a kind that this version does not know is ignored, because a newer server may send more. The first message that cannot be used ends the session: nothing of it is applied, the design that is shown stays as it was, the connection is closed and not tried again, and the status is `denied` with the reason `invalid`, which the Share panel and the page of a link say in words ("The server sent something that Craftly does not accept ..."). Nothing that a browser had made while it was away is sent to a server that has shown what it is.

**The server decides the order.** `Room.receive` checks each batch from a person who may edit, persists the new revision, answers the sender with `ack` and sends the same operations to everyone else as `ops`. Every copy therefore applies the same batches in the same order from the same start and ends the same. A batch carries a number from its sender; a number the server has seen is acknowledged and not applied again (`lastSeq` per client name, saved with the room; see below for how long). A batch that `checkOps` or `checkSets` refuses is answered with `rejected`; a viewer's batch is always refused.

**What a room remembers of its clients, and how it forgets (`seqs`, `seqSeen`, `seqFloor`).** The last number per client grew by one entry for every page load that ever edited a room, was never pruned, and is written with every save. It is bounded now (`src/collab/room.ts`): a client that is not in the room and was last seen (joined, or had a batch applied) more than 30 days ago is forgotten when the next batch is applied, and above 1,000 clients those seen longest ago go first. A client that is in the room is never forgotten. Forgetting must not let a batch count twice: a forgotten client may come back and send again a batch that was applied but whose `ack` it never heard, and a room with no entry for it would take the batch for new. So the room keeps one number more, the **floor**: the highest last number of any client it ever forgot (`seqFloor` in the record; `seqSeen` holds the times). A client the room has no entry for is treated as one whose last applied batch was the floor: its welcome says `lastSeq: floor`, and a batch of its numbered at or below the floor is acknowledged and not applied. Everything a forgotten client had applied is numbered at or below its own last number, which is at or below the floor; the floor never goes down and is saved by the same write that drops the entry. So no batch of a forgotten client is ever applied a second time, also after a restart. The price: a batch that a forgotten client had sent and that was **not** applied before it stayed away for a month is dropped as well, because the room cannot tell the two apart. A client the room has never seen pays nothing, with a browser of this version: the session keeps the highest number it ever handed to a connection (`sent`, kept for a reload with the rest), and at a welcome it gives up only batches at or below `lastSeq` that were sent; batches that never left the browser (made before the first welcome, or waiting when the tab went on under a new name after close code 4000) get the numbers after `lastSeq`. **A browser with older code in a room that has forgotten somebody** drops what it made before its first welcome, without a word, when those batches are numbered at or below the floor; the service worker keeps an old editor around for a while, so this can happen until it has updated. A record from an older server has no times: its clients count as seen when the room is opened. If the server stops in the moment between the save that forgets a client and that client's next batch, a client that had come back during that save is welcomed with the floor after the restart, like any forgotten one.

**Replay and recovery.** The browser shows the server's confirmed revision with its own queued edits applied on top. It stores unconfirmed batches and their client sequence in session storage so they can replay after a reconnect or reload in the same tab. Closing that tab, clearing storage or exhausting its quota can interrupt replay. If the server rejects a batch, the editor explains why and keeps the local draft as a separate recovery copy, with a download fallback if local storage cannot write the copy.

**Why this and not a CRDT.** The editor's data are plain JSON with ids, edits are property-level, and the collaboration mode uses a self-hosted server: a server-authoritative total order with per-property last-writer-wins is far simpler than Yjs or Automerge, needs no change of the model, and is the design of the Driftboard project that this one was ported from (`PLAN-DIAGRAMS-AND-COLLABORATION.md`). Its price: text typed into the same text box by two people at once is one value, so one wins (the plan calls for an "X is editing" lock), and a concurrent deletion and addition of the same id can leave an empty group behind. Both are conflicts that every copy resolves the same way.

## The server

Run it (Node 22 or newer; the one dependency is `ws`):

```bash
npm run server                       # builds dist-server/live.mjs with esbuild, then runs it
PORT=8787 HOST=127.0.0.1 DATA_DIR=live-data ALLOW_ORIGIN=http://127.0.0.1:5173 node dist-server/live.mjs
```

Settings (environment): `PORT` (8787), `HOST` (127.0.0.1; `0.0.0.0` to be reachable from other machines, then put TLS in front of it: browsers need `wss://` from an `https://` page, and the server, which speaks plain HTTP and WebSocket, prints a warning at its start whenever `HOST` is not an address of the machine itself, `listenWarning` in `src/server/listenWarning.ts`), `DATA_DIR` (live-data), `ALLOW_ORIGIN` (the origin of the editor, a comma separated list, or `*`; none by default, which omits cross-origin response headers), `MAX_ROOMS` (1000), `MAX_PEERS_PER_ROOM` (50), `SHUTDOWN_TIMEOUT_MS` (10000: told to stop with SIGINT or SIGTERM, the server waits for the saves and requests that are at work and closes every connection, but no longer than this; it then leaves with exit code 1 and a line in the log, as it does when closing fails, and a second signal ends it at once. Nothing acknowledged is lost by that: an edit is saved before it is acknowledged). In code (`createLiveServer`): `maxMessageBytes` (4 MiB per WebSocket message; more closes the connection with 1009), `maxDesignBytes` (16 MiB for the room’s design, checked on creation and before an edit is committed), `idleCloseMs` (a room with nobody in it leaves memory after 60 s and is loaded again by the next visitor), `joinWaitMs` (a connection has ten seconds to show its key in its first message, then it is sent away with `bad-request`), `rate` (a burst of 200 messages, then 100 a second per connection; more closes the connection with 1008).

**What one visitor may cost (admission control).** Each of these is an option of `createLiveServer` with a default, and a setting of the environment that `main.ts` reads; what is not set keeps the default.

| Environment | Option | Default | What it does |
| --- | --- | --- | --- |
| `MAX_CONNECTIONS` | `maxConnections` | 5000 | The most WebSocket connections at one time, to all rooms together. Beyond it the upgrade is answered with `503` and never becomes a connection; a browser tries again by itself. |
| `MAX_WAITING_PER_ROOM` | `maxWaitingPerRoom` | 20 | The most connections to one room that have not shown their key yet. The next is closed with 1013 ("try again later"), not with `denied`, which a browser takes as final. |
| `MAX_BUFFERED_BYTES` | `maxBufferedBytes` | twice `maxDesignBytes` (32 MiB) | The most that may wait in memory to be sent to one connection. A connection that reads slower than that is dropped at once (the browser sees 1006, comes back, and is sent the design as it is then). Keep it above the size of one design, or nobody can be welcomed. |
| `MAX_UNJOINED_MESSAGE_BYTES` | `maxUnjoinedMessageBytes` | 8 KiB | The most a message may be before the connection has shown its key. A bigger one is not parsed and closes the connection with 1009. A join is about a hundred bytes. |
| `BYTE_BURST`, `BYTES_PER_SECOND` | `byteRate` | 8 MiB, then 1 MiB a second | Bytes a connection may send, counted beside its messages (`rate`); more closes the connection with 1008. |
| `JOIN_BURST`, `JOIN_EVERY_MS` | `joinRate` (`burst`, `perSecond`) | 4, then one every 2000 ms | How often one connection may send `join`. Every join is answered with the whole design, so a connection that keeps asking is closed with 1008. |

**Who may ask, and how often an address may make a room.** Also options of `createLiveServer` that `main.ts` reads from the environment.

| Environment | Option | Default | What it does |
| --- | --- | --- | --- |
| `ALLOW_ORIGIN` | `allowOrigin` | none | With a list of origins, the server refuses the WebSocket upgrade and every `POST`, `PUT` and `DELETE` that names an `Origin` which is not on the list, with `403`. The CORS headers alone never did that: they stop a page from reading an answer, not from sending the request (making a room needs no preflight, because its body has no content type that would ask for one), and a WebSocket is not subject to CORS. A request with no `Origin` header (curl, another server) is not refused by this, so it keeps the pages of other sites out and nobody else. With `*`, or with nothing set, no origin is asked for, as before. |
| `ROOM_CREATE_PER_HOUR` | `roomCreatePerHour` | 10 | How many rooms one address may make in any hour; 0 for no limit. Every `POST /api/rooms` counts, also one that is then refused for another reason. Beyond it the answer is `429` with `Retry-After` (seconds), given before the body is read. An IPv6 address is counted by its first half (its /64), because one visitor is given all the addresses of one. What is remembered is at most an hour old (`src/server/address.ts`). |
| `ROOM_CREATE_KEY` | `roomCreateKey` | none (anybody may make rooms) | A secret that whoever starts to share must show, in the header `x-craftly-create-key` of `POST /api/rooms`. Without it the answer is `401 { error, code: "create-key-needed" }`, with a wrong one `403 { error, code: "create-key-wrong" }`; the body is not read for either. It is compared in constant time, never taken from the address and never written to the log, and the preflight answer names the header for the origins that are allowed. Every attempt counts towards `ROOM_CREATE_PER_HOUR`, which is what limits guessing (so do not set that to 0 on a server with a key). It is one secret for everybody the operator lets share, not an account: it cannot be taken back from one person without changing it for all. Joining, editing and stopping a room never ask for it. `main.ts` refuses a key of fewer than 8 characters, or with spaces or characters outside printable ASCII. |
| `ADMIN_KEY` | `adminKey` | none (no operator interface) | The operator's key. Only with it does anything answer under `/api/admin/` (see "The operator's interface" below); without it those addresses are `404` like any other that does not exist. `main.ts` refuses a key of fewer than 16 characters, or with spaces or characters outside printable ASCII. In code, `wrongKeysPerHour` (10) is how many wrong keys one address may show in an hour before it is not listened to at all. |
| `TRUST_PROXY` | `trustProxy` | off | Set it to `1` when exactly one reverse proxy stands in front of the server and the server can be reached through it alone. The address of a visitor is then the **last** entry of `X-Forwarded-For`, the one that proxy added; entries before it were sent by the visitor and are not believed, so two proxies in a row are not supported (the second would be counted as the visitor). A header that is missing or does not end in an address counts as the proxy's own address. When it is off the header is never read, and behind a proxy every visitor then shares the proxy's address and its ten rooms an hour. |

**Rooms that nobody uses (expiry, off by default).** `ROOM_TTL_DAYS` (option `roomTtlMs`, in milliseconds; not set or 0: never) is how long a room may go unused before the server removes it. A room is used when it is saved (an edit, an image) and when somebody joins it, also with the key that only looks. "Last used" is the time of the room's file, so the sweep (`sweepEveryMs` in code: once when the server starts to listen, then every hour) asks the storage for a list with times (`LiveStorage.list`) and reads no room that has not expired. A join sets the time of the file (`LiveStorage.touch`, which does not read or write the room) at most once a day for a room in memory, or every quarter of the time rooms live when that is less than four days; it does so whether or not expiry is on, so that turning it on later finds true times. A room with a connection or a request at it is never removed: when the sweep finds such a room past its time, it notes it as used now. Removing is what "stop sharing" does (through the room's queue: whoever is at the door at that moment is sent away with `not-found`, close 4004). A room that cannot be read or removed is written to the log and left, and tried again in the next round. For a public server set it (30 days, say): without it `MAX_ROOMS` rooms that nobody uses fill the server for good. Nobody loses a design to it, because every person who opened a shared design keeps a copy in their own library; the link stops working.

**What a save writes.** An accepted edit is saved before it is acknowledged, and a save writes the record of the room whole: the design, the revision, the batch numbers and the hashes of the keys. The images of the room are not part of that any more. Each is a file of its own (`FileStorage`: `<room>.assets/<SHA-256 of the image's id>.json`, written whole and renamed into place like a room; the name is a hash because ids may differ only in capitals or be a name a file may not have), written once when it is uploaded and not again; an upload does not write the design either. Before, every edit wrote and flushed every image of the room again, up to 48 MiB of them. A record that an older server wrote, with the images inside it (`RoomRecord.assets`), is still read: its images are served from the record, and the first save of such a room (an edit or an upload) writes each image to its own file and then the record without them. If that stops halfway the record still holds them and the next save does it again. Removing a room (stop sharing, expiry) removes its folder of images. The design is turned into text once for a save: the text that is measured against `maxDesignBytes` is the text that is written (`LiveStorage.save` takes it as a third argument). The limit for the images of one room (`maxRoomAssetBytes` in code, 48 MiB) counts what they take in the storage, which is the base64 text and about thirty bytes around each. **Not done:** every edit still writes the whole design (up to 16 MiB) with a flush of its own; edits that arrive while a save runs are not yet saved together, and the queue of a room has no limit of its own beyond what each connection may send (HANDOFF, stage 1, item 6, third and fourth part).

Applying a batch no longer walks the whole design for every element it adds: `applyOps` counts the ids of the design once for a batch and keeps the count right as the batch adds and deletes (`src/collab/ops.ts`).

**Interface.** `POST /api/rooms` with `{ "design": <Design> }` returns `201 { room, editKey, viewKey, ownerKey }`; the keys are shown once, the server keeps only their SHA-256 (a copy of `live-data` cannot be used to edit or to look). The design is accepted when it could be added to an empty one by `checkOps` (so the content checks apply to it) and has a title and a size; its library fields are replaced (the room's id is its id). `DELETE /api/rooms/:id` with the owner key in `x-craftly-key` sends everybody away (`denied`, then close 4004) and forgets the room. `GET /api/health` checks that room storage is writable. It returns `503` when storage is unavailable. The check writes a file, so its answer is kept for five seconds (`healthCacheMs` in code) and given to everybody who asks meanwhile. A room whose file is there and cannot be read (the disk fails, or the file is damaged) is not reported as missing: a connection is sent `denied` with the reason `server-error`, which the editor shows as a problem of the server and not as a design that is gone, an HTTP request is answered `500` (the browser asks again later for an image, where it takes `404` as final), and the error is written to the log (`console.error`) with the id of the room. The file is left as it is; it still counts towards `MAX_ROOMS` until the operator mends or removes it. The room image endpoint accepts authenticated reads and editor uploads, with per-image and per-room limits. A room stays in memory for as long as a request for one of its images is at work (the body of an upload may take minutes), and an upload is saved only into the room that is in memory then: one that was stopped meanwhile answers `404`. The WebSocket is `/ws?room=<id>`, and **the key is not in the address**, which every server and proxy that it passes writes in a log: the first message is `{ t: "join", client, key }`. `denied` with a reason (`not-found`, `no-access`, `server-full`, `bad-request`, `server-error`) and close 4003 when the room is not there, the room is there and cannot be read (`server-error`), the key is missing or wrong (the edit key gives `edit`, the view key `view`; a key that is no text, or is longer than 200 characters, allows nothing), the room is full, the client name is not `[A-Za-z0-9._-]{1,64}`, or no join comes within `joinWaitMs` (`bad-request`); then the messages of `protocol.ts`. What is said before the join is ignored and not answered, not even a ping. A connection that has not shown its key belongs to the room only so that the room stays in memory for it and is closed with it when sharing stops; it does not count against `MAX_PEERS_PER_ROOM`, and gets its place with the join. A client that joins again under the same name on another connection replaces the old one (closed with 4000). A room id is 16 random bytes in base64url; a link with a room and a key is a capability, so treat it as a secret.

**The operator's interface (off unless `ADMIN_KEY` is set).** Two calls, both with the key in the header `x-craftly-admin-key`, for a terminal and never for a page. `GET /api/admin/rooms?limit=<n>&after=<id>` answers `{ rooms, total, next }`: the rooms in the order of their ids, 100 to a page unless `limit` says otherwise and never more than 500; `next` is the id to give as `after` for the page that follows, or `null`. A room is `{ id, title, createdAt, usedAt, designBytes, imageBytes, people }`: the times in milliseconds (`usedAt` is the time of the room's file, as for expiry), `designBytes` the design as JSON, `imageBytes` what its images take in the storage, `people` the connections that have shown a key and are in it now. A room that cannot be read is listed as `{ id, usedAt, people, error }` and written to the log. Each room of a page is read for this, so a page of big rooms is work. No key is listed (the server has none) and no hash of one. `DELETE /api/admin/rooms/<id>` removes a room through the same function and the same queue as "stop sharing" and expiry (`forget`): whoever is in it or at its door is sent `denied` with `not-found` and closed with 4004, and its images go with it; `404` when there is no such room. A room that cannot be read is removed too, straight from the storage, which nothing else can do. Who may: a request that names an `Origin` is refused with `403` whatever the origin and whatever `ALLOW_ORIGIN` says, and nothing under `/api/admin/` is ever answered with a CORS header, so a page can neither act nor read. The key is compared in constant time, taken from its header only, and never logged. An address that shows ten wrong keys within an hour (`wrongKeysPerHour`) is answered `429` with `Retry-After` until the oldest is an hour old, **also for the right key**: otherwise only the failed guesses would be slowed down. A right key is not counted. Behind a proxy without `TRUST_PROXY` all callers share the proxy's address and so this allowance; the script below is meant to ask the server directly. `scripts/rooms.mjs` (`npm run server:rooms -- list`, `-- delete <id>`) is these two calls with a table around them; [`DEPLOY.md`](DEPLOY.md) section 2.7 says how to use it.

**The key in the editor.** The Share panel does not know beforehand whether a server wants a key. The first attempt goes without one; when the answer has the code `create-key-needed`, a field appears ("Key to start sharing", a password field, with the sentence "This server asks for a key to start sharing. Whoever runs it can give it to you.") and the person tries again. A wrong key is said in the field ("That key is not right. Check it with whoever runs the server."). The key is **not remembered**: it lives in the panel while the panel is open, and is asked for again the next time a design is shared. That was chosen over a "remember on this device" box because the only place a page can keep it is `localStorage`, as plain text that every script of the page and every person at the browser can read, and the key is the operator's secret and not the person's own; a password manager may offer to keep it. Changing the server address takes the field and what was typed away, so a key is never shown to another server. The key is not part of the link, of the design or of a project file (`CreateKeyError` and `shareDesign` in `src/editor/live/connection.ts`, `LiveSection.tsx`).

**Not done here (see "Hardening" below):** accounts (who may create rooms is everybody who can reach `POST /api/rooms`, or, with `ROOM_CREATE_KEY`, everybody who has that one key; up to `MAX_ROOMS` and `ROOM_CREATE_PER_HOUR` for an address), logs and metrics, a Dockerfile (it is not written, and not tested), SQLite instead of one file per room, TLS (use a reverse proxy).

Rooms created before the owner key was introduced require operator cleanup or recreation. Existing edit and view links retain their room permissions. A room credential is omitted when exporting or importing a portable project or backup.

## What is left (in order)

1. **Presence and review.** Propose participant names and cursors, pinned comment threads, a commenter role, safer editing when two people work on the same object, and approval tied to a specific room revision. These are planned features.
2. **Room operations.** Expiry (`ROOM_TTL_DAYS`), the limit on making rooms per address and the refusal of other origins are there (see "The server"). Add revocation, a room admission policy, operational telemetry, retention and restore procedures, and deployment and load tests. See [the roadmap](PLAN-DIAGRAMS-AND-COLLABORATION.md) and [the security policy](../SECURITY.md).
3. **Asset lifecycle and durable queues.** Shared uploads currently have a 9 MiB per-image and 36 MiB per-room limit. A room retains unused uploads until deletion (each is a file in the room's folder of images). If a server stops between removing a room's record and removing its images, the folder `<room>.assets` stays behind with no room; nothing looks for such folders yet. Evaluate cleanup for unused images and recovery of unsent batches across a tab close.
4. **Protocol evolution.** Consider catch-up by revision, offline batch compaction and explicit protocol versions. Same-property changes still use server order, including simultaneous text edits.

## Rules for changing this code

- A change to `ops.ts` or `protocol.ts` is a change of the wire format: keep old and new browsers talking, or bump a protocol version (not there yet) and refuse the old.
- A new field on an element needs nothing here (properties are generic, and `diffDesign` and `applyOp` replay a mode that is set or taken away: `blend` is the example); a new **kind of container** (something that holds elements, as a group does) needs `diffElements` and `edit` in `ops.ts` to learn about it, plus the checks in `protocol.ts`. A new property that holds an address needs its name in `ADDRESS_KEYS` of `protocol.ts`, or it is not checked; a new property that holds markup, or text that is put into markup or handed to a canvas as it is (as `svg`, `colors` and `blend` are), needs the same care in `checkValue`. A graphic that needs an element or an attribute that `svgSafety.ts` does not allow means a line on its list, the reason, and a test in `svgSafety.test.ts` (and the content test will tell if something that ships is refused).
- Keep `applyOp` total: never throw, return the same object when nothing changes.
- Every change to this code is checked by `ops.store.test.ts` (real actions), `content.test.ts` (everything the app ships) and `sync.sim.test.ts` (bad weather); add a step to the first when the editor gets a new action that touches the design in a new way.
