# How Craftly was verified

This record separates the current readiness regressions, full-suite measurements and the historical release checks. See the [roadmap](ROADMAP.md) for open work and the [accessibility audit](ACCESSIBILITY.md) for its scope.

## Production-readiness regressions

The 16 fixes were exercised in targeted regressions on the working tree after the blend-mode baseline. The full-suite outcome is recorded separately below. The production build, type checking, lint and formatting passed. The targeted automated run passed **893 tests**, and the final focused rerun passed **125 overlapping tests**. Those counts describe the two targeted runs.

| Evidence | Cases verified |
| --- | --- |
| Edge, 12 cases | Stale-tab overwrite and deletion, room-owner flow, portable credential removal and legacy import, failed-save navigation, failed and timed-out update saves, offline edit replay after a same-tab reload, rejected-edit recovery, image exchange in both directions, missing-image export, atomic project import and retry, and same-origin cache isolation |
| Server integration, 4 cases | Malformed HTTP and WebSocket targets, default room and peer limits, persistence before acknowledging an edit, and storage-aware health checks |

The browser regressions live in [readiness-regressions.cjs](../e2e/readiness-regressions.cjs) and [update.cjs](../e2e/update.cjs). The browser run injected an IndexedDB deletion and write failure, delayed save confirmation, disconnected a WebSocket, and rejected a collaboration batch. Regular Edge journeys also passed for editing, backup, migration, offline reopening and crash recovery.

**Current full run (2026-11-11, from the working tree).** Vitest ran 7,699 tests in 339 files. All 7,699 passed, none were skipped, and the test command exited with status 0. Type checking, lint with no warning, formatting, `npm audit` (0), the production build and the live-server build passed in the same session.

On 2026-11-10 the same suite had reported 7,696 passing and 3 failing, the same three on every run. All three were tests that had fallen behind the code, and only the tests were changed:

- Two [persisted-shape checks](../src/core/schema/persistedShapes.test.ts) flagged the optional owner key of a live link and the save revision of a summary. Both are now named there as added on purpose. An older summary has no revision, which is read as `null`. A link without an owner key only leaves the room on this device.
- The [File-menu test](../src/editor/topbar/FileMenu.test.tsx) did not navigate home after confirming Move to trash. The editor leaves only once the trashed state is saved, and the test had no autosave to save it. It installs one now, as the test of the action itself does. In the browser pane the same action saved, went home and offered Undo.

**Browser journeys (2026-11-10 and 2026-11-11, from the working tree).** On a freshly started dev server all 232 checks passed. On the production build (`dist-e2e`, with `OFFLINE=1`, served by `vite preview` without the Content-Security-Policy) 247 checks passed and one failed: in `live.cjs`, "a box dragged with the real pointer by one person moves for the other" read 100 for one person and 120 for the other. The fault was in the journey. A drag is sent while it happens, the box starts at 300 and the journey moves it 20 at a step, so 120 is the place one step before the end, and the journey took the first place under 250 that the other person showed. It now waits for the place the box was dropped at.

With that change the production build was served under the README's policy, enforced, by a small server written for the run (with `http://127.0.0.1:8788 ws://127.0.0.1:8788` and the same for 8789 added to `connect-src`, and a `report-uri` that writes every violation down). All 248 checks passed (`OFFLINE=1`, `LIVE_PORT=8788`) and no violation was reported. A fetch that the policy forbids, made on purpose afterwards, was blocked and written down, so the count of none can be trusted. [readiness-regressions.cjs](../e2e/readiness-regressions.cjs) passed its 8 steps against the same server and a disposable live server on 8789, also with no violation. A first run under the policy had failed two checks of `ml.cjs` for a reason that was in that server and not in the product: it answered 404 for a path that is no file, where `vite preview` answers with the app's page. The edited `live.cjs` then passed twice more on a freshly started dev server (14 checks each time).

## Historical verification

### Method

Everything below was run from a clean copy: the project folder without `node_modules`, `dist`, `dist-*` or `coverage`, then `npm ci` from `package-lock.json` (26 s, 288 top-level packages, no native add-ons). That shows that the repository holds everything it needs, and the numbers do not depend on what an earlier run left behind. The machine was Windows 11 with Node 26.13 and a local Chrome; **the GitHub Actions workflow has never run** (the repository has not been pushed to GitHub yet), so Linux and Node 22 are unchecked.

Back up & restore (2026-11-08) was checked the same way. Its tests were written first. A clean copy was installed again (`npm ci`, 658 source files) and put through types, lint, format, `npm audit`, the whole test suite with coverage and the production build; the first lint run in the copy found an error in a test that had been added after the last lint run in the project folder, which was fixed and the copy checked again. The dev-server journeys ran in the project folder, and the production journeys ran from the copy's build with the policy below enforced.

The update prompt (2026-11-08, the same night) was checked the same way: its tests first, then the clean copy again (types, lint, format, `npm audit`, the whole suite with coverage, the builds), the dev-server journeys in the project folder and the production journeys, with the new one, from the copy under the enforced policy.

The migration framework (2026-11-08, the morning after) was checked the same way: its tests first, then the clean copy again (types, lint, format, `npm audit`, the whole suite with coverage, the builds), the dev-server journeys in the project folder (on a freshly started server: after the source changes while one runs, a hot-reloaded module can be a second copy of the store) and the production journeys, with the new one, from the copy under the enforced policy.

The Pen tool (2026-11-08, the evening) was checked the same way: its tests first (the path maths, the bridge to a shape element, the pointer, point editing, the toolbar, the keys), then the clean copy again (types, lint, format, `npm audit`, the whole suite with coverage and the builds), the dev-server journeys in the project folder on a freshly started server and the production journeys, with the new one, from the copy under the enforced policy. All eight new source files are covered completely, on all four measures. Coverage and the mutation checks below found what the first tests had missed: unreachable guards (two exported hit-test functions that the overlay never used, a branch of the path reader that cannot be reached, a type guard that always held) were removed instead of tested, and 51 more tests were written for the guards that can be reached and for the lines that the mutation checks showed nobody was watching. The first browser run found a bug that no unit test had: a real browser puts the workspace away from the corner of the screen, and a press on the side of a path found nothing; a unit test with a displaced workspace now pins it.

Testing the Pen by hand in the browser pane (2026-11-09, a window 594 px wide, the way a person would) found five problems that the tests and the journeys had missed: Ctrl+Z while a path was being placed undid the shape made before it (and Enter then made that loss permanent), another page chosen in the middle of a path threw the path away without a word, Tab wrapped round the points for ever so that a keyboard could not reach Corner, Smooth or Close path, the toolbar of the points pushed Done off the edge of a narrow window, and Enter opened a locked path. They were fixed test-first: 18 tests were written and seen to fail for the right reasons, then the fixes made them pass; five checks were added to `e2e/pen.cjs`, and the one for the narrow window was shown to fail against the old stylesheet (Done ended 53 px past the bar); the clean copy was checked again, and the journeys on the dev server and on the production build were run again.

Combine shapes (2026-11-09) was checked the same way: its tests first at each layer (the path maths, the replace operation, the geometry, the store action, the editor's actions, the menus), each seen to fail for the right reason, then the clean copy again (types, lint, format, `npm audit`, the whole suite with coverage and the builds), the dev-server journeys on a freshly started server and the production journeys from the copy under the enforced policy. Three things came out of it that the unit tests alone had not shown. The first browser run failed in its first step: Vite's dev server found paper.js only when the page asked for it, prepared it and reloaded the page, which emptied the page the journey was working on; `optimizeDeps.include` now names it and `src/test/devServerDeps.test.ts` fails for any library that loads on first use and is not named. A test with a made-up shape whose even-odd hole runs the same way round as its outline showed that `reorient(true, true)`, which the first version used, takes such a hole away (the ring of the shape list runs the other way and had hidden it): even-odd shapes now use `reorient(false, true)`. And a probe of where the keyboard focus lands found it on `body` after Union (the toolbar button is gone with the shapes), so it is put on the canvas. 68 lines of the new code were then broken on purpose, one at a time, in the clean copy: the first pass noticed 59 of 65, and the six that nothing noticed led to the corrected orientation above, tests for a turn about the centre of the box, for straight sides written as lines, for a page deleted while the geometry loads, the removal of a check that could not matter, and a break of the toolbar that had changed nothing and was written again; the last full pass noticed all 68. In a window 594 px wide the shape toolbar has to be scrolled to reach **Combine** (it comes after Group and Align), and its menu opens inside the window.

Lines attached to shapes (2026-11-09, **checked from the working tree, not from a clean copy**) were built test first at each layer (the geometry, the rules, the store, the clones, the menus, the toolbar). Then: types, lint, format, `npm audit`, the whole suite with coverage and the builds; the new journey `e2e/connect.cjs` (mouse, keyboard and menu, dragging a box with the real pointer and reading the arrow from the pixels, undo, delete, duplicate, reload); and mutation spot checks. 55 deliberate breaks of the connector rules: 46 were caught at once; of the 9 that were not, 3 were conditions that turned out to be redundant and were removed from the code (a line that is attached to itself, a "was attached" test that nothing could reach, a fast path that only saved work), and 6 were missing tests (a line that is moved together with its shapes, facing the middle of the other box, the sides that were chosen kept on copies, the weight of a connector, a line whose shape was another line, an unchanged page) that were then written, after which all of them are caught. One of the nine looked like a missing test and was a wrong list of test files in the script. The first full run of the journeys on the dev server failed four "job layer" steps of `ml.cjs`: the known symptom of a dev server that has been running while the sources changed (see `e2e/README.md`); they passed on a freshly started server, and the whole set (173 checks) passed there. The first full run of the journeys on the production build under the enforced policy failed two clicks of `features.cjs` (30 s timeouts, in "Find and replace" and "delete a page"); both passed when that journey was run alone against the same build, and the second complete run, with nothing else running on the machine, passed all 187 checks with no policy violation. The cause of the two timeouts was not found; the likeliest is that unit tests were running at the same time.

Live editing, the core and a server (2026-11-09, also **from the working tree**): the operations, the check of what arrives, the room, the browser's session, the connection and the server (`docs/COLLABORATION.md`) were built test first. 161 tests: 3 of them run the real editor store through 40 random sequences of 60 actions and check that every change, sent through JSON and replayed on the design before, gives the design after and the other way round; 3 simulate up to six browsers with random delays, dropped connections and server restarts and check, after every step and at the end, that every copy equals what it has confirmed plus its own unconfirmed changes, and finally the server's design; 23 run the real server on a real port with real WebSockets and the browser's connection class as the client (the suite was run three times in a row to check that it is not flaky). 83 deliberate breaks of the core (not of the content checks, the connection class and the server, which came later) are all caught, 16 of them only after tests were added for what the first 67 had missed. A test that sends every template page and every graphic of the app through the content check failed at first, and found that pictures also use `builtin:` addresses. The built server (`npm run server:build`) was started by hand and answered `/api/health` and `POST /api/rooms`. **No browser journey covers any of this yet** because the editor is not connected to it; the production bundle does not contain it. `ws` is the new runtime dependency (MIT; `npm audit` finds nothing).

Working together in the interface (2026-11-09, also **from the working tree**) was built test first layer by layer: the store (25 tests first, 30 now: own-step undo, what others did, the connection), the browser's side (15 tests with the real store, the real connection and the real server on a real port), the links (21), the Share section, the mark in the top bar and the page of a link (25 component tests). Then the whole suite with coverage (333 files, 7,289 tests, statements 99.30 %, branches 97.13 %, functions 99.50 %, lines 99.85 %), format, lint, `npm audit` (0) and the build, and the journeys: the new `e2e/live.cjs` drives **three real browsers against the real server** (13 checks: starting from Share, joining by the edit link, a box dragged with the pointer, simultaneous edits to different properties, the title, an arrow attached by one person and followed by the other, undo of only one's own step, a view link that only looks, a reload, the same link twice, stopping to share) and passed on a fresh dev server; the whole set passed there (186 checks) and on the production build under the enforced policy (200 checks; the policy needs the origin of the live server added to `connect-src`, as the README says; the journey uses 8788). Things the checks found: the style test of the design tokens refused the plain red for the text of an error (`--c-danger` instead of `--c-danger-ink`), and a test that sends every template and graphic of the app through the content check found that pictures also use `builtin:` addresses. Mutation spot checks of this layer are in `docs/COLLABORATION.md`.

Hardening of what arrives from outside (2026-11-10, also **from the working tree**). An automated security review of the live-editing code pointed out two things, and both were true: the browser applied whatever a server sent (a link names the server and anybody can make a link), and the check of the markup of graphics was a pattern for what to keep out, which `<svg/onload=…>`, an attribute without quotes and a character reference that spells `javascript:` walk around. Three more turned up while fixing them: `recolorSvg` put the colours of a design into the markup as they were; the cleaning of the SVG exporter missed handlers written after a slash or without quotes, scripts that are never closed and tags built round each other; and a session that had been ended could be brought back by a good-looking message that was already on its way (the tests for that were run and seen to fail before the one line that fixes it; the others were written before the code, and what shows that they matter is the breaks below and the journey that fails without the check). What was built: `svgProblem` (a list of what is allowed, read with a tokenizer of its own; 97 tests, and a test in which the XML and HTML parsers of the test browser read 4,000 damaged drawings and whatever is accepted must come out of both as nothing but drawing), `checkDesign` and `parseServerMsg` (the protocol tests went from 60 to 134; the new `hostile.test.ts` has 25), `isPlainColor`, and an exporter that cleans until nothing changes. 95 deliberate breaks of these rules, one at a time on a clean copy of the final tree: 94 were caught by the first complete pass, and the last, whose search text had changed, by a run of its own; on the way an earlier pass had found one that nothing noticed (a test for a finite size in `checkDesign` that the walk below it already makes), which was removed from the code. The new journey `e2e/hostile.cjs` (5 checks: a few lines of `ws` pretend to be a server that sends a design with code in it, an honest one, and the same one turning bad) passes on the dev server and on the production build, and failed at exactly its two hostile steps when it was run once with the check of the browser switched off. Then the whole chain from the working tree: lint with no warning, format, `npm audit` (0), the build (which type-checks), the whole suite with coverage (336 files, 7,535 tests, statements 99.30 %, branches 97.16 %, functions 99.50 %, lines 99.85 %), and every journey: 191 checks on a freshly started dev server and 205 on the production build under the enforced policy, with no violation. The first run of this chain was stopped five minutes in to put the fix for the revived session into it; the numbers are those of the second. What was left on purpose is in `docs/COLLABORATION.md` (the server does not run `checkDesign` when it makes a room, no confirmation before joining a server that is not known, project files and backups are not checked for the markup of graphics).

The key out of the address of the socket (2026-11-10, also **from the working tree**). A second automated security review pointed out that the socket was opened at `/ws?room=…&key=…`, and an address is written in the log of every server and proxy that it passes. The tests were changed first and seen to fail (37 failed, each because the key was not yet in the first message or was still in the address), then the code: `join` carries the key (`ClientMsg`, `Session`, `Live`), `websocketUrl` names the room only, and the server takes the key from the first message, answers nothing before it, sends away a connection that shows none within `joinWaitMs` and keeps those who wait out of the room's places. 14 tests are new: 11 for the server (a key in the address lets nobody in, five shapes of a bad key, a connection that never joins and one that joins in time, those who wait use no places, a place given back, a room not kept in memory by a visitor who was turned away, those who wait sent away when sharing stops) and one each for the address of the socket (`links.test.ts`), the connection that shows its key again after every reconnect (`live.test.ts`) and the four addresses of a whole session (`connection.test.ts`). `e2e/live.cjs` has a 14th check (Playwright's `page.on("websocket")`: each of the nine connections of three people shows its key in its first message and none has it in its address); it passes, and when the key was put back into the address of a clean copy it failed alone, the other 13 passing. 23 deliberate breaks of these rules, one at a time on a clean copy: 22 were caught; the 23rd is equivalent (a key that is too long is hashed and cannot match anyway: the cap only saves the work). Then the whole chain from the working tree: lint with no warning, format, `npm audit` (0), the build (which type-checks), the whole suite with coverage (336 files, 7,549 tests, statements 99.30 %, branches 97.16 %, functions 99.50 %, lines 99.85 %), and every journey: 192 checks on a freshly started dev server and 206 on the production build under the enforced policy, with no violation (210 different ones).

Blend modes (2026-11-10, **from the working tree**) were built test first at each layer: the list of modes, the painter (jsdom has no compositing, so its tests read the calls: which canvas was painted, with which transform, alpha and operation), the SVG exporter, the check of what arrives, ungrouping, the toolbar box, the thumbnail and the exports; 132 new tests, each seen to fail for the right reason (the missing module, the refusals that did not happen, the group that kept no mode, the two new lines of the stored shape). Then types, lint, format, `npm audit`, the whole suite with coverage and the build; the new journey `e2e/blend.cjs` (20 checks) on a freshly started dev server and, from the clean copy, on the production build under the enforced policy (no violation); and 50 deliberate breaks. The journey reads real pixels: fifteen pairs of shapes, a backdrop and a shape in a different mode in each, at three points each, against the formulas of the W3C compositing standard that the journey carries, on the page (within 4 levels of 255), in the downloaded PNG (5) and in the downloaded SVG as the browser draws it (8): the 45 points agree in all three. Four things came out of it that the tests alone had not shown. (1) **The text editing box cannot mix.** `mix-blend-mode` on the box passed its unit test and did nothing in the browser, because the canvas and the box are in different stacking contexts (a screenshot of the editing state showed the plain colour); the style was taken out again and the limit is written down (`BLEND-MODES.md`, the README's known limitations). (2) **The Tab order of the popover looked broken to a script that pressed Tab every few milliseconds**: in Chrome `input.select()` also focuses, and the number field selects its text one frame after it gets the focus, so the focus came back to it. A person is slower than a frame; the journey waits 80 ms between keys and the component was not changed. (3) **The thumb of the transparency slider is 16 x 16 px**, which it was before; it is recorded in `ACCESSIBILITY.md`. (4) **A clean copy with a damaged `node_modules` made 33 breaks look noticed**: the copy's `jsdom` had lost one file, so no jsdom test could start, and a script that counted any failing run as a catch said "caught (no tests)" for every break checked by a component test. The copy was repaired and the script now counts a break as noticed only when a test ran and failed; all 50 were run again. Result: 49 noticed, one of them only after a test was added (a layer cleared while its context still had a transform), and the fiftieth changes nothing (the SVG writing `el.blend` where it writes `mode`, which are the same text whenever the group is made). The cost of an element with a mode was measured on 2026-11-10 (about 0.8 ms at 1280 x 720 and 3.5 ms at 2560 x 1440 per element, in the browser pane with the graphics card and in headless Chrome alike; the figures are in `BLEND-MODES.md`) and is the one known weak point. Lint found two unused variables in the journey itself, which were removed.

## What the coverage number counts

The gate counts configured TypeScript source under `src/`. JavaScript outside that include, such as `public/sw.js` and the browser journeys, does not contribute to the percentage. `vite.config.ts` excludes the live-server entry point (`src/server/main.ts`), declarations, tests and their harness, the development pages (`src/dev`, the UI-kit gallery: 14 files, 1,639 statements, not in the production build) and two files that only run in a real browser (`src/ml/worker.ts`, `src/ml/ortRuntime.ts`: 5 statements, which `e2e/ml.cjs` runs). On 2026-11-07, with the two browser-only files counted as uncovered the totals were 99.40, 97.14, 99.65 and 99.90 %, and with the development pages counted as uncovered too about 93.5, 92.6, 93.7 and 94.0 %. With the backup code, the update prompt and the migration framework added, the statements figures are 99.41 % and about 93.7 % (the other three were not worked out again). The Pen tool adds 599 statements at full coverage, and the totals of the gate are now 99.44, 97.36, 99.69 and 99.92 %.

The totals hide thin spots. Of 359 files, 226 are covered completely on all four measures; 58 are under 95 % on at least one (47 of them on branches alone). By folder the thinnest are `src/ml` (branches 94.2 %, functions 94.0 %, the model store, the service and the engine) and `src/data` (branches 94.8 %). Each folder is above 90 % on every measure. The backup code is covered completely or nearly: the ZIP reader and the manifest rules at 100 % on all four measures, `backup.ts` at 99.56 % of statements and 100 % of branches. The eight files of the Pen tool (`pen.ts`, `penShape.ts`, `penTool.ts`, `PenPreview.tsx`, `PathEditOverlay.tsx`, `pathEditActions.ts`, `pathEditStore.ts`, `PathBar.tsx`) are at 100 % on all four.

## Limits of the historical runs

- **GitHub Actions.** The workflow had never run when these checks were made; its first run is described above.
- **Other browsers and devices.** Firefox, Safari, a real phone or tablet with touch, and a real screen reader (NVDA, VoiceOver) were not used. The journeys run in Chrome.
- **A real model download** from Hugging Face behind the Content-Security-Policy, and from a sub-folder. The journeys use hand-made models; the hosts in the policy for the real download are not verified.
- **Performance on weak hardware** beyond the measurements in [`ROADMAP.md`](ROADMAP.md). The dashboard shows a layout shift of 0.06 to 0.10 while its carousels appear.
- **The migration framework** with a migration step that has run on real data (none exists yet), in other browsers (the order of `versionchange` and `blocked` events and what a connection may still write while an upgrade waits was seen in Chrome only), and with a library of a gigabyte or more when a database step has to move records.
- **The update prompt** with a real deployment on a real host (the journey changes what a local server answers), in other browsers, and with a screen reader. A person who upgrades from the release before it keeps the old worker until every tab is closed once: its pages have no notice.
- **The Pen tool** in other browsers, with touch or a stylus (it uses pointer events, so it should work, but no device was tried), with a screen reader (the toolbar caption is a live region that nobody listened to), and with a path of thousands of points (every pointer move rewrites the element and redraws the page; the speed was not measured). Points can only be placed with a pointer.
- **Crash recovery and problem reports** (built 2026-11-09, finished and checked 2026-11-10, from the working tree): 135 new tests, and every statement and branch of its files is covered (a run of those files alone lists no line that no test reaches). 75 deliberate breaks of its rules, one at a time on a clean copy: the first pass caught 74, the survivor (a problem that came again is told again, hidden by the minute between notices) got a test, and all 75 are caught; 17 more, of the way back on the screen that cannot open a design, are all caught (92 of 92). `e2e/crash.cjs` (20 checks, in `npm run e2e` and in CI) passes on the dev server and on the production build under the enforced policy, with no violation: a state that stops the editor and cannot be stored, the screen and the time the design was saved, the problem written down, the report read, copied, downloaded and sent only on Send (no cookies, no referrer, nothing of the design), a reload that opens the design again and a second stop within two minutes that says so, going back to a version (and what was there kept), a copy of the design as a file, a design that is stored damaged and so refused, with the way back on the screen that says so (its earlier versions read, the newest one put back, the three shapes again), errors that nothing caught, both menu entries, a part of the app that cannot be fetched, and, on the crash screen and the dialog, the keyboard walk, the contrast of the text, the size of the controls and the fit of a window 375 px and 594 px wide. Finishing it found and fixed three faults: a list of problems cleared in another tab came back with the next problem, the headings of the two folded sections of the crash screen were 20 px tall, and the list in the dialog was a `listbox` without the arrow keys it promises. The screen "We couldn't open this design" had no way back to the earlier versions; it shows the section of the crash screen now (`RecoveryPanel`, written test first: the new tests failed, then passed), and its contrast, controls and fit at 375 px are measured with the rest. Not run: a real screen reader or axe-core, a real endpoint receiving a report, and a deployment that replaces a file under an open tab.
