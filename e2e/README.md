# Browser journeys

Scripted end-to-end checks that drive the real app in Chrome (through `playwright-core`; no browser is downloaded, a local Chrome, Edge or Chromium is used). They click through the interface the way a person would and read the document store (`window.__editor`) to confirm the result.

```bash
npm run dev            # in one terminal: http://127.0.0.1:5173
npm run e2e            # in another: runs every journey, exits non-zero on a failure
```

Together the journeys hold 229 checks: 211 run on the dev server and 225 on a production build (with `OFFLINE=1`), since a few belong to one or the other. The video checks of `animated-export.cjs` record in real time and need the tab in front, so a very busy machine can fail one of them once: run `node e2e/animated-export.cjs` alone before you suspect the app.

`ml-real.cjs` is not part of `npm run e2e`: it downloads the real models once (the background remover is 88.1 MB, the upscaler 4.9 MB), keeps them in a browser profile in the temp folder, runs Remove background on a drawn photo, Blur background on one with a wall of dots (the mug unchanged, the dots gone, no halo, a second try without the model; a cut-out sticker left alone; a 12-megapixel photo, with a watch on how long the page is blocked), Colour pop on a mug in front of a wall of strong colour (the wall grey, the mug unchanged, a faint rim, the faded style without the model, a sticker left alone, a 12-megapixel photo) and Upscale on a small soft one, and checks the results (the upscaled edges against a plain stretch, a transparent picture for a dark fringe), printing the toasts, the console lines and the GPU's limits when a job fails. `ONLY=upscale`, `ONLY=remove-background` or `ONLY=blur-background` or `ONLY=colour-pop` runs one tool and downloads only its model (the three background tools share one). Run it with `node e2e/ml-real.cjs` when you want that proof. `ML_PROFILE` names the browser profile folder that keeps the models (default: `craftly-ml-profile` in the system temp folder) and `FRESH=1` deletes that folder first, so the models are downloaded again.

`ml-probe.cjs` (`MODEL=path/to/model.onnx node e2e/ml-probe.cjs`) tries any model file on this GPU before it is wired into the app: its inputs and outputs, the session, timed runs at a tile size (`DIM`, `RUNS`), and a check against a reference output (`REF_IN`, `REF_OUT`, two `.npy` files). It needs a production build to be served.

Build variables: `VITE_EXPOSE_STORE=1` exposes the store to the journeys, and `VITE_CRAFTLY_REPORT_URL=/__report` gives a production build the Send button of the problem report that `crash.cjs` uses (the development server has it already; the journey answers the request itself, so nothing has to take it). In Git Bash on Windows put `MSYS_NO_PATHCONV=1` in front of the build command, or the shell turns `/__report` into a path in the Git folder and the build has no Send button.

Settings (environment variables): `BASE` the app URL (default `http://127.0.0.1:5173`), `CHROME_PATH` a browser executable, `HEADED=1` to watch, `E2E_DIST` the production build that `update.cjs` serves (default `dist-e2e` in the project folder, built as described below), `E2E_OUT` where screenshots go (default: a `craftly-e2e` folder in the system temp directory; a failing step saves `NN-FAIL-....png`).

The store handle `window.__editor` exists in the dev server. After you edit source files while the dev server is running, restart it before running the journeys: the job-layer steps of `ml.cjs` import the app's modules by their plain URLs, and once the server has reloaded a module that many others depend on (`core/color.ts`, say) it hands the app those modules under `?t=` URLs, so the step and the app would hold two separate stores and the four steps fail with "That picture could not be read." A freshly started server passes. To run the journeys against a production build, build with `VITE_EXPOSE_STORE=1 VITE_CRAFTLY_REPORT_URL=/__report npx vite build --outDir dist-e2e` (a `dist-` folder is not watched by the dev server, so it can keep running meanwhile) and serve it with `npx vite preview --outDir dist-e2e --port 4174`. The offline journey needs `OFFLINE=1`:

```bash
BASE=http://127.0.0.1:4174 OFFLINE=1 npm run e2e
```

To check a build that is published in a sub-folder, build with that base (`npx vite build --base=/craftly/ --outDir dist-sub`; in Git Bash put `MSYS_NO_PATHCONV=1` in front, or the shell rewrites `/craftly/`), serve it with `npx vite preview --base=/craftly/ --outDir dist-sub --port 4177`, and give the journeys the folder in `BASE`: `BASE=http://127.0.0.1:4177/craftly node e2e/journey.cjs` (and `dashboard.cjs`, `ml.cjs`, `offline.cjs`). On 2026-11-07 these four passed from `/craftly/` with 19, 7, 13 and 4 checks; on 2026-11-09 `combine.cjs` (13 checks) and `offline.cjs` (6) passed from there too, with a build made with `VITE_EXPOSE_STORE=1`; the others were not run there.

In PowerShell a variable is set first, on its own: `$env:BASE = "http://127.0.0.1:4174"; $env:OFFLINE = "1"; npm run e2e` (and `Remove-Item Env:OFFLINE` afterwards).
