## 1. WebCodecs support status in 2026 (Chrome, Edge, Safari, Firefox; video and audio; codecs; hardware acceleration; mobile; limits)

### Takeaway
WebCodecs is effectively universal on current desktop browsers and on Chrome Android and iOS Safari (caniuse: 95.92% global usage). Gaps that still matter are: Firefox Android (none), Safari audio codecs only since 26.0, Safari video-encoder bugs fixed only in 27.x, hardware-dependent codecs (HEVC encode, AV1 encode and Safari AV1 decode) and uneven AAC encoder availability. The W3C spec is still a Working Draft (2 Nov 2026).

### Cited Findings

#### Support matrix and spec status
- caniuse "WebCodecs API": Chrome 94, Edge 94, Opera 80, Samsung Internet 17.0, Firefox 130, Safari desktop 26.0 and Safari iOS 26.0 (both shown as partial for 16.4 to 18.7 with no footnote text), Chrome for Android listed only at 157, Firefox for Android not supported through 159. Global usage 95.92% (92.27% full + 3.65% partial). — [caniuse](https://caniuse.com/webcodecs)
- Spec status: W3C Working Draft dated 2 November 2026 (previous version 26 October 2026); editors Paul Adenot (Mozilla) and Eugene Zemtsov (Google); not a Recommendation. — [W3C WebCodecs](https://www.w3.org/TR/webcodecs/)
- MDN lists 12 interfaces (VideoEncoder, VideoDecoder, AudioEncoder, AudioDecoder, VideoFrame, AudioData, EncodedVideoChunk, EncodedAudioChunk, ImageDecoder, ImageTrack, ImageTrackList, VideoColorSpace), "available in Dedicated Web Workers", says devices/browsers support only a subset of codecs, that H.265 has "significant gaps in browser support outside of Apple platforms", and that AV1 hardware encoder support is "limited". — [MDN WebCodecs API](https://developer.mozilla.org/en-US/docs/Web/API/WebCodecs_API)
- AudioEncoder is marked not Baseline ("does not work in some of the most widely-used browsers"), secure-contexts only (HTTPS), dedicated workers. — [MDN AudioEncoder](https://developer.mozilla.org/en-US/docs/Web/API/AudioEncoder)

#### Chrome / Edge
- HEVC encoding in WebCodecs landed in Chromium M130; scope limited to Windows, macOS and Android hosts, ChromeOS/Linux "may follow"; only works if device and OS provide the capability ("requires hardware support" per a Chromium engineer); MediaRecorder got HEVC/H.264 MP4 and Matroska support as a follow-up; the M130 WebCodecs change was initially not listed on chromestatus. — [blink-dev thread](https://groups.google.com/a/chromium.org/g/blink-dev/c/YJ1QijNiHeM)

#### Firefox
- Firefox 130 release notes: WebCodecs "supported on desktop releases"; Android enabled only in Nightly; interfaces VideoEncoder, VideoDecoder, EncodedVideoChunk, VideoFrame, VideoColorSpace, AudioEncoder, EncodedAudioChunk, AudioData, AudioDecoder (ImageDecoder not listed). — [MDN Firefox 130](https://developer.mozilla.org/en-US/docs/Mozilla/Firefox/Releases/130)
- Mozilla meta bug: desktop "shipped in H1 2024"; latest human comments (about a year old on the page) say "Android support is all that's left" and is being worked on; flags for Firefox 159-161 are unset (no Android ship version recorded). Open dependent bugs include H.264 encoder bitrate issue on FFmpeg 4.x, invalid AVCC record, timestamp shifts, a libx264 level failure under decimal-comma locales, VideoDecoder.close() crash with pending callbacks, outputs delivered after reset(), HEVC test enablement still open. — [Bugzilla 1746557](https://bugzilla.mozilla.org/show_bug.cgi?id=1746557)
- Firefox Android: AV1 shows 0% in the 2026 dataset, attributed to the missing WebCodecs API rather than hardware. — [Codec analysis 2026](https://webcodecsfundamentals.org/datasets/codec-analysis-2026/)

#### Hardware acceleration
- WebCodecs accepts a hardware hint; Mediabunny exposes `hardwareAcceleration: 'no-preference' | 'prefer-hardware' | 'prefer-software'`, applied to both decode and encode; docs say it is "best left on" no-preference. — [Mediabunny: converting](https://mediabunny.dev/guide/converting-media-files), [Mediabunny: media sources](https://raw.githubusercontent.com/Vanilagy/mediabunny/main/docs/guide/media-sources.md)
- Spec privacy section: user agents may silently fall back to software codecs when hardware codec instances are exhausted; retaining VideoFrames until decode stalls reveals driver buffer-pool sizes; codec reclamation (inactive/background codecs) is observable. — [W3C WebCodecs §13.3](https://www.w3.org/TR/webcodecs/)

#### Practical limits (library-agnostic)
- Decoders need about 3 to 5 chunks before the first frame is emitted; the last outputs never arrive until `flush()`; queues (`decodeQueueSize`, `encodeQueueSize`) must be fed progressively or the app "might crash"; settings that work on one device can fail on another so call `isConfigSupported`; a corrupted frame can stop decoding so recovery is required. — [WebCodecs Fundamentals: reality check](https://webcodecsfundamentals.org/intro/reality-check/)
- Frame memory: site claims one 4K VideoFrame uses about 24 MB (so roughly 200 frames on a 5 GB GPU, about 7 s of video) [reality check]. Mozilla's Paul Adenot's talk gives YUV420 1080p SDR about 4 MB, 4K SDR about 16 MB, P010 1080p HDR about 32 MB (these two sources do not agree; see Inferences for computed values). — [reality check](https://webcodecsfundamentals.org/intro/reality-check/), [Adenot talk](https://www.w3.org/2021/03/media-production-workshop/talks/paul-adenot-webcodecs-performance.html)
- VideoFrames live in GPU memory (when HW decoded); `copyTo`/readback is expensive; Adenot's single-frame copy times (C++, high-end Linux workstation): YUV420 1080p 1.5 ms hot cache / 4.5 ms cold, 4K 6.6 / 17 ms, P010 1080p 15 / 33 ms. — [CPU vs GPU](https://webcodecsfundamentals.org/concepts/cpu-vs-gpu/), [Adenot talk](https://www.w3.org/2021/03/media-production-workshop/talks/paul-adenot-webcodecs-performance.html)
- Chrome's own guidance: call `VideoFrame.close()` promptly; move per-frame and per-chunk handling into a worker (VideoFrame is transferable; `transferControlToOffscreen()` for off-main-thread rendering). — [Chrome for Developers](https://developer.chrome.com/docs/web-platform/best-practices/webcodecs)
- W3C best practices (non-normative): realtime VideoFrame processing "generally" belongs in a worker; main-thread jank varies in the field. — [W3C WebCodecs §14](https://www.w3.org/TR/webcodecs/)

### Inferences
- A defensible support policy for Craftly video: Chromium 94+ (full), Safari 26+ (recommend requiring 27.2+ for the H.264 Main/High encoder stall fix and 27.0+ for the B-frame ordering fix), Firefox 130+ desktop (works, but no File System Access API and WebGPU uncertain). Treat Firefox Android as unsupported: feature-detect `VideoEncoder`/`AudioEncoder` and keep the existing MediaRecorder/GIF path as the fallback.
- For export, H.264 Baseline/Main + AAC in MP4 is available on essentially all supported browsers; AAC encoding should be probed with `AudioEncoder.isConfigSupported` and fall back to Opus (WebM or MP4) rather than shipping a WASM AAC encoder (smaller patent surface, see section 7). Hold HEVC/AV1 export out of v1.
- Computed raw frame sizes (not from a source): 1080p 8-bit 4:2:0 (NV12/I420) = 3.1 MB; 1080p RGBA = 8.3 MB; 4K 4:2:0 = 12.4 MB; 4K RGBA = 33.2 MB. The "24 MB" figure matches roughly 3 bytes/pixel (RGB24), the 16 MB figure matches 4:2:0 plus alignment. Budget on the RGBA numbers if frames get drawn to canvases.
- iPhone/modern-phone footage is commonly HEVC (general knowledge, not source-verified here): expect import failures on Firefox/Edge for HEVC clips; plan a clear "unsupported codec" error and an optional (lazy-loaded) transcode path.

### Gaps
- No per-browser × per-platform × hardware-acceleration matrix exists in the sources (dataset v2 planned).
- No source found for maximum simultaneous hardware decoders on Chrome/Safari/mobile, or for iOS/Android memory ceilings.
- caniuse gives no footnote for Safari 16.4 to 18.7 "partial" (the WebKit 26.0 blog implies video-only).
- Whether Chrome's AAC encoder exists on Linux, and which Safari 27.x audio codecs are encodable, was not verified.
- HEVC Advance (Access Advance) rate-increase article (27 Jan 2026, headline "extends HEVC Advance rate increase deadline") could not be retrieved; content unknown.

## 2. Libraries and building blocks (Mediabunny, mp4-muxer/webm-muxer, ffmpeg.wasm, mp4box.js, Remotion, PixiJS/WebGL compositors, Web Audio/OfflineAudioContext, waveforms, timeline UI)

### Takeaway
Mediabunny (MPL-2.0, pure TypeScript, zero runtime dependencies, v1.65.2, 18.0M npm downloads in the last month) is now the standard media I/O layer on top of WebCodecs and has superseded mp4-muxer/webm-muxer; Remotion is migrating to it. ffmpeg.wasm carries a GPL-2.0-or-later core of about 31 MB per wasm file and is 12x to 25x slower than native in its own benchmark, so it belongs only on a lazy-loaded fallback path, if at all. For the timeline UI, react-timeline-editor (MIT) exists but is small; the established editors mostly built their own.

### Cited Findings

#### Mediabunny
- What it is: "Pure TypeScript media toolkit for reading, writing, and converting media files, directly in the browser"; reads/writes MP4, MOV, WebM, MKV, Ogg, MP3, WAVE, ADTS, FLAC, MPEG-TS, HLS, segmented MP4; Node/Bun/Deno through `@mediabunny/server`; zero dependencies; tree-shakable (claims "as small as 5 kB gzipped"); microsecond-accurate; streaming I/O "for files of any size". — [GitHub](https://github.com/Vanilagy/mediabunny), [intro](https://mediabunny.dev/guide/introduction)
- Version/licence/size from npm: 1.65.2, MPL-2.0, unpackedSize 11,355,831 bytes in 293 files (includes types/sourcemaps; not the bundle size), runtime deps are type-only (`@types/dom-webcodecs`, `@types/dom-mediacapture-transform`). — [npm registry](https://registry.npmjs.org/mediabunny/latest)
- Adoption: 18,018,742 npm downloads 2026-10-05 to 2026-11-03; 7.4k GitHub stars, 1,531 commits; sponsors include Figma (platinum), Remotion, Kino, Screen Studio, Tella (gold), Jitter (silver), React Video Editor, Mux (bronze). — [npm downloads API](https://api.npmjs.org/downloads/point/last-month/mediabunny), [GitHub](https://github.com/Vanilagy/mediabunny)
- Licence reading (summary of GitHub text): MPL-2.0; "free to use for any purpose, including closed-source commercial use"; if you modify the licensed source and distribute it you must publish those modifications under MPL-2.0; do not remove licence/copyright headers or claim the "Mediabunny" trademark; no warranty. — [GitHub](https://github.com/Vanilagy/mediabunny)
- Codecs: AVC, HEVC, VP8, VP9, AV1 via WebCodecs; AAC/Opus/Vorbis via WebCodecs (browser-dependent); PCM, mu-law, A-law built in; polyfills as separate packages: `@mediabunny/aac-encoder` (for browsers lacking AAC encode), `@mediabunny/mp3-encoder`, `@mediabunny/flac-encoder`, `@mediabunny/ac3`, `@mediabunny/dts`, `@mediabunny/truehd`, `@mediabunny/prores` (decode); you can register custom encoders/decoders; runtime checks `canEncode`, `canDecode`, `getFirstEncodableVideoCodec`; WebVTT subtitle output only. — [supported formats and codecs](https://mediabunny.dev/guide/supported-formats-and-codecs)
- Reading by timestamp (editor-relevant): `VideoSampleSink.getSample(t)` returns the last sample with timestamp <= t (or null); `samples()` iterates in presentation order; `samplesAtTimestamps()` for sparse lookups "avoids decoding the same packet twice"; `CanvasSink` yields canvases and with `poolSize` reuses them in a ring buffer to keep VRAM constant; `AudioBufferSink`/`AudioSampleSink` for audio; `EncodedPacketSink` exposes `getKeyPacket`/`getNextKeyPacket` and `verifyKeyPackets`; samples must be `close()`d; breaking out of a `for await` cleans up decoders. The docs do not define frame accuracy beyond this. — [media sinks](https://mediabunny.dev/guide/media-sinks)
- Writing: `CanvasSource.add(timestamp, duration)` captures a canvas per output frame; `VideoSampleSource`, `AudioSampleSource`, `AudioBufferSource` (first buffer at t=0, later buffers appended in order, i.e. no arbitrary placement), `MediaStreamVideoTrackSource`/`MediaStreamAudioTrackSource` (webcam/mic/screen), packet sources for remuxing, `TextSubtitleSource`. Every `add()` returns a promise that propagates backpressure. Video config: `codec`, `quality` (or bitrate/quantizer), `keyFrameInterval` (max seconds between key frames, default 2), `latencyMode` ('quality' default | 'realtime'), `hardwareAcceleration`, `alpha` ('discard' default | 'keep', needs WebM/Matroska), `sizeChangeBehavior`, `transform` (width/height/fit/rotate/flip/crop/frameRate). Close sources as soon as done. — [media sources](https://raw.githubusercontent.com/Vanilagy/mediabunny/main/docs/guide/media-sources.md)
- Output targets: `BufferTarget` ("great choice for small-ish files (< 100 MB)"), `StreamTarget` (wraps a WritableStream, chunks must be written at byte offsets, default chunk 16 MiB, respects backpressure), `NullTarget`, `PathedTarget` (HLS), `FilePathTarget` (Node). Multi-track outputs must buffer packets (written chronologically), so add media in interleaved chunks (example: 10 s video then 10 s audio). Video `frameRate` snaps timestamps/durations to that rate (use exact fractions like 24000/1001). Lifecycle `start()` -> `finalize()` / `cancel()`. — [writing media files](https://raw.githubusercontent.com/Vanilagy/mediabunny/main/docs/guide/writing-media-files.md)
- `Conversion.init({input, output, ...}).execute()`: trim (`trim: {start, end}` seconds), resize/fit (fill|contain|cover), rotate, flip, crop, frameRate, quality, audio resample/channel mix, per-track discard, `onProgress` (0 to 1), `cancel()`, `isValid`/`discardedTracks` reasons; copies packets without re-encoding whenever the config allows ("fast and lossless"); any pixel/sample change forces transcode; auto-picks an encodable codec or discards the track with `no_encodable_target_codec`. — [converting media files](https://mediabunny.dev/guide/converting-media-files)
- Mediabunny's docs live in the repo as 14 markdown guides (converting, input/output formats, media sinks/sources, packets-and-samples, quick-start, HLS read/write). — [docs/guide](https://github.com/Vanilagy/mediabunny/tree/main/docs/guide)

#### Web Audio, mixing and waveforms
- `AudioContext.currentTime` is the master reference timeline; schedule with `start(when, offset, duration)`; `AudioBufferSourceNode` cannot pause (stop and store position, restart to seek); `playbackRate` alone shifts pitch; pitch-preserving speed change uses a SoundTouch AudioWorklet and requires rebuilding the chain (parameters "can't be changed on-the-fly reliably"); decoded audio is large ("1 hour of audio taking up more than 1GB of RAM"). — [WebCodecs Fundamentals: Web Audio playback](https://webcodecsfundamentals.org/audio/web-audio/)
- Adenot: playing audio through an AudioWorklet requires copying into the worklet output buffer; AudioData/VideoFrame ownership transfer (`detach()`) is only proposed. — [Adenot talk](https://www.w3.org/2021/03/media-production-workshop/talks/paul-adenot-webcodecs-performance.html)

- wavesurfer.js 8.0.5, BSD-3-Clause, 1.66 MB unpacked, 5,795,637 downloads/month. — [npm wavesurfer.js](https://registry.npmjs.org/wavesurfer.js/latest), [downloads](https://api.npmjs.org/downloads/point/last-month/mp4-muxer,webm-muxer,mp4box,pixi.js,wavesurfer.js,remotion,fabric,essentia.js,web-audio-beat-detector,onnxruntime-web)

- OpenVideo/react-video-editor packages `@openvideo/timeline` and `@openvideo/core` (dual licence, see section 3). — [GitHub](https://github.com/designcombo/react-video-editor)

### Inferences
- Recommended stack for Craftly: Mediabunny (Input/sinks for decode-by-timestamp, `CanvasSource` + audio sources + `StreamTarget` for export, `MediaStream*TrackSource` or MediaRecorder for voiceover), your existing canvas renderer as the compositor, Web Audio (+ AudioWorklet where needed) for preview, WebCodecs through Mediabunny only. MPL-2.0 is file-level copyleft: using it unmodified as an npm dependency needs no source disclosure for Craftly; patches to Mediabunny's own files would have to be published.
- Because `AudioBufferSource` appends buffers sequentially, an export mixer should render the timeline mix as continuous chunks (or use `AudioSampleSource` with explicit timestamps) rather than adding clips at offsets.
- Computed audio memory (not from a source): 48 kHz stereo float32 = 384,000 B/s = 23.0 MB/min = 1.38 GB/h (consistent with the ">1 GB per hour" claim); 16 kHz mono float32 for Whisper = 3.84 MB/min. Decode audio lazily in chunks (AudioBufferSink/AudioSampleSink) and mix in 10 to 30 s segments instead of one giant OfflineAudioContext.
- ffmpeg.wasm is a poor fit for the default path: GPL core (x264/x265 enabled), about 31 MB per wasm, 12x to 25x slower than native, needs cross-origin isolation for threads. Keep it, if ever, as an optional lazy-loaded "import odd formats / transcode" tool, and take the GPL obligations into account.
- PixiJS is not needed since Craftly already owns a 2D renderer; Diffusion Studio's choice (Canvas 2D for composition) shows 2D canvas is viable for a v1 compositor. WebGL/WebGPU becomes valuable for transitions/colour effects later.
- Timeline UI: react-timeline-editor is small and generic (rows/actions); Craftly's existing selection, snapping and undo model suggests a custom canvas or DOM timeline will integrate better, using react-timeline-editor only as a reference or for a throwaway spike.

### Gaps
- Mediabunny's real-world frame-accurate seeking performance (decode-from-keyframe cost, GOP-length sensitivity) is not documented; needs a spike.
- No source for OfflineAudioContext limits (max length, Safari quirks); peaks.js, dnd-timeline and other timeline/waveform libraries were not checked.
- The licence/provenance of the encoder inside `@mediabunny/aac-encoder` was not checked.
- Remotion web-renderer's supported CSS/HTML subset (limitations page 404'd) and Remotion's Editor Starter price/rendering approach were not retrieved.
- The ffmpeg.wasm 2 GB file-size limit was not confirmed from an ffmpeg.wasm source (the fetched docs pages state no memory limit).

## 4. Architecture patterns (project model, preview compositor, seeking and proxies, audio sync, export pipeline, memory/performance, file access, workers)

### Takeaway
Every credible implementation converges on the same shape: a declarative project model (tracks, clips with in/out and transform, keyframes, effects) in a store with snapshot-based undo; a clock-driven preview that decodes frames on demand by timestamp and draws them through the same compositor used for export; Web Audio as the audio master clock; and an offline export loop that pulls frames by timestamp, composites, encodes with backpressure and streams into a file. The hard parts are decode scheduling, memory discipline (bounded frame queues) and cross-browser file output.

### Cited Findings

#### Project model
- FreeCut: items (video, audio, text, image, shape, mask, Lottie, compound) on multiple tracks; multiple "sequences" per project with compound clips unified as sequences; linked audio/video clips; keyframes (Bezier graph + dopesheet, easing presets, procedural modifiers evaluated at render time with one-click bake) on transform/crop/mask/text/effect/colour; Zustand stores with a snapshot-diff command store for undo/redo; projects stored as plain files in a user-chosen workspace folder (File System Access), media imported without copying originals, auto-save, soft delete/restore, ZIP bundles validated with Zod, legacy browser-storage projects migrated. — [FreeCut README](https://raw.githubusercontent.com/walterlow/freecut/main/README.md)
- Diffusion Studio: Composition > Layers > Clips (video/image/text/rectangle), `SEQUENTIAL` layer mode, keyframe animations, masks, effects, transitions, audio ramps, checkpoints; layered like Pixi but over Canvas 2D. — [GitHub](https://github.com/diffusionstudio/core)
- WebAV: `IClip` wraps media sources; `Sprite` adds spatial and temporal properties; `Combinator` composites sprites into an output stream; `av-canvas` adds interactive move/scale/rotate. — [WebAV](https://github.com/hughfenghen/WebAV)
- Twick: `@twick/timeline` holds the model, tracks, operations and undo/redo; `@twick/live-player` syncs playback with timeline state; `@twick/effects`/`@twick/gl-runtime` apply WebGL fragment-shader passes on both the browser and server export paths. — [Twick](https://github.com/ncounterspecialist/twick)
- Omniclip: unidirectional flow (State, Actions, Controllers, Views). — [Omniclip](https://github.com/omni-media/omniclip)

#### Preview compositor, seeking, proxies
- FreeCut preview: custom `Clock` + composition runtime for frame-accurate playback, decoder prewarming, source warming, adaptive preview quality, fast-scrub overlays; WebGPU-first compositing with Canvas 2D fallback for transitions; proxy generation supported (internals undocumented); frame-cache design undocumented. — [FreeCut README](https://raw.githubusercontent.com/walterlow/freecut/main/README.md)
- Mediabunny timestamp semantics: `getSample(t)` = last sample with timestamp <= t; `samplesAtTimestamps` avoids re-decoding the same packet; `CanvasSink` pooling keeps VRAM constant; `getKeyPacket`/`getNextKeyPacket` expose keyframes; `keyFrameInterval` (default 2 s) controls GOP length of anything you encode (e.g. proxies). — [media sinks](https://mediabunny.dev/guide/media-sinks), [media sources](https://raw.githubusercontent.com/Vanilagy/mediabunny/main/docs/guide/media-sources.md)
- Copy discipline: keep VideoFrames on the GPU; `importExternalTexture` zero-copy to WebGPU; avoid `copyTo`; Adenot's principle "memcpy is murder". — [CPU vs GPU](https://webcodecsfundamentals.org/concepts/cpu-vs-gpu/), [Adenot talk](https://www.w3.org/2021/03/media-production-workshop/talks/paul-adenot-webcodecs-performance.html)
- Safari bug history relevant to seeking/ordering: hardware VideoDecoder returned frames out of order for B-frame videos until Safari 27.0. — [WebKit 27.0](https://webkit.org/blog/18325/webkit-features-for-safari-27-0/)

#### Audio sync
- Use `AudioContext.currentTime` as the clock: position = `pausedAt + (ctx.currentTime - startTime) * speed`; schedule each clip's buffer with `start(when, offset, duration)`; pause = stop and remember position; speed change rebuilds the chain. — [Web Audio playback page](https://webcodecsfundamentals.org/audio/web-audio/)
- Export mixes the same DSP (fades/EQ/pitch) as preview (FreeCut); Mediabunny audio sources take `AudioBuffer`s (sequential) or `AudioSample`s (timestamped). — [FreeCut](https://raw.githubusercontent.com/walterlow/freecut/main/README.md), [media sources](https://raw.githubusercontent.com/Vanilagy/mediabunny/main/docs/guide/media-sources.md)
- Audio can be copied without re-encode when unchanged: the upscaler pipeline copies `EncodedAudioChunk`s from demuxer to muxer preserving timestamps. — [upscaler architecture](https://free.upscaler.video/technical/architecture/)

#### Export pipeline
- Reference five-stage pipeline (demux with Mediabunny, decode, process with WebGL/WebGPU, encode, mux) with explicit backpressure: decode queue capped at 20 chunks, at most 10 VideoFrames alive, encode queue capped at 20 frames, Streams API propagating pressure up to file reads; ETA from an exponential moving average of per-frame time; writes straight to disk with the File System Access API; Firefox/older browsers fall back to an in-memory ArrayBuffer + download. Reported throughput at 720p (WebGPU, super-resolution shaders): M4 MacBook Pro 120/40/15 FPS for small/medium/large networks; integrated-GPU desktops 40-60 FPS, a $200 Chromebook 40 FPS, recent phones 15-30 FPS (small model); about 6,500 daily users and about 100 h of video/day with zero server cost. — [upscaler architecture](https://free.upscaler.video/technical/architecture/)
- Mediabunny export primitives: `CanvasSource.add(timestamp, duration)` per frame, awaiting each `add()` for backpressure; `StreamTarget` for disk; interleave tracks in about 10 s chunks. — [media sources](https://raw.githubusercontent.com/Vanilagy/mediabunny/main/docs/guide/media-sources.md), [writing media files](https://raw.githubusercontent.com/Vanilagy/mediabunny/main/docs/guide/writing-media-files.md)
- Browser export limits reported by Twick: RAM/CPU-bound, recommends server rendering for long or complex projects. — [Twick](https://github.com/ncounterspecialist/twick)

#### Memory and performance numbers
- File sizes: 1080p about 2-5 GB/hour; user uploads over 20 GB seen; Chromium limits a single ArrayBuffer to 2 GB; finding the moov atom in a 5 GB file can take over a minute on a low-end netbook; the author transcoded 20 GB to 40 GB on a $200 netbook by streaming; suggests reading in chunks of about 5 minutes of video; `BufferTarget` fails past 2 GB. — [File handling](https://webcodecsfundamentals.org/concepts/file-handling/)
- Frame memory and copy costs: see section 1.

#### File access and storage
- File System Access API (`showOpenFilePicker`/`showSaveFilePicker`): Chrome 105, Edge 105, Opera 91; not supported in Firefox (listed through 162) or Safari (through 27.x) or Chrome Android; global 30.9%; Mozilla's standards position is "harmful". — [caniuse](https://caniuse.com/native-filesystem-api)
- Origin Private File System (`navigator.storage.getDirectory()`): Chrome/Edge 86, Firefox 111, Safari 15.2 (desktop and iOS), Samsung 21, Opera 72, Firefox Android 159; global 96.65%. — [caniuse OPFS](https://caniuse.com/mdn-api_storagemanager_getdirectory)
- Safari 17+ storage policy: browser-app origin quota up to 60% of total disk (15% for other apps), overall 80%/20%; no more prompts; eviction can happen under storage pressure or after a period without user interaction, per origin in LRU order; origins are "best-effort" unless `persist()` is granted (WebKit grants by heuristics, e.g. Home Screen web apps); `QuotaExceededError` must be handled. — [WebKit storage policy](https://webkit.org/blog/14403/updates-to-storage-policy/)
- Safari 26.0 added File System WritableStream support (scope unclear, see section 1); Safari 27.0 fixed IndexedDB issues (stale version-0 database after abort, worker connections after network-process crash, transactions blocked for a long time) and two FileSystemDirectoryHandle bugs. — [WebKit 26.0](https://webkit.org/blog/17333/webkit-features-in-safari-26-0/), [WebKit 27.0](https://webkit.org/blog/18325/webkit-features-for-safari-27-0/)
- FreeCut keeps originals in place and stores only metadata/caches (OPFS), reducing duplication; OpenReel warns that browser storage can be cleared and recommends backups. — [FreeCut](https://raw.githubusercontent.com/walterlow/freecut/main/README.md), [OpenReel](https://github.com/Augani/openreel-video)

#### Workers
- Dedicated workers support WebCodecs; Chrome and the spec advise handling frames/chunks in workers; VideoFrame is transferable; `transferControlToOffscreen()` allows off-main-thread canvas rendering. — [MDN](https://developer.mozilla.org/en-US/docs/Web/API/WebCodecs_API), [Chrome for Developers](https://developer.chrome.com/docs/web-platform/best-practices/webcodecs), [W3C §14](https://www.w3.org/TR/webcodecs/)
- FreeCut: Web Workers for heavy media processing and worker-backed render paths; AudioWorklets for audio. — [FreeCut](https://raw.githubusercontent.com/walterlow/freecut/main/README.md)

#### Cross-origin isolation (static hosting)
- Diffusion Studio requires `Cross-Origin-Opener-Policy: same-origin` and `Cross-Origin-Embedder-Policy: credentialless`; ffmpeg.wasm multi-thread and threaded whisper.cpp builds need SharedArrayBuffer; `coi-serviceworker` is the header-less workaround (see section 2). — [Diffusion Studio](https://github.com/diffusionstudio/core), [coi-serviceworker](https://github.com/gzuidhof/coi-serviceworker)

### Inferences
- Proposed Craftly architecture (my synthesis from the above):
  1. Project model: `Timeline { tracks[] { clips[] { assetId, trackId, start, duration, sourceIn, sourceOut, speed, transform, volume, fadeIn/Out, keyframes } } }`, with existing design elements (text/shapes/stickers/animations) as "overlay clips" so the current renderer draws them at timeline time t. Keep assets (media blobs/handles + probe metadata) separate from the timeline; reference-by-id.
  2. One `renderFrame(t)` used by both preview and export: pulls the video frame for each active clip via timestamp lookup, draws it as a layer into the existing renderer, then draws overlays. Preview = clock-driven; export = deterministic loop n/fps.
  3. Decode scheduler per active clip with a small bounded frame queue (about 4 to 10 frames, mirroring the upscaler's cap of 10), prefetch about 0.5 to 1 s ahead, flush on seek; use low-res proxies and keyframe-only scrubbing when speed matters. Use proxies (short GOP, `keyFrameInterval` of 0.5 to 1 s, 480p/720p) mainly for long-GOP or high-bitrate sources.
  4. Audio: Web Audio graph per track (gain/fades), scheduled from the timeline; master clock = `AudioContext.currentTime`; the video renderer follows the audio clock; mix for export in chunks.
  5. Export: worker + OffscreenCanvas if the renderer can run there (font loading and DOM-dependent code are the risk); Mediabunny `CanvasSource` + audio source + `StreamTarget` to a File System Access handle on Chromium, and an OPFS-backed target (then `getFile()` and download) on Safari/Firefox so output is not forced into RAM [verify per browser whether OPFS `createWritable()` or only worker-side sync access handles are available; the Safari 26.0 notes mention a "File System WritableStream API" without saying where].
  6. Persistence: store media in OPFS (or keep user file handles on Chromium), keep only project JSON in IndexedDB; call `navigator.storage.persist()` and surface Safari eviction risk.
- Cross-origin isolation is only needed if threaded WASM (ffmpeg-mt, threaded whisper.cpp) is used; a WebCodecs + Transformers.js (WebGPU or single-thread WASM) design avoids the COOP/COEP constraint on static hosts.

### Gaps
- No first-party engineering write-ups from Canva, Clipchamp, Kapwing, Descript or Veed were found, so claims about how those editors structure preview/export are not sourced.
- Mediabunny/WebCodecs seek latency numbers for long-GOP sources, and a recommended frame-queue depth for multi-clip compositing, were not found; the "4 to 10 frames" figure is extrapolated from one tool.
- The WebCodecs Fundamentals "Video Editing" pattern page is a stub ("Work in Progress"); its Remotion page says "Coming soon".
- OPFS `FileSystemWritableFileStream` availability per browser (vs. sync access handles) not confirmed from a primary source.

## 5. AI-assisted video features that can run locally (captions, silence removal, beat detection, background removal, auto-reframe)

### Takeaway
Local captions are practical: Whisper-tiny/base via Transformers.js (Apache-2.0 library, MIT model) is about 41 to 207 MB depending on quantisation, runs on WebGPU or WASM, and word-level timestamps are supported in an official example; Parakeet TDT v3 (CC-BY-4.0) is a stronger but much heavier alternative. Silence removal is easy (VAD or energy threshold). Beat detection has a permissive option (web-audio-beat-detector, MIT) and a copyleft trap (Essentia.js, AGPL-3.0). Video background removal and auto-reframe have no turnkey permissive browser library; licences of the best models (RVM GPL-3.0, RMBG-2.0 CC BY-NC, imgly AGPL-3.0) are the main hazard.

### Inferences
- Captions v1: Whisper-base (int8 enc+dec about 77 MB, or fp32-encoder/q4-decoder about 207 MB if quality matters, given the encoder quantisation sensitivity) in a Worker via Transformers.js with `return_timestamps: 'word'`, fall back from WebGPU to WASM; offer tiny (fast) and small (about 250 to 590 MB, optional download) as quality tiers; cache models in Cache Storage/OPFS. Estimated time (from unmeasured RTF claims): a 10-minute video is about 75 to 120 s at base on WebGPU (5 to 8x) and about 200 to 300 s on CPU WASM (2 to 3x) [needs an in-house benchmark]. Feed Whisper 16 kHz mono PCM extracted via Mediabunny audio sinks.
- Parakeet is attractive for accuracy/word timestamps but it is a 600M-parameter model requiring at least 2 GB RAM; defer to v2 and only as WebGPU opt-in.
- Silence removal: either an RMS/threshold analysis on decoded PCM (no model, instant) or Silero VAD through `@ricky0123/vad-web` (npm package ISC, 6.76 MB unpacked including three ONNX model versions; individual model size and the Silero model's own licence were not retrieved) for noisy audio; output a non-destructive list of "silent regions" that the UI turns into splits/ripple deletes.
- Beat markers: use web-audio-beat-detector (MIT, constant tempo) for music-track snapping; do not bundle Essentia.js/its models in a product you do not want to open-source (AGPL, NC-ND).
- Background removal: for a clean-licence v1 use MediaPipe selfie segmentation or MODNet per frame (with temporal smoothing on the alpha), run at preview resolution and upscale; RVM (GPL-3.0), RMBG-2.0 (non-commercial) and imgly (AGPL) are unsuitable for a closed-source commercial product without a licence deal. Treat as post-v1.
- Auto-reframe (16:9 to 9:16): sample frames at about 2 to 5 fps, run MediaPipe face detection, smooth the crop path (e.g. Kalman or exponential smoothing, hold-last on loss), emit as keyframes on the clip transform. This is custom work (about 1 to 2 weeks) and not needed for v1.

- Essentia model licence and the claims of the Essentia licensing page were not verified at source.
- Licence terms of MediaPipe models and `@mediapipe/tasks-vision` were not stated on the fetched pages.

## 6. Scope: what a credible v1 costs, and what to leave out

### Takeaway
A credible v1 (trim, split, multiple tracks, design-editor text/shape overlays, simple transitions, music, voiceover, captions, MP4 export) is, in my estimate, about 22 to 31 focused engineer-weeks for a solo developer at an unassisted pace (roughly 5.5 to 7.5 months), with the preview engine and cross-browser hardening dominating the cost; an MVP slice is about 12 to 14 weeks at that pace. If heavy AI-assisted development cuts effort by 40 to 60% (pure judgement, no data behind the factor) that is roughly 9 to 19 weeks for v1 and 5 to 8 weeks for the MVP. These are estimates, not sourced facts.

### Cited Findings
- Reference points for scale (repo pages): Omniclip (MIT) covers trim/split, text/audio/video/images, undo/redo, transitions, effects, 4K render, project manager, collaboration in 460 commits but lacks audio volume editing, speech-to-text and keyframes; OpenReel 244 commits for a wide feature list; Diffusion Studio engine 179 commits (no UI); FreeCut 2,795 commits ("professional-grade", keyframe graph editor, WebGPU effects, local AI). — [Omniclip](https://github.com/omni-media/omniclip), [OpenReel](https://github.com/Augani/openreel-video), [Diffusion Studio](https://github.com/diffusionstudio/core), [FreeCut](https://github.com/walterlow/freecut)
- FreeCut's maintainers state priorities as bug fixes first, then performance, then new features, and accept no outside PRs; real-GPU effects require a manual release gate. — [FreeCut](https://github.com/walterlow/freecut)
- Katana's author says 4K rendering on a low-end Chromebook is not something he can speed up; Twick recommends server export for long/complex projects. — [Katana](https://katana.video/blog/what-does-katana-actually-do), [Twick](https://github.com/ncounterspecialist/twick)
- Remotion's pricing page places "video editors, prompt-to-video apps" in the Automators tier ($0.01/render, $100/month minimum) and lists Editor Starter as included in the Enterprise tier (from $500/month), whereas the Editor Starter page describes a one-time purchase for individuals/small companies and a Company License for larger ones (the two pages are not fully consistent): a commercial alternative to building the timeline UI. — [remotion.pro/license](https://www.remotion.pro/license), [Editor Starter](https://www.remotion.dev/docs/editor-starter)

### Inferences (all estimates by me; "weeks" = focused full-time engineer-weeks)

## 7. Pitfalls (codec patents and licensing, Safari quirks, memory exhaustion, A/V drift, variable frame rate sources, audio autoplay rules)

### Takeaway
Using the browser's built-in WebCodecs encoders keeps codec-patent licensing with the browser/OS vendor in practice (my reading, not legal advice), whereas shipping your own x264/FDK-AAC/x265 WASM makes you the implementer (and ffmpeg.wasm's core is GPL). The sharpest technical traps are Safari's historical VideoEncoder/VideoDecoder bugs, unbounded VideoFrame retention, and keeping audio and video on one clock; autoplay rules require a user gesture before any AudioContext sound.

### Cited Findings

#### Codec patents and licences
- Via LA AVC/H.264 licence (official page): covers decoders, encoders and combined products; per-unit fees for PC/OEM and OS-embedded products: units 1 to 100,000 $0.00, 100,001 to 5,000,000 $0.20 each, above 5,000,000 $0.10 each; annual enterprise cap $9.75M from 2017; streaming section has tiers (Tier 1 $4.5M, Tier 2 $3.375M, Tier 3 $2.25M, small/nascent $100K per year) and titles of 12 minutes or less $0.00; the page contains no explicit "free internet video" provision and states the actual agreement is the only definitive statement. — [Via LA AVC/H.264](https://www.via-la.com/licensing-2/avc-h%20264/)
- Streaming Media coverage of the 2026 change: Via LA replaced a single annual cap with tiered streaming fees for previously unlicensed implementers from 2026; licensees active at end of 2025 keep their original terms; assessed per legal entity; the article does not say whether free-to-user internet video is exempt. The 2010 MPEG LA statement that internet video free to end users carries no royalty "for the life of the licence" is cited but not confirmed as still applying; a LinkedIn claim that H.264 has been free since 1 Jan 2024 is reported but not endorsed. — [Streaming Media](https://www.streamingmediaglobal.com/Articles/News/Featured-News/H.264-Streaming-Fees-What-Changed-Whos-Affected-and-What-It-Means-173934.aspx)
- Cisco OpenH264: Cisco's prebuilt binary is covered by Cisco's MPEG LA AVC/H.264 licence at no cost to the user under stated conditions, but only for that binary; teams building from source "are responsible for paying all applicable license fees"; Cisco gives no guarantee about other patent holders. — [OpenH264 FAQ](https://www.openh264.org/faq.html)
- AAC: Via LA administers the AAC patent pool (about 1,000 licensees; a March 2026 press release claims over 80% mobile penetration). An old (2017) mailing-list post quoting a Via FAQ says fees are due on sale of encoders/decoders and not on distributing AAC bitstreams; a third-party article gives historic per-unit rates of roughly $0.10 to $0.98; HE-AAC v2 parametric-stereo patents (Dolby/Philips) are outside the pool. [All secondary and/or old; Via's current rate card not retrieved.] — [Via LA HONOR release](https://via-la.com/via-licensing-alliance-welcomes-honor-as-advanced-audio-coding-patent-pool-licensee/), [Icecast list 2017](https://lists.xiph.org/pipermail/icecast/2017-May/013947.html)
- AV1: AOMedia Patent License 1.0 grants a perpetual, worldwide, royalty-free, non-sublicensable licence to necessary claims for implementations (encoder and/or decoder) with defensive termination if a licensee sues over implementations; the text does not mention patent pools such as Sisvel. — [AOMedia patent license](https://aomedia.org/license/patent-license/)
- HEVC: Access Advance announced on 27 Jan 2026 an extension of an HEVC Advance rate-increase deadline (headline only; details not retrieved). — [Business Wire mirror](https://business.mammothtimes.com/mammothtimes/article/bizwire-2026-1-27-access-advance-extends-hevc-advance-rate-increase-deadline)
- ffmpeg.wasm core is GPL-2.0-or-later and built with `--enable-gpl` plus libx264/libx265; FFmpeg's legal page says GPL parts make the GPL apply to all of FFmpeg and FFmpeg gives no patent assurance (see section 2).
- Library licences to watch: Mediabunny MPL-2.0; Remotion custom licence (free up to 3 people); Twick Sustainable Use License; Essentia.js AGPL-3.0; imgly background removal AGPL-3.0; RVM GPL-3.0; RMBG-2.0 CC BY-NC 4.0; WebCut LGPL-3.0 (section 5 and 3 sources).

#### Safari and WebKit quirks (primary release notes)
- WebCodecs audio only from 26.0; hardware VideoDecoder frame-order bug with B-frames fixed in 27.0; VideoEncoder could stall with no output for H.264 Main/High until 27.2; AudioData.copyTo RangeError and NV12 colour-range issues fixed in 27.0; `decodeAudioData` failed for valid AAC/M4A until 27.2 and for MP4 with Opus until 27.0; WebRTC I420 BT709 VideoFrame encoded in the wrong colour space for VP9 until 27.0; IndexedDB fixes in 27.0; WebGPU partial on desktop per caniuse. — [WebKit 26.0](https://webkit.org/blog/17333/webkit-features-in-safari-26-0/), [27.0](https://webkit.org/blog/18325/webkit-features-for-safari-27-0/), [27.2](https://webkit.org/blog/18515/webkit-features-for-safari-27-2/), [caniuse WebGPU](https://caniuse.com/webgpu)
- Safari lacks the File System Access picker API (caniuse), has OPFS since 15.2, applies per-origin LRU eviction and "best-effort" storage unless `persist()` is granted, and AV1 decode only on hardware-capable devices (about 27% macOS / 33% iOS sessions). — [caniuse FS Access](https://caniuse.com/native-filesystem-api), [WebKit storage policy](https://webkit.org/blog/14403/updates-to-storage-policy/), [Codec analysis 2026](https://webcodecsfundamentals.org/datasets/codec-analysis-2026/)

#### Memory exhaustion
- VideoFrames hold GPU memory (one site claims about 24 MB per 4K frame, so about 200 frames on a 5 GB GPU), retaining them until decode stalls reveals driver pool sizes; always `close()` frames and samples; keep decode/encode queues bounded (the reference pipeline caps at 20/10/20). — [reality check](https://webcodecsfundamentals.org/intro/reality-check/), [W3C §13.3](https://www.w3.org/TR/webcodecs/), [upscaler architecture](https://free.upscaler.video/technical/architecture/), [Chrome for Developers](https://developer.chrome.com/docs/web-platform/best-practices/webcodecs)
- Chromium caps a single ArrayBuffer at 2 GB; `BufferTarget` is advised only for outputs under about 100 MB; hour of audio >1 GB decoded. — [file handling](https://webcodecsfundamentals.org/concepts/file-handling/), [writing media files](https://raw.githubusercontent.com/Vanilagy/mediabunny/main/docs/guide/writing-media-files.md), [Web Audio playback page](https://webcodecsfundamentals.org/audio/web-audio/)

#### A/V sync, drift and variable frame rate
- Mediabunny stores timestamps in seconds; `getSample(t)` returns the last sample at or before t (so presentation time, not frame index, drives lookup); output `frameRate` snaps timestamps/durations to a constant rate; `AudioBufferSource` appends buffers sequentially. — [media sinks](https://mediabunny.dev/guide/media-sinks), [writing media files](https://raw.githubusercontent.com/Vanilagy/mediabunny/main/docs/guide/writing-media-files.md), [media sources](https://raw.githubusercontent.com/Vanilagy/mediabunny/main/docs/guide/media-sources.md)
- Packet timestamp rule for remuxing: a video packet must not have a timestamp smaller than the largest timestamp added before the last key frame (B-frame reordering constraint); packets must be added in decode order. — [media sources](https://raw.githubusercontent.com/Vanilagy/mediabunny/main/docs/guide/media-sources.md)
- Remotion's converter explicitly lists "fixing videos recorded with MediaRecorder" as a use case, i.e. MediaRecorder output (which Craftly's current WebM export uses) commonly needs repair. — [Remotion WebCodecs](https://www.remotion.dev/docs/webcodecs)
- Audio-clock approach (position from `AudioContext.currentTime`) described above is the documented way to keep timeline position consistent. — [Web Audio playback page](https://webcodecsfundamentals.org/audio/web-audio/)

#### Audio autoplay
- Programmatic playback of media with audio is generally blocked until the user has interacted with the page; for Web Audio, starting a source node outside a user-input handler is subject to autoplay rules; Firefox pref `media.autoplay.block-webaudio` (default true) means contexts only play after sticky activation; `Permissions-Policy: autoplay` defaults to `self` for iframes. (The usual pattern of resuming a suspended AudioContext from a click handler is standard practice but is not stated on that MDN page.) — [MDN autoplay guide](https://developer.mozilla.org/en-US/docs/Web/Media/Guides/Autoplay)

### Inferences
- Patent exposure (not legal advice): relying on `VideoEncoder`/`AudioEncoder` means the encoder is the browser's or OS's; shipping x264 (GPL), x265, FDK-AAC or a WASM AAC polyfill makes Craftly the distributor of an implementation, which is where Via LA / Access Advance / OpenH264 "build from source" language applies. Preferred policy: native WebCodecs only; fall back to Opus/VP9 (WebM) where H.264/AAC are not available; if a WASM fallback is ever added, get a legal read first. The 2026 Via LA streaming fees target streaming services; whether a free browser tool that only exports files is in scope is unresolved in the sources.
- Safari: require/recommend 27.2+ for H.264 export, add a startup probe that encodes 10 frames with the chosen profile/level and a watchdog timeout (the bug mode was a silent stall with no output), prefer Baseline/Constrained High if Main/High stall on older versions, and avoid `decodeAudioData` for MP4/AAC/Opus on old versions (decode via WebCodecs `AudioDecoder` through Mediabunny instead).
- Memory: design the preview and export around bounded queues from day one; budget on RGBA frame size for canvas copies; enforce a per-clip decoder budget (open/close decoders as clips enter/leave the playhead window) and a global cap on live VideoFrames.
- VFR: normalise by always sampling by presentation time at timeline fps (the `getSample(t)` contract does this) rather than by frame index; at export, give Mediabunny the target `frameRate` so timestamps are snapped; handle rotation metadata; test with phone screen recordings and mixed-fps clips. (VFR behaviour of phone footage is general knowledge; not source-verified in this research.)
- A/V drift: video follows the audio clock in preview; in export, derive audio from the same timeline math and verify the muxed duration of audio vs video; insert explicit silence rather than relying on sequential `AudioBufferSource` appends where clips have gaps.
- Autoplay: create/resume the AudioContext inside the first Play/Record click; show a "click to enable sound" state when `ctx.state === 'suspended'`; voiceover capture needs a user gesture plus `getUserMedia` permission.
- Replace MediaRecorder for video exports: WebCodecs/Mediabunny output has proper duration/cues and frame-accurate timing, avoiding the repair step that Remotion lists as a use case.

### Gaps
- No primary source for current Via LA AAC rates or for whether browser-based tools that call platform encoders owe anything; no source for HEVC pool terms (article not retrievable); the Tom's Hardware report on the 2026 H.264 streaming fees timed out (Streaming Media and Via LA's own page were used instead); legal advice needed before shipping any bundled encoder.
- Variable frame rate behaviour and A/V drift in WebCodecs were not covered by any fetched source beyond API semantics; no benchmark of drift over long exports.
- Chrome/Firefox-specific encoder quirks beyond the Firefox Bugzilla list were not researched.

## 8. Comparison of approaches: pure WebCodecs pipeline vs ffmpeg.wasm vs local server / desktop wrapper (Electron, Tauri)

### Takeaway
For a static-hosted, no-backend editor the WebCodecs + Mediabunny path is the clear default: hardware-accelerated, small (Mediabunny tree-shakes to kilobytes versus about 31 MB per ffmpeg.wasm core), and licence-clean (MPL-2.0 versus a GPL core). ffmpeg.wasm only makes sense as a lazy-loaded compatibility fallback. A desktop wrapper (Tauri/Electron) is a later option when you need native FFmpeg/hardware encoders, >1080p or very long videos, but it changes distribution, licensing and the "static files" principle.

### Inferences
- Recommendation: build v1 on WebCodecs + Mediabunny; do not ship ffmpeg.wasm in v1. If a fallback is needed for browsers without WebCodecs encoders (e.g. Firefox Android), prefer degraded behaviour (existing MediaRecorder WebM/GIF export) over a 31 MB GPL core.
- Electron bundles its own Chromium, so WebCodecs availability would be consistent across OS, but whether Electron's Chromium includes H.264/AAC encoders was not verified here; test with `VideoEncoder.isConfigSupported({codec:'avc1.42001f', ...})` before relying on it. Tauri's embedded system webviews inherit the platform's WebCodecs/codec support (Windows via WebView2 is closest to desktop Chrome; macOS WKWebView follows the installed macOS/Safari version, so Safari 26/27 bugs apply on older macOS; Linux WebKitGTK is the least predictable).
- A wrapper is justified only if requirements move beyond what browsers expose: 4K/HEVC/ProRes export, multi-hour sources, native hardware encoders, or filesystem-native workflows. Because Craftly is already a static web app, the same codebase can later be wrapped in Tauri/Electron with an FFmpeg sidecar for "pro export" without a rewrite; FFmpeg distribution then triggers the GPL/LGPL and patent considerations in section 7.
- A "local server" (user runs FFmpeg behind localhost) contradicts the static, no-backend design and adds install friction; it is dominated by the desktop-wrapper option.

### Gaps
- No independent benchmark of WebCodecs vs ffmpeg.wasm vs native (all comparisons are self-reported or from 2023); no Electron-specific codec or licensing source was fetched.
- Tauri sidecar mechanics, WebKitGTK WebCodecs support and macOS WKWebView WebCodecs availability by OS version were not verified.
- Memory/time for long (multi-hour) projects in browser vs native was not measured in any source.
