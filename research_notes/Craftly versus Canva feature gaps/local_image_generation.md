> Method notes (read first)
> - Research date 2026-11-05. "GB/MB" are decimal (1 GB = 1,000,000,000 bytes) unless a source says otherwise. File sizes come from Hugging Face `api/models/<repo>/tree/main?recursive=true` JSON (exact byte counts), so they are reliable for the fetch date.
> - Narrative facts (licences, speeds, features) were extracted from pages by a fetch-time summariser; "not stated" means not found in the fetched text, not proof of absence upstream. Licence readings are plain-text readings, not legal advice.
> - WebSearch hit a shared per-turn budget limit after about 27 successful searches. Remaining gaps were closed by fetching primary pages directly (HF model cards/APIs, GitHub, vendor docs). About 140 tool calls were used because the scope has eight sub-questions.
> - Tags: [vendor] = claim by the model/tool author; [secondary] = blog/aggregator quoting someone else; [snippet] = only seen in a search-result snippet, page not opened; [low] = SEO/forum-grade number. Numbers without a tag come from the primary page/API named in the link.
> - Sibling note `local_image_editing_models.md` (same folder) covers in-browser ORT Web / Transformers.js / WebNN runtime internals, background removal, SAM, LaMa and upscalers in depth; this note only references them where they touch image generation.

## 1. In-browser text-to-image (WebGPU / WASM): models, sizes, speed, quality, browser support

### Takeaway
Only a few text-to-image models are verified to run inside a web page in Nov 2026: SD-Turbo (ORT Web, 512x512 fixed, 1 step, 2.58 GB fp16 ONNX; "within one second" on an RTX 4090), Janus-Pro-1B (Transformers.js, 1.94 GB q4f16) and Microsoft's Z-Image-Turbo ONNX (Q4F16, ~6 GB, Apache-2.0; a Sept 2026 WebXPRT 5 workload quotes "about five minutes" per 4-image run on "late-model, high-performance" machines). I found no browser builds of FLUX schnell, SANA or Qwen-Image, and the common SD-Turbo ONNX weights carry a non-commercial licence file. WebGPU itself is now about 87% global (caniuse) but Firefox and Safari are only partially on by default.

### Cited Findings

#### WebGPU availability (Nov 2026)

- web.dev (2025-11-25): WebGPU "officially supported across Chrome, Edge, Firefox, and Safari". Chrome/Edge 113 on Windows (D3D12), macOS, ChromeOS; Chrome 121 on Android 12+ with Qualcomm/ARM GPUs; Firefox 141 on Windows; Firefox 145 on ARM64 Macs running macOS Tahoe 26; Safari 26 on macOS Tahoe 26, iOS 26, iPadOS 26, visionOS 26. Linux, Firefox Android and Intel Macs still "in progress". — [web.dev](https://web.dev/blog/webgpu-supported-major-browsers)
- gpuweb Implementation Status wiki: Android Imagination GPUs need Android 16+ (Chrome 139); Linux Intel Gen12+ since Chromium 144, NVIDIA (driver 535.183.01+) on Wayland since 147, other Linux behind `--enable-unsafe-webgpu`; Windows ARM64 behind a flag; Firefox "147 on all macOS versions"; Firefox Linux Nightly only (Mozilla expects 2026); Firefox Android behind `gfx.webgpu.ignore-blocklist`; Safari 26 enabled by default on macOS/iOS/iPadOS/visionOS. — [gpuweb wiki](https://github.com/gpuweb/gpuweb/wiki/Implementation-Status) (conflicts mildly with web.dev on Firefox macOS: ARM64-Tahoe-only at 145 vs all macOS at 147).

#### Models verified to run in a web page
- **SD-Turbo via ONNX Runtime Web + WebGPU** (distilled from SD 2.1): Microsoft's Feb 2024 post says WebGPU (ORT 1.17) made it practical with results "within one second on an RTX 4090"; fp16 WebGPU support arrived with Chrome/Edge 121. — [Microsoft Open Source Blog](https://opensource.microsoft.com/blog/2024/02/29/onnx-runtime-web-unleashes-generative-ai-in-the-browser-using-webgpu/)
- SD-Turbo ONNX files (`schmuell/sd-turbo-ort-web`, the repo the MS example loads): `unet/model.onnx` 1,733,430,199 B (1.73 GB), `text_encoder/model.onnx` 681 MB, `vae_decoder` 99 MB, `vae_encoder` 68 MB, total 2,583,948,499 B = 2.58 GB. — [HF API tree](https://huggingface.co/api/models/schmuell/sd-turbo-ort-web/tree/main?recursive=true); example README calls it "a research oriented model to study small, distilled text-to-image models" and uses ORT Web with WebGPU — [onnxruntime-inference-examples/js/sd-turbo](https://github.com/microsoft/onnxruntime-inference-examples/tree/main/js/sd-turbo)
- SD-Turbo model facts: 0.9B params, "preferably 512x512", 1-4 steps (one step "sufficient"); SDXL-Turbo: fixed 512x512, "cannot render legible text", faces/people "may not be generated properly". — [sd-turbo card](https://huggingface.co/stabilityai/sd-turbo), [sdxl-turbo card](https://huggingface.co/stabilityai/sdxl-turbo)
- **LICENCE TRAP for SD-Turbo web weights**: the `schmuell/sd-turbo-ort-web` repo's LICENSE file is the "Stability AI Non-Commercial Research Community License Agreement" dated Nov 28, 2023 (no production use; no hosted/API use enabling third parties) — [LICENSE](https://huggingface.co/schmuell/sd-turbo-ort-web/raw/main/LICENSE). The official `stabilityai/sd-turbo` LICENSE.md is the "Stability AI Community License Agreement" (last updated July 5, 2024): free commercial use under US$1,000,000 annual revenue (incl. affiliates), registration with Stability required, "Powered by Stability AI" attribution when distributing — [LICENSE.md](https://huggingface.co/stabilityai/sd-turbo/raw/main/LICENSE.md). SDXL-Turbo's card lists licence `sai-nc-community` and points commercial users to stability.ai/license — [card](https://huggingface.co/stabilityai/sdxl-turbo).
- **Janus-Pro-1B via Transformers.js** (autoregressive image generator): ONNX repo `onnx-community/Janus-Pro-1B-ONNX` q4f16 set totals 1,941.57 MB (language_model 698 MB, prepare_inputs_embeds 597 MB, embed_tokens 419 MB, lm_head 118 MB, image_decode 85 MB, gen_head 21 MB, gen_img_embeds 2.7 MB); fp16 set totals 4.52 GB. — [HF API tree](https://huggingface.co/api/models/onnx-community/Janus-Pro-1B-ONNX/tree/main?recursive=true). Licence: code MIT, model under the DeepSeek Model License (card does not state commercial terms). — [Janus-Pro-1B card](https://huggingface.co/deepseek-ai/Janus-Pro-1B)
- `web-txt2img` (MIT) wraps SD-Turbo (ORT Web, 512x512, best-effort seed, "seed determinism not guaranteed across hardware or drivers") and Janus-Pro-1B (no size or seed controls, WebGPU-only because of "heavy shader workloads and memory usage"); weights go to Cache Storage; one model loaded at a time; WASM fallback "experimental and not recommended for production". — [lacerbi/web-txt2img](https://github.com/lacerbi/web-txt2img)
- **Z-Image-Turbo (6B) ONNX for ORT Web/WebGPU/WebNN**: `lwanming/Z-Image-Turbo-opt`, Apache-2.0. Pipeline: text encoder Q4F16, transformer Q4F16, scheduler-step FP16, VAE decoder FP16, plus an FP16 safety checker. Files: text encoder 2.219 GB (`.onnx` 58 MB + data 2.036 GB + data_1 124 MB), transformer 3.670 GB (130 MB + 2.032 GB + 1.508 GB), VAE decoder 99 MB, safety checker 0.608 GB; `onnx/` total 6,596,033,667 B = 6.60 GB (core generation path = 5.99 GB without the safety checker). — [HF card](https://huggingface.co/lwanming/Z-Image-Turbo-opt), [HF API tree](https://huggingface.co/api/models/lwanming/Z-Image-Turbo-opt/tree/main?recursive=true). Microsoft's live demo exposes 512x512 and 1024x1024, Load/Execution/Fetch/Create and per-stage (text encoder, transformer, VAE, safety checker) timers, and a "Release memory after leaving" option, but the timing fields were blank in the fetched static page. — [WebNN Developer Preview demo](https://microsoft.github.io/webnn-developer-preview/demos/z-image-turbo/)
- WebXPRT 5 experimental workload (Principled Technologies, 2026-09-10): browser text-to-image with Z-Image-Turbo (6B, Apache-2.0) through ORT Web / Transformers.js on WebGPU ("the best path"; WebNN "still maturing"); download "just under 6 GB" on first run, "5 to 20 minutes" depending on connection; "each run may take about five minutes" (one warm-up image + three scored images); "will best suit late-model, high-performance laptops and desktops"; no resolution, steps or results published. — [PT BenchmarkXPRT blog](https://www.principledtechnologies.com/benchmarkxprt/blog/?p=5567)
- Microsoft WebNN Developer Preview repo lists SD 1.5, SD-Turbo and SDXL-Turbo demos; needs Windows 11 21H2+ (DirectML), Edge/Chromium Canary with the `webnn` flag (known compatible Chromium 136.0.7051.0); claims for SD-Turbo "you can generate an image in 2s on AI PC devices". — [microsoft/webnn-developer-preview](https://github.com/microsoft/webnn-developer-preview)
- MLC `web-stable-diffusion` (SD v1-5 compiled with TVM Unity): needs WebGPU via Chrome Canary with `--enable-dawn-features=disable_robustness`, "a GPU with a decent amount of RAM (8GB)", FP32 only, tested on Apple silicon (about 3x slower than native without the flag), Apache-2.0; no absolute timings or download size published. Treat as historical. — [mlc-ai/web-stable-diffusion](https://github.com/mlc-ai/web-stable-diffusion)

#### Negative results (what I could not find)
- SANA's repo lists PyTorch, diffusers, ComfyUI, SGLang, Cosmos-RL and no browser/ONNX/WebGPU support (SANA-Sprint is "0.1s per 1024px image on H100, 0.3s on RTX 4090" natively). — [NVlabs/Sana](https://github.com/NVlabs/Sana)
- HF model search for "webgpu" sorted by downloads (top 25) returned background-removal, speech, LLM and VLM models and no text-to-image model. — [HF API search](https://huggingface.co/api/models?search=webgpu&sort=downloads&limit=25). A `filter=transformers.js&pipeline_tag=text-to-image` query returned an empty list. — [HF API](https://huggingface.co/api/models?filter=transformers.js&pipeline_tag=text-to-image&sort=downloads&limit=25)
- No quantized FLUX.1 schnell, Qwen-Image or SANA browser demo was found (one targeted search for FLUX schnell/SANA/Z-Image WebGPU returned only Janus-Pro results — search snippet).

### Inferences
- Realistic zero-install tiers: (a) "Light": SD-Turbo-class 512x512, 1 step, 2.6 GB download, about 1-2 s on strong GPUs/NPUs per Microsoft's own demos, but licence handling needed (see gaps); (b) "Quality": Z-Image-Turbo ONNX, ~6 GB, Apache-2.0, 1024x1024 capable, but PT's own estimate (~5 min for 4 images including load) implies tens of seconds to about a minute per image even on a good laptop (derived, uncertain).
- Because defaults are 128 MB per storage-buffer binding, any ORT pipeline must request adapter limits; low-end iGPUs may fail at `requestDevice` (not directly verified).
- Safari path: WebGPU is on by default only on macOS 26+/iOS 26+, so Safari users on older macOS get no in-browser generation; and (section 2) Safari also blocks https-to-http-localhost, so Mac+Safari users are the group for whom in-browser is the only local option.
- A Hugging Face or CDN download of 2.6-6 GB counts as "distribution" for licence purposes if Craftly points browsers at it; plan for NOTICE/attribution UI (not legal advice).
- Mobile: iOS 26 Safari and Android Chrome expose WebGPU, but 2.6-6 GB weights plus mobile tab-memory limits make the generation path impractical (memory limits not verified here).

### Gaps
- No verified seconds-per-image for in-browser SD-Turbo/Z-Image on Apple M-series, Intel iGPU, RTX 3060 or typical laptops; only the three anchors above (<1 s RTX 4090, ~2 s "AI PC" via WebNN, ~5 min per 4-image WebXPRT run).
- GPU memory needed by the Z-Image ONNX pipeline and by SD-Turbo in WebGPU is not published in any fetched source.
- Visible quality of the browser models is only described by model cards (no independent evaluation found); Janus-Pro-1B output resolution (commonly stated as 384x384) was not confirmed from the fetched card.
- Which of the SD-Turbo ONNX copies (if any) is cleanly licensed for redistribution through a commercial app was not resolved; SDXL-Turbo is non-commercial per its HF licence tag.
- Transformers.js v4 status and ORT Web large-model limits: see the sibling note `local_image_editing_models.md` section 7 (not re-verified here).

## 2. Local servers a user already runs (ComfyUI, A1111/Forge, InvokeAI, stable-diffusion.cpp, Draw Things, Ollama, LM Studio, Fooocus) and how a static https page talks to localhost

### Takeaway
stable-diffusion.cpp's server is the easiest backend for a static page (OpenAI-style, A1111-style and a native async job API with preview and cancel; it reflects any `Origin`, so no CORS flag), while ComfyUI is the most capable (every new model lands there) but returns 403 to a cross-site page unless started with `--enable-cors-header`. Chrome (142+) gates https-to-localhost behind a `loopback-network` permission prompt, Firefox 151+ is rolling out a similar prompt, and Safari blocks https-to-http-localhost as mixed content. Ollama image generation is still macOS-only with no documented API, and LM Studio has no native diffusion.

### Cited Findings

#### Per-server capabilities
- **stable-diffusion.cpp (MIT)** — backends CPU (AVX/AVX2/AVX512), CUDA, Vulkan, Metal, OpenCL, SYCL; weights ckpt/safetensors/GGUF; model list includes SD1.x/2.x/Turbo, SDXL(+Turbo), SD3/3.5, FLUX.1 dev/schnell/Kontext-dev, FLUX.2 dev/klein, FLUX.3 Image Klein (Day-0 2026-10-16), Chroma, Qwen Image and Qwen Image 2.1 (Day-0 2026-09-20), Qwen Image Edit series, Z-Image, Krea2 (2026-06-25), Ideogram4 (2026-06-04), LongCat, PixArt, Ovis-Image, Wan/LTX video; ControlNet only "with SD 1.5"; ESRGAN upscaling; PhotoMaker; LoRA; IP-Adapter (SD1.5/SDXL). — [README](https://raw.githubusercontent.com/leejet/stable-diffusion.cpp/master/README.md)
- sd.cpp server API (`examples/server/api.md`): OpenAI `POST /v1/images/generations` (prompt, n, size `WxH`, output_format, response `data[].b64_json`), `POST /v1/images/edits` (multipart `image[]`, `mask`), `GET /v1/models`; A1111-style `POST /sdapi/v1/txt2img` (prompt, negative_prompt, width, height, steps, cfg_scale, seed with -1 = random, batch_size, lora, hires fields), `POST /sdapi/v1/img2img` (+ init_images, mask, inpainting_mask_invert, denoising_strength clamped 0..1), `GET /sdapi/v1/progress` (progress, state, `current_image` latent-projection JPEG, eta_relative), `/sdapi/v1/upscalers|loras|samplers|schedulers|sd-models|options`; native async `POST /sdcpp/v1/img_gen` (negative_prompt, seed, sample_params, init_image, ref_images, mask_image, control_image, ip_adapter_image, lora array, hires, preview, output_format) returning 202 with `id` and `poll_url`; `GET /sdcpp/v1/jobs/{id}` (states queued/generating/completed/failed/cancelled; `preview` = pass, step, total_steps, b64 image), `POST /sdcpp/v1/jobs/{id}/cancel`, `POST /sdcpp/v1/upscale` (image, upscaler, repeats 1-4, tile_size), `GET /sdcpp/v1/capabilities`, model load/unload endpoints. `<lora:...>` prompt tags are not parsed. — [api.md](https://raw.githubusercontent.com/leejet/stable-diffusion.cpp/master/examples/server/api.md)
- sd.cpp server CORS: the pre-routing handler sets `Access-Control-Allow-Origin` to the request's `Origin` (fallback `*`), `Access-Control-Allow-Headers: *`, and answers OPTIONS with 204; no authentication/API-key option appears in `main.cpp`. — [main.cpp](https://raw.githubusercontent.com/leejet/stable-diffusion.cpp/master/examples/server/main.cpp)
- sd.cpp release `master-1050-58bb3c1` (2026-11-04): win-cuda12 362.11 MB (+ `cudart` 563.45 MB), win-vulkan 29.84 MB, win-cpu 18.10 MB, win-rocm 265.88 MB, macOS arm64 37.73 MB, Linux Vulkan 41.64 MB, Linux ROCm 298.23 MB. — [GitHub releases API](https://api.github.com/repos/leejet/stable-diffusion.cpp/releases/latest)
- **ComfyUI (GPL-3.0)** — Desktop app (Windows and macOS), Windows portable (NVIDIA 20-series+; separate CUDA 12.6 build for 10-series; Python 3.13, torch CUDA 13.0; AMD and Intel portables), `comfy-cli`; supports Flux.2, Z-Image, Qwen Image, HunyuanImage 2.1; edit models Flux.2 Klein and Qwen Image Edit; "as low as 4GB vram + 8GB ram". — [README](https://github.com/comfyanonymous/ComfyUI)

#### Browser-to-localhost mechanics (https page to http://127.0.0.1)
- Chrome Local Network Access (LNA): Chrome blog (June 2025, updated 2025-09-29) says the prompt "is launching in Chrome 142"; it gates `fetch()`, subresource loads and subframe navigations from public origins to local/loopback; secure contexts only; initial scope excluded WebSockets/WebTransport/WebRTC; test flag `chrome://flags#local-network-access-check` = "Enabled (Blocking)"; enterprise policy planned. — [Chrome blog](https://developer.chrome.com/blog/local-network-access)
- Current Chrome guidance: two permissions, `local-network` (RFC1918/link-local/ULA/.local) and `loopback-network` (127.0.0.1, ::1, localhost, from public or local origins); a page served from `http://localhost` does not trigger checks; permission is "denied automatically in insecure (`http://`) top-level contexts"; query with `navigator.permissions.query({name:'loopback-network'})` (states granted/prompt/denied), trigger the first request from a user gesture, never from a Service Worker; do NOT query `local-network-access` ("can crash older Chrome versions"); `fetch(url,{targetAddressSpace:'loopback'})` exempts the request from mixed-content blocking and makes Chrome verify the resolved IP (mismatch = TypeError); `ws://` to loopback is exempt from mixed content; CORS still applies; the old Private Network Access preflight headers are deprecated; cross-origin iframes need `allow="local-network; loopback-network"`; dev testing via the `--ip-address-space-overrides` flag or Site settings (Ask/Allow/Block). — [Chrome LNA guidance](https://developer.chrome.com/docs/modern-web-guidance/guides/security/local-network-access)
- Chrome 145 split the single permission into `local-network` and `loopback-network` (old name kept as alias) — [blink-dev Intent to Ship, search-result snippet; page not opened](https://groups.google.com/a/chromium.org/g/blink-dev/c/Zl3P6NHhMBw). MDN documents `Request.targetAddressSpace` for the same purpose — [MDN](https://developer.mozilla.org/en-US/docs/Web/API/Request/targetAddressSpace) [snippet].
- Firefox 151 (released 2026-05-19) release notes: "Local network access restrictions are now rolling out to all users"; "Firefox requires websites to request permission before connecting to devices on your local network"; previously limited to Enhanced Tracking Protection "Strict"; progressive rollout. — [Firefox 151 release notes](https://www.firefox.com/en-US/firefox/151.0/releasenotes/?redirect_source=mozilla-org). Mozilla's support article (snippet only; page failed to load when fetched) says the prompt covers other apps/services on the device or network and the pref `network.lna.blocking` defaults to true — [Mozilla support](https://support.mozilla.org/en-US/kb/control-personal-device-local-network-permissions-firefox) [snippet].
- Safari: WebKit bug 171934 "Don't treat loopback addresses (127.0.0.0/8, ::1/128, localhost, .localhost) as mixed content" is still status NEW; last visible comment 2023-06-29; a 2021 Apple comment ties any exemption to also mitigating localhost access from non-localhost HTTP pages. — [WebKit bug 171934](https://bugs.webkit.org/show_bug.cgi?id=171934). A WebKit 2024 bug (281149) reportedly says WebKit's MixedContentChecker treats localhost as insecure unless loaded over HTTPS, with 2026 comments saying related bugs remain open [snippet] — [bug 281149](https://bugs.webkit.org/show_bug.cgi?id=281149). A Stack Overflow thread summary says Chrome and Firefox allow http://localhost fetches from https pages while Safari blocks them [snippet; 2023 mirror] — [thread mirror](https://kaweah.freedombox.rocks/kiwix/stackoverflow.com_en_all_2023-11/questions/66689081/localhost-http-accessed-from-https-webpage-why-no-mixed-content-error).
- CORS "recipe" per server: ComfyUI `--enable-cors-header https://<craftly-origin>`; A1111/Forge `--api --cors-allow-origins=https://<craftly-origin>`; InvokeAI `allow_origins: ["https://<craftly-origin>"]`; sd.cpp server none (reflects Origin). Sources above.

#### Security caveats evidenced in the fetched sources
- ComfyUI itself blocks cross-site and Host/Origin-mismatched requests by default (403) — i.e. the project treats "any website can hit localhost" as a real threat; enabling `--enable-cors-header *` with `Allow-Credentials: true` removes that protection. — [server.py](https://raw.githubusercontent.com/comfyanonymous/ComfyUI/master/server.py)
- sd.cpp's server reflects any Origin and has no auth option; the only gate in browsers without LNA (Safari, older Chrome/Firefox) is that the user runs it on 127.0.0.1. — [main.cpp](https://raw.githubusercontent.com/leejet/stable-diffusion.cpp/master/examples/server/main.cpp)
- Fooocus UI is unauthenticated by default and `--share` publishes it on gradio.live; A1111 `--share` and `--listen` likewise widen exposure, while `--api-auth` adds basic auth. — [Fooocus](https://github.com/lllyasviel/Fooocus), [A1111 CLI wiki](https://github.com/AUTOMATIC1111/stable-diffusion-webui/wiki/Command-Line-Arguments-and-Settings)
- sd.cpp accepts pickle-based `.ckpt/.pth/.pt` as well as safetensors/GGUF (pickle files can execute code when loaded; this risk statement is background knowledge, not from the source). — [README](https://raw.githubusercontent.com/leejet/stable-diffusion.cpp/master/README.md)

### Inferences
- Connection UX that works on Chrome/Edge/Firefox: probe on a user click, `targetAddressSpace:'loopback'`, catch TypeError, show a per-server CORS snippet, and always use `127.0.0.1` rather than `localhost` (avoid IPv6/DNS ambiguity). Default ports to probe: 8188 ComfyUI, 7860 A1111/Forge/Draw Things(claimed), 9090 InvokeAI, sd.cpp user-chosen (README example shows 1234).
- Safari users cannot reach an http localhost server from an https Craftly (mixed content) unless the server speaks https with a certificate the browser trusts (ComfyUI supports `--tls-keyfile/--tls-certfile`), or Craftly is served over http from localhost, or Craftly is wrapped in a desktop shell that makes requests natively (not verified here).
- The LNA prompt is per-origin and not a security boundary against XSS: an XSS on Craftly's origin could drive a user's local server after consent. Keep user-generated HTML/SVG sandboxed and keep tokens/CORS allow-lists as tight as the server allows.
- For a "managed engine" Craftly would have to add what sd.cpp lacks: a per-session bearer token (reverse proxy or wrapper), CORS pinned to Craftly's origin, and 127.0.0.1-only bind.
- Ollama and LM Studio should not be first-class targets in 2026: Ollama's image path is macOS-only with no documented API; LM Studio has no diffusion.

### Gaps
- InvokeAI's HTTP/WebSocket API surface (FastAPI/OpenAPI + socket.io is background knowledge, not verified); whether Forge Neo keeps the full `/sdapi/v1` surface (README only says `--api` links to the A1111 wiki).
- Draw Things' official HTTP API documentation (port, endpoints, CORS) was not reachable; only third-party descriptions.
- Whether Ollama has since shipped Windows/Linux image generation or an API: model page still says macOS-only as of the fetch; release notes not checked.
- Safari 26/27 actual behaviour for https-to-localhost was not tested; WebKit bugs are the only evidence. Firefox's treatment of loopback specifically (vs "local network") is from a snippet.
- No ComfyUI/Forge/Invoke CVE or custom-node malware research (search budget exhausted); sd.cpp's `.ckpt` pickle risk is an unsourced background claim.

Qwen-Image-2.1: "improved typography" with 2048x2048 neon-sign example (no benchmark in card) — [HF card](https://huggingface.co/Qwen/Qwen-Image-2.1).
- Editing-capable open models: FLUX.2 klein 4B/9B (multi-reference), FLUX.3 klein (10 refs, bbox), Qwen-Image-Edit-2511 (Apache-2.0), Qwen-Image-2.1 (NC), HunyuanImage-3.0-Instruct (3 refs), FLUX.1 Kontext dev (NC), Fibo Edit Turbo (NC; mentioned on Fibo card). Sources as above.

### Inferences
- For a product that must stay commercially clean, default presets should be limited to Apache/MIT checkpoints: Z-Image-Turbo (speed, bilingual text), FLUX.2 klein 4B (editing + references), Qwen-Image / Qwen-Image-Edit-2511 (heavy, 20B, best for 24 GB cards), FLUX.1 schnell (legacy, large).
- Weights size is the practical gate: derived bundles (decimal GB) — Z-Image-Turbo GGUF Q4_K 3.86 + Qwen3-4B Q4_K_M 2.50 + VAE ~0.34 = ~6.7 GB; same with Q2_K 2.59 + Q2_K text encoder 1.67 + VAE = ~4.6 GB; FLUX.2 klein 4B GGUF Q4_0 2.46 + Qwen3-4B Q4_K_M 2.50 + VAE 0.17 = ~5.1 GB; FLUX.3 klein fp8 6.27 + TE 8.88 + VAE 0.34 = ~15.5 GB (text encoder is not quantised in the HF repo); Qwen-Image Q4_K_M 13.07 + 16.58 bf16 text encoder = ~29.7 GB unless a GGUF/fp8 encoder is used.
- Many "Turbo/Lightning" releases target 4-8 steps, which is what makes 8-12 GB GPUs viable; the 20B-class models are realistically 24 GB-card (or heavy-offload) territory.
- Per-device speed ordering that the evidence supports: klein 4B (4 steps) and Z-Image-Turbo (8 steps) >> SDXL-Lightning on small GPUs >> FLUX.3 klein (16 steps) >> Qwen-Image (even with Lightning LoRA).
- Because licence terms differ by revenue and territory, Craftly should display a licence badge per preset and avoid auto-downloading NC models into a commercial user's workflow without a prompt.

### Gaps
- No measured SDXL/FLUX.1/FLUX.2 timings on RTX 3060, 4070 and 4090 from a controlled source (search budget ran out); the Z-Image numbers are SEO-grade and conflicting; the FLUX.3 klein RTX 4070 figure is second-hand.
- SD 3.5 / SDXL OpenRAIL++-M licence texts were not read; "OpenRAIL++ permits commercial use subject to use restrictions" is background knowledge and the SDXL card's "research purposes only" wording is ambiguous.
- Licences/terms not retrieved: SANA weights, PixArt, Lumina-Image 2.0, LongCat-Image, OmniGen2, Ovis-Image, P-H3-Image, Anima, Qwen-Image-2.1's separate Turbo licence text (the card says Qwen Research License), Krea 2 licence text.
- HiDream-I1 VRAM and steps; HunyuanImage 3.0 GPU requirements; FLUX.2 dev bf16/fp8/4-bit VRAM; Qwen-Image-Edit VRAM were not stated in fetched sources.
- Text-rendering quality ranking across models is not independently verified; only card claims and one community quote.
- The FLUX.3 klein licence was read from the HF model-card summary, not the full licence PDF (check bfl.ai/licensing before relying on the US$5M threshold).

## 4. CPU-only and low-end hardware: realistic expectations

### Takeaway
Without a usable GPU, expect sketch-quality 512x512 images from 1-step distilled models in roughly 2-35 s on a tuned desktop CPU and minutes for classic SD1.5; modern 6-12B models are impractical on CPU. With a 4-6 GB NVIDIA GPU, quantised Z-Image-Turbo (2.6-3.9 GB GGUF) or SDXL-Lightning-class models are the realistic ceiling. Steam's Oct 2026 top GPUs are mostly 8-12 GB-class cards (RTX 3060/5070/4060/3050/5060), so 8 GB is the design point for a "local server" tier.

### Cited Findings
- Steam Hardware Survey (October 2026) top GPUs: RTX 3060 3.78%, RTX 5070 3.78%, RTX 4060 Laptop 3.60%, RTX 4060 3.51%, RTX 3050 3.25%, RTX 5060 3.15%, RTX 5060 Ti 2.70%, RTX 5060 Laptop 2.68%, GTX 1650 2.44%, RTX 4060 Ti 2.30% (VRAM buckets and OS shares not in the fetched page). — [Steam survey](https://store.steampowered.com/hwsurvey/videocard/)
- FastSD CPU (Intel Core i7-12700, 512x512, 1 step): SD-Turbo PyTorch 7.8 s, OpenVINO 5 s, OpenVINO + TAESD 1.7 s; SDXS-512-0.9 PyTorch 4.8 s, OpenVINO 3.8 s, OpenVINO + TAESD 0.82 s [snippet of the project README]. — [rupeshs/fastsdcpu](https://github.com/rupeshs/fastsdcpu)
- One Reddit report (HP EliteBook laptop, stable-diffusion.cpp): SD 2.1 Turbo 512x512 in 31 s; SD1.5 20 steps 155 s using 14 GB memory; SDXL-Turbo 1 step 35 s [snippet; single unverified post]. — [Reddit snapshot](https://reddit.sentinel-team.org/posts/1rin2js/snapshots/2026-03-02T18%3A12%3A19.790243Z)
- Fooocus (SDXL): minimum 4 GB VRAM on RTX 2xxx/3xxx/4xxx, 8 GB on GTX 1xxx and AMD, 8 GB RAM minimum and system swap required; CPU-only "32GB RAM ... about 17x slower than an RTX 3XXX". — [Fooocus README](https://github.com/lllyasviel/Fooocus)
- Fooocus SDXL timings on small GPUs (1152x896): RTX 3050 6GB laptop "Speed" preset 38.0 s, LCM-style Extreme Speed 11.5 s, Lightning 9.5 s, Hyper-SD 10.2 s; RTX 2070 Super 8GB 27.4 / 7.5 / 6.1 / 6.8 s. — [TechTactician](https://techtactician.com/best-gpu-for-stable-diffusion-sdxl-and-flux/)
- Krita AI Diffusion: recommends an NVIDIA card with at least 6 GB VRAM; CPU "works but is very slow". — [Acly/krita-ai-diffusion](https://github.com/Acly/krita-ai-diffusion)
- ComfyUI "as low as 4GB vram + 8GB ram"; sd.cpp: Z-Image on "GPUs with 4GB of VRAM — or even less" (GGUF Q2_K 2.59 GB, Q3_K 3.14 GB, Q4_K 3.86 GB). — [ComfyUI README](https://github.com/comfyanonymous/ComfyUI), [sd.cpp z_image.md](https://raw.githubusercontent.com/leejet/stable-diffusion.cpp/master/docs/z_image.md), [HF GGUF list](https://huggingface.co/api/models/leejet/Z-Image-Turbo-GGUF/tree/main?recursive=true)
- Platform reach: ComfyUI's Windows portable is NVIDIA-first (20-series+, torch CUDA 13.0) with separate AMD and Intel portables; Forge Neo pins `torch==2.14.0+cu130`; the Krita plugin lists CUDA (NVIDIA), ROCm (AMD), XPU (Intel) and MPS (Apple Silicon, macOS 14+); sd.cpp ships a 29.84 MB Windows Vulkan build that targets non-NVIDIA GPUs as well. — [Krita AI Diffusion](https://github.com/Acly/krita-ai-diffusion), [sd.cpp releases](https://api.github.com/repos/leejet/stable-diffusion.cpp/releases/latest)
- Apple Silicon: Z-Image-Turbo q4 pipeline ≈ 6 GB (fits 16 GB Macs); FLUX.2 klein 4B 30-40 s on M1 Max. — [mlx-community card](https://huggingface.co/mlx-community/Z-Image-Turbo-bf16), [lilting.ch](https://lilting.ch/en/articles/flux2-klein-apple-silicon)

### Inferences
- Suggested capability tiers (my synthesis): Tier 0 no discrete GPU or <4 GB: only 1-step 512x512 (SD-Turbo/SDXS class) via WebGPU/OpenVINO/sd.cpp CPU, 2-35 s, "draft" quality; Tier 1 4-6 GB VRAM: Z-Image-Turbo GGUF Q2-Q4 or SDXL-Lightning, ~6-40 s; Tier 2 8 GB: Z-Image-Turbo GGUF Q4-Q8 / FLUX.2 klein 4B GGUF, editing with klein; Tier 3 12-16 GB: Z-Image bf16/fp8, klein 4B bf16; Tier 4 24 GB+: Qwen-Image/Qwen-Image-Edit fp8 (20.4 GB), FLUX.3 klein bf16.
- GPU-share note: RTX 4060/5060/3050 (6-8 GB class) dominate Steam's list, so an 8 GB-tier default matters more than a 24 GB-tier default (card VRAM specs here are background knowledge, not fetched).
- CPU-only should be a documented "works but slow" path, not a marketed feature; the browser Light tier (SD-Turbo) is the more honest zero-GPU fallback for modern iGPUs.

### Gaps
- No controlled benchmark for sd.cpp CPU or iGPU Vulkan on mainstream laptops; the only CPU numbers are one tuned OpenVINO desktop run and one anecdote (both snippets).
- No data on Intel Arc/AMD iGPU WebGPU speeds, or on Windows Copilot+ NPU generation.
- VRAM distribution of Steam users (share with 4/6/8/12/16 GB) was not available from the fetched page.

## 5. Packaging for an end-user product (bundled runtime, one-click installers, weights download, disk footprint)

### Takeaway
The lightest embeddable runtime is stable-diffusion.cpp (MIT; 18-38 MB for CPU/Vulkan/macOS builds, 362 MB + 563 MB cudart for CUDA) wrapped as a Tauri sidecar; ComfyUI Desktop/portable and Stability Matrix/Pinokio are better treated as "user already has it" integrations. Weights dominate disk: 2.6-6.7 GB for the small tier, 13-30 GB for the big tier, and several are gated on Hugging Face.

### Cited Findings
- **Tauri sidecar**: add `externalBin` to `tauri.conf.json`; each binary needs a copy named with a `-$TARGET_TRIPLE` suffix (`rustc --print host-tuple`, Rust 1.84+); Windows needs `.exe`; spawn with `shell().sidecar()` (Rust) or `Command.sidecar('binaries/my-sidecar')` (JS); capabilities require `shell:allow-execute` or `shell:allow-spawn` with `"sidecar": true`; allowed arguments are declared statically or by regex validators; stdout is read via events. — [Tauri v2 sidecar docs](https://v2.tauri.app/develop/sidecar/)
- **sd.cpp binary sizes (2026-11-04)**: CPU 18.10 MB, Vulkan 29.84 MB, CUDA12 362.11 MB + separate cudart 563.45 MB, ROCm 265.88 MB (Windows), macOS arm64 37.73 MB. — [releases API](https://api.github.com/repos/leejet/stable-diffusion.cpp/releases/latest). Licence MIT (README lists "MIT"). — [README](https://github.com/leejet/stable-diffusion.cpp)
- **ComfyUI** — Desktop app for Windows and macOS (README is internally inconsistent about Linux), Windows portable packages, `comfy-cli`; licence GPL-3.0; portable size not stated. — [README](https://github.com/comfyanonymous/ComfyUI)
- **Stability Matrix** — source AGPL-3.0, binaries under an EULA (lykos.ai/license); one-click install/update of A1111, reForge/Forge, SD.Next, Fooocus variants, ComfyUI, SwarmUI, InvokeAI and trainers; embedded Git + Python; fully portable data dir; CivitAI + Hugging Face model browser with pause/resume; Windows 10/11, Linux AppImage/AUR, macOS Apple Silicon. — [LykosAI/StabilityMatrix](https://github.com/LykosAI/StabilityMatrix)
- **Pinokio** — MIT; "1-click launcher for any open-source project"; JSON scripts from public git repos; everything under `~/pinokio` (scripts in `api`, binaries in `bin`, per-app venvs); README does not name ComfyUI/Forge/Fooocus or a deep-link protocol. — [pinokiocomputer/pinokio](https://github.com/pinokiocomputer/pinokio)
- **Licence entanglement of bundling a server**: Draw Things server source/Protobuf are GPL-3.0 and its README warns that bundling client+server or auto-downloading the server from the client is "deep integration"; ComfyUI GPL-3.0; Forge Neo AGPL-3.0; Stability Matrix AGPL-3.0; Krita plugin GPL-3.0; InvokeAI Apache-2.0 (+3 component licences); sd.cpp MIT; Pinokio MIT. — [Draw Things](https://github.com/drawthingsai/draw-things-community), [Forge Neo](https://github.com/Haoming02/sd-webui-forge-classic), [InvokeAI](https://github.com/invoke-ai/InvokeAI), [Krita AI Diffusion](https://github.com/Acly/krita-ai-diffusion)
- **Weights sizes and gating** (see section 3 for sources): FLUX.3 klein repo is gated by a contact-sharing form and its HF file listing sums to 43.29 GB, but that total double-counts (root `model.safetensors` 11.10 GB = the `transformer/` shards 11.10 GB; `ae.safetensors` 0.34 GB = `vae/`) and includes both quantised variants (fp8r 6.27 GB, nvfp4 5.28 GB) plus the 8.88 GB text encoder, so one working set is 15.5-20.3 GB (fp8 or bf16 + text encoder + VAE); FLUX.2 [dev] and Krea 2 are gated; Z-Image-Turbo diffusers repo 32.83 GB (public); Qwen-Image diffusers repo 57.70 GB; FLUX.2 klein 4B repo 23.7 GB. — [FLUX.3 klein tree](https://huggingface.co/api/models/black-forest-labs/flux-3-image-klein/tree/main?recursive=true), [Z-Image tree](https://huggingface.co/api/models/Tongyi-MAI/Z-Image-Turbo/tree/main?recursive=true), [Qwen-Image tree](https://huggingface.co/api/models/Qwen/Qwen-Image/tree/main?recursive=true), [klein-4B tree](https://huggingface.co/api/models/black-forest-labs/FLUX.2-klein-4B/tree/main?recursive=true)
- **Smaller packaged variants**: Z-Image-Turbo GGUF 2.59-6.58 GB; FLUX.2 klein 4B GGUF 2.46/4.30 GB; Qwen3-4B text encoder GGUF 1.67-8.05 GB (Q4_K_M 2.50 GB); Z-Image ONNX for browsers 5.99 GB; SD-Turbo ONNX 2.58 GB. Sources in sections 1 and 3.
- **Browser cache capacity** (for the in-browser tier): Chromium up to 60% of disk per origin; Firefox min(10% of disk, 10 GiB) per site group unless persisted; Safari ~60%, with 7-day script-data eviction under tracking prevention. — [MDN](https://developer.mozilla.org/en-US/docs/Web/API/Storage_API/Storage_quotas_and_eviction_criteria)
- sd.cpp `--offload-to-cpu` appears in the Z-Image and klein example commands (reduces VRAM at a speed cost). — [z_image.md](https://raw.githubusercontent.com/leejet/stable-diffusion.cpp/master/docs/z_image.md), [flux2.md](https://raw.githubusercontent.com/leejet/stable-diffusion.cpp/master/docs/flux2.md)

### Inferences
- A "Craftly Engine" sidecar based on sd.cpp could ship at 30 MB (Vulkan; covers NVIDIA/AMD/Intel) to ~930 MB (CUDA + cudart) plus a model downloader; the model, not the runtime, is the install-size problem (about 5-7 GB for a small-tier bundle).
- Download manager needs: HTTP Range resume, SHA256 verification, free-disk check, gated-repo token flow (users must accept FLUX.3/Krea licences on huggingface.co first), and a model-licence manifest (name, SPDX/licence, revenue threshold) shown before download.
- Prefer MIT/Apache runtimes (sd.cpp, InvokeAI) for anything Craftly bundles; treat ComfyUI/Forge/Stability Matrix/Pinokio as external programs the user installs (GPL/AGPL obligations avoided by not linking or redistributing them).
- A desktop wrapper (Tauri/Electron) also sidesteps mixed-content/LNA/CORS because requests can originate from native code (not verified in this research).

### Gaps
- ComfyUI Desktop/portable download sizes, Electron vs Tauri bundle sizes with a sidecar, installer signing/SmartScreen behaviour, and code-signing costs were not researched.
- Pinokio's availability of ready-made ComfyUI/Forge scripts was not confirmed from the README; Hugging Face rate limits/resume behaviour and CORS headers on `resolve/` URLs were not verified directly.
- Auto-update/CVE handling story for bundled runtimes not researched.

## 6. Safety and compliance: NSFW filters, watermarking and C2PA, user liability, licence obligations

### Takeaway
Several open licences make output filtering or review a licence condition (FLUX NC v2.1 §2(e)(i), Krea 2, FLUX.3 klein), and the EU AI Act's machine-readable marking duty (Art. 50(2)) has applied to new generative systems since 2026-08-02 with a grace period to 2026-12-02 for systems already on the market; C2PA reading is available in browsers but signing in a no-backend app is the hard part. A client-side NSFW check is technically feasible (Microsoft's Z-Image ONNX pipeline ships a safety checker) but is bypassable by design when everything runs on the user's machine.

### Cited Findings
- **EU AI Act Art. 50(2)**: "Providers of AI systems, including general-purpose AI systems, generating synthetic audio, image, video or text content shall ensure that the outputs of the AI system are marked in a machine-readable format and detectable as artificially generated or manipulated"; exception where the system performs "an assistive function for standard editing" or does not substantially alter input data/semantics; **Art. 50(4)**: deployers of deepfakes "shall disclose that the content has been artificially generated or manipulated" (lighter duty for evidently artistic, creative, satirical or fictional works); Art. 50 applies from 2 August 2026. — [artificialintelligenceact.eu Art. 50](https://artificialintelligenceact.eu/article/50/)
- **Digital Omnibus on AI**: Regulation (EU) 2026/1744 "entered into force" 27 July 2026; Art. 50(2) marking applies to new systems from 2 Aug 2026 and to generative systems already on the market before then until 2 December 2026; content in circulation before 2 Aug 2026 need not be marked retroactively; Commission published a voluntary Code of Practice on marking AI-generated content on 10 June 2026 and Art. 50 guidelines on 20 July 2026. — [Cobalt Legal](https://www.cobalt.legal/news-cases/digital-omnibus-on-ai/) [secondary; its own timeline table labels 2 Aug 2026 "Partially postponed", which conflicts with its text]. Search-result snippets from other trackers say the same but frame the 2 Dec date inconsistently ("extension" vs "transition close") — [Usercentrics](https://usercentrics.com/knowledge-hub/eu-ai-act-high-risk-delay-article-50-transparency-consent/) [snippet].
- **BFL FLUX Non-Commercial License v2.1**: §2(e)(i) either (A) maintain content filtering or (B) ensure outputs are reviewed for unlawful or infringing content before distribution or display; §7(b) failure to implement required filters is an indemnification matter; §2(e)(ii) AI disclosure "to the extent required under applicable law"; no watermark or metadata requirement. — [licence text](https://raw.githubusercontent.com/black-forest-labs/flux2/main/model_licenses/LICENSE-FLUX-NON-COMMERICAL). BFL's FLUX.2 repo: optional invisible watermark and a recommendation to "mark the metadata of your outputs" (linked to C2PA), not a requirement. — [flux2 repo](https://github.com/black-forest-labs/flux2)
- **FLUX.3 klein / FLUX Kommunity License**: commercial output generation allowed under US$5M revenue; use restrictions in §4 (military, surveillance, biometric processing, unlawful/abusive content, training similar models); reference CLI "always loaded" safety classifier Falconsai/nsfw_image_detection; BFL says it "evaluated and mitigated" CSAM and NCII risks; the card states no watermark/C2PA requirement. — [HF card](https://huggingface.co/black-forest-labs/flux-3-image-klein)
- **Krea 2 Community License**: deployers must implement "content filtering measures or equivalent review processes"; failure is a licence breach. — [Krea-2-Turbo card](https://huggingface.co/krea/Krea-2-Turbo)
- **SD 3.5 / Stability Community License**: AUP incorporated by reference (stability.ai/use-policy); "Powered by Stability AI" attribution and Notice file when distributing; licence terminates above US$1M revenue. — [Stability licence](https://stability.ai/community-license-agreement)
- **Other obligations**: Hunyuan licence has an AUP (e.g., item 19 "For military purposes"), forbids using outputs to improve other AI models, and requires a NOTICE line; Qwen Research License requires "Built with Qwen" for derived distributed models and is non-commercial; Chroma1-HD "has not been aligned with a specific safety filter" and "potential to generate content that may be considered harmful, explicit, or offensive". — [Hunyuan licence](https://scancode-licensedb.aboutcode.org/tencent-hunyuan-image-3.0-cla.html), [Qwen LICENSE](https://huggingface.co/Qwen/Qwen-Image-2.1/raw/main/LICENSE), [Chroma1-HD](https://huggingface.co/lodestones/Chroma1-HD)
- **In-browser safety checker precedent**: Microsoft's Z-Image-Turbo ONNX bundle includes `safety_checker_model_f16.onnx` + 606,797,824-byte external data (0.608 GB) and a preprocessing model; the demo timing panel has a "Safety Checker" stage. — [HF tree](https://huggingface.co/api/models/lwanming/Z-Image-Turbo-opt/tree/main?recursive=true), [demo](https://microsoft.github.io/webnn-developer-preview/demos/z-image-turbo/)
- **C2PA tooling**: `contentauth/c2pa-js` (MIT) provides `c2pa-web` ("Library for C2PA metadata in the browser") and `c2pa-node` (read/validate manifests and "add signed manifests"; Node 22+); signing is documented only for the Node library; "C2PA signing trust anchors and test certificates are separate from HTTPS CA roots". — [contentauth/c2pa-js](https://github.com/contentauth/c2pa-js) (Content Authenticity docs page for browser signing returned 404, so browser signing capability is unconfirmed.)
- **Output ownership/liability statements in licences**: Tencent "claims no rights in Outputs You generate"; Qwen license disclaims warranty and liability for safety of materials and outputs (§6(b)-(c)); FLUX NC v2.1 allows commercial use of outputs. Sources as above.

### Inferences
- Craftly is plausibly a "provider" of an AI system if it ships its own in-browser generator and a "deployer"-adjacent tool if it only drives a user's server; which role applies, and whether inpaint/outpaint/restyle fall under the "assistive function for standard editing" exception, is a legal question not answered by the sources (get advice).
- A pragmatic compliance baseline: embed standard provenance metadata in every AI-generated asset (IPTC DigitalSourceType trainedAlgorithmicMedia / XMP custom fields plus a Craftly manifest) and keep a "generated by AI" flag in the project model so exports can add it; real C2PA signing needs a private key that cannot safely live in a static JS bundle, so offer it only where the user supplies their own credential (desktop wrapper) or defer.
- Licence conditions of "filter OR review" (FLUX NC, Krea 2) can be met in a local-first editor by mandatory preview-before-insert plus an optional classifier; an on-device NSFW classifier is bypassable, so describe it as a safeguard, not a guarantee.
- Surface licence obligations in-app: model name, licence, revenue threshold, attribution string (e.g. "Powered by Stability AI") and AUP link; block auto-selection of NC models for users who mark their projects commercial.

### Gaps
- Not researched (search budget): California AI Transparency Act (SB 942/AB 853) dates, US TAKE IT DOWN Act platform duties, UK/other regimes, app-store policies for AI generators, platform/host liability for user-generated content.
- Actual text of OpenRAIL++-M (SDXL), SD 3.5 AUP, Krea 2 and FLUX Kommunity licences was not read in full; EU Code of Practice content (watermark + metadata expectations) not read.
- Whether c2pa-web can create/sign manifests in-browser; feasibility of invisible watermarks (e.g., via the BFL invisible-watermark option) in a pure-browser pipeline.
- Practical accuracy/size of client-side NSFW classifiers (e.g., a ViT classifier via Transformers.js) was not measured.

## 7. Integration patterns in a canvas design editor (generate into a frame, inpaint, outpaint, restyle, references, upscale, queue, seeds, history)

### Takeaway
Existing tools show a stable pattern: a ComfyUI-class backend, selection/mask-driven generative fill and expand, reference/control layers, a job queue with history of results and prompts, and an upscale step that tiles to avoid memory limits (Krita AI Diffusion is the closest open precedent). Backends differ mainly in how they express masks, progress and cancel, so an adapter layer around a common job model is the key design decision.

### Cited Findings
- **Krita AI Diffusion (GPL-3.0)**: uses ComfyUI as backend (auto-installs a local server, or connects to a running local/remote server; cloud option); "Use selections for generative fill, expand, to add or remove objects"; live painting; "Upscale and enrich images to 4k, 8k and beyond without running out of memory"; regions (per-layer text descriptions); reference images (style/composition transfer, face swap via IP-Adapter); control layers (scribble, line art, canny, pose, depth, normals, segmentation); job queue; history of results and prompts; style presets; models Flux 2, Z-Image, SD1.5/XL, Illustrious plus instruction-edit models; at least 6 GB NVIDIA VRAM recommended; Windows/Linux/macOS. — [Acly/krita-ai-diffusion](https://github.com/Acly/krita-ai-diffusion)
- **Inpaint**: ComfyUI "VAE Encoder (for Inpainting)" with `grow_mask_by` ("pixel value to expand the original mask outward ... reduces hard edges"), mask from alpha or mask editor; masks can be uploaded via `POST /upload/mask`. — [ComfyUI inpaint](https://docs.comfy.org/tutorials/basic/inpaint), [routes](https://docs.comfy.org/development/comfyui-server/comms_routes). sd.cpp: `POST /v1/images/edits` with `mask`, or `/sdapi/v1/img2img` with `mask` + `inpainting_mask_invert` + `denoising_strength`, or native `mask_image`. — [api.md](https://raw.githubusercontent.com/leejet/stable-diffusion.cpp/master/examples/server/api.md)
- **Outpaint (Magic-Expand analogue)**: ComfyUI "Pad Image for outpainting" takes left/top/right/bottom padding and `feathering` and outputs the padded image and a mask for the new area, then feeds the inpainting encoder. — [ComfyUI outpaint](https://docs.comfy.org/tutorials/basic/outpaint). Fooocus bundles "Inpaint / Up / Down / Left / Right" in one tool. — [Fooocus](https://github.com/lllyasviel/Fooocus)
- **Image-to-image restyle**: A1111-style `img2img` with `denoising_strength` (clamped 0..1) in sd.cpp; Z-Image/Qwen-Image control via ControlNet-union model patches; the SD-Turbo diffusers card requires `num_inference_steps x strength >= 1` for img2img (so 1-step restyle needs strength 1.0, or more steps), and the ORT repo includes a separate `vae_encoder` (68 MB), so browser img2img looks possible in principle (not verified in any demo). — [api.md](https://raw.githubusercontent.com/leejet/stable-diffusion.cpp/master/examples/server/api.md), [sd-turbo card](https://huggingface.co/stabilityai/sd-turbo), [sd-turbo-ort-web tree](https://huggingface.co/api/models/schmuell/sd-turbo-ort-web/tree/main?recursive=true)
- **Reference images / edit models**: FLUX.2 klein supports multi-reference composition (sd.cpp `-r` reference flag in examples), FLUX.3 klein up to 10 references and a 0-1000 bounding-box grid ("guide placement and are not a hard mask"), Qwen-Image-Edit-2511 fuses multiple input images, HunyuanImage-3.0-Instruct up to 3. — [sd.cpp flux2.md](https://raw.githubusercontent.com/leejet/stable-diffusion.cpp/master/docs/flux2.md), [FLUX.3 klein card](https://huggingface.co/black-forest-labs/flux-3-image-klein), [Qwen-Image-Edit-2511](https://huggingface.co/Qwen/Qwen-Image-Edit-2511), [HunyuanImage-3.0](https://huggingface.co/tencent/HunyuanImage-3.0)
- **Upscaling**: sd.cpp `POST /sdcpp/v1/upscale` (repeats 1-4, tile_size) and A1111-style `/sdapi/v1/upscalers`; README: "Upscale images generated with ESRGAN". — [api.md](https://raw.githubusercontent.com/leejet/stable-diffusion.cpp/master/examples/server/api.md), [README](https://raw.githubusercontent.com/leejet/stable-diffusion.cpp/master/README.md). Browser upscalers: see sibling note section 4.
- **Job queue, progress, cancel**: ComfyUI `POST /prompt` -> `prompt_id`; WS `progress`/`executing`/`executed` plus binary latent previews (needs `--preview-method latent2rgb|taesd`), `POST /interrupt` (optional `prompt_id`), `POST /queue` (delete/clear), `GET /history/{prompt_id}` + `GET /view` to fetch results. — [routes](https://docs.comfy.org/development/comfyui-server/comms_routes), [server.py](https://raw.githubusercontent.com/comfyanonymous/ComfyUI/master/server.py), [cli_args.py](https://raw.githubusercontent.com/comfyanonymous/ComfyUI/master/comfy/cli_args.py). sd.cpp native: 202 + `poll_url`, job states queued/generating/completed/failed/cancelled, `preview` {pass, step, total_steps, image}, `POST .../cancel`; A1111-style `GET /sdapi/v1/progress` with `current_image`. Generation endpoints on the OpenAI/A1111 families are synchronous. — [api.md](https://raw.githubusercontent.com/leejet/stable-diffusion.cpp/master/examples/server/api.md)
- **Capability discovery**: sd.cpp `GET /sdcpp/v1/capabilities` (defaults, features, samplers, LoRAs, upscalers, limits); ComfyUI `GET /object_info`, `GET /models/{folder}`, `GET /system_stats` (devices, VRAM); A1111 `/sdapi/v1/sd-models`. — [api.md](https://raw.githubusercontent.com/leejet/stable-diffusion.cpp/master/examples/server/api.md), [routes](https://docs.comfy.org/development/comfyui-server/comms_routes)
- **Seeds**: A1111-style `seed` -1 = random; SD-Turbo in ORT Web has only best-effort determinism across hardware/drivers; ComfyUI's `--disable-metadata` flag turns off embedding prompt metadata in saved files (default embeds it). — [api.md](https://raw.githubusercontent.com/leejet/stable-diffusion.cpp/master/examples/server/api.md), [web-txt2img](https://github.com/lacerbi/web-txt2img), [cli_args.py](https://raw.githubusercontent.com/comfyanonymous/ComfyUI/master/comfy/cli_args.py)
- **Speed levers that change UX**: Qwen-Image 8-step Lightning LoRA cut ≈71 s to ≈34 s; klein 4B distilled ≈1.2 s on RTX 5090 means "live" preview is plausible on high-end cards. — [ComfyUI Qwen-Image doc](https://docs.comfy.org/tutorials/image/qwen/qwen-image), [ComfyUI klein doc](https://docs.comfy.org/tutorials/flux/flux-2-klein)

### Inferences
- Common job model for Craftly: `{id, backend, kind: txt2img|img2img|inpaint|outpaint|upscale|edit, params{prompt, negative, seed, steps, cfg, size, strength, modelRef, refs[], mask?}, state: queued|running|done|failed|cancelled, progress{step,total,previewBlob?}, result{blob, seed, modelHash, params}}`, persisted in IndexedDB with thumbnails so history/regenerate/variation by seed are cheap; map to ComfyUI (WS + queue), sd.cpp native (poll), A1111-style (single in-flight, poll `/progress`), in-browser (worker, single-flight).
- Generate-into-frame: create the target image element immediately (placeholder with progress ring and preview frames), size the request to a model-friendly resolution (multiples of 16, ~1 MP for 6-20B models, 512x512 for Turbo-SD), then fit/fill into the frame; store the original and the AI metadata on the element.
- Inpaint: render the brush mask as a grayscale/alpha PNG at working resolution; crop with context padding around the mask bbox, run inpaint, then composite back with feathered mask edges and `grow_mask_by`-like dilation; different backends invert masks differently (`inpainting_mask_invert`), so the adapter must normalise.
- Outpaint/Magic Expand: pad canvas by user-dragged margins, auto-generate the mask (new area white), use feathering, optionally two-stage (low-denoise blend pass).
- Prefer sending the user's pixels as blobs over localhost only to the chosen backend; never to a Craftly server (there is none) — a privacy selling point to state in the UI.
- Preview strategy: ComfyUI previews require `--preview-method` (default none), so don't promise live previews unless the server was started with it; sd.cpp native API returns previews when requested.

### Gaps
- No documentation of Canva's Magic Expand/Grab Text behaviours was examined here (out of scope); mask semantics across backends not tested.
- ComfyUI workflow JSON templates for each model family (node IDs, model filenames) were not collected; they vary by install and ComfyUI version.
- Browser-side upscaling and inpainting options are in the sibling note, not re-verified.

## 8. Recommended architecture for Craftly (first two or three options, effort estimates)

### Takeaway
Build one `ImageBackend` abstraction (capabilities + job model) and ship three backends in this order: (1) an sd.cpp/A1111-compatible HTTP adapter (cheapest, works from a static page with no CORS flags, and covers sd.cpp, Forge/Neo, A1111 and, if confirmed, Draw Things), (2) a ComfyUI adapter with bundled workflow templates (most capable, where new models land first), (3) an "Instant" in-browser WebGPU mode (zero-install; the only local option for Safari users) with Apache-2.0 Z-Image-Turbo ONNX as the quality tier and a licence-cleared SD-Turbo-class model as the light tier. A managed sd.cpp sidecar in a Tauri shell is the follow-on for non-technical users.

### Cited Findings (facts that drive the recommendation)
- sd.cpp server already exposes OpenAI, A1111 and native async job APIs (txt2img, img2img+mask, edits, upscale, capabilities, progress/preview, cancel), reflects Origin for CORS, MIT, 18-38 MB builds for CPU/Vulkan/macOS, weekly releases (master-1050 on 2026-11-04), same-day support for FLUX.3 klein and Qwen-Image-2.1. — [api.md](https://raw.githubusercontent.com/leejet/stable-diffusion.cpp/master/examples/server/api.md), [main.cpp](https://raw.githubusercontent.com/leejet/stable-diffusion.cpp/master/examples/server/main.cpp), [README](https://raw.githubusercontent.com/leejet/stable-diffusion.cpp/master/README.md), [releases](https://api.github.com/repos/leejet/stable-diffusion.cpp/releases/latest)
- ComfyUI is the first to list Flux.2, Z-Image, Qwen Image, HunyuanImage 2.1 and edit models; stable HTTP/WS API; but 403 for cross-site pages unless `--enable-cors-header`. — [README](https://github.com/comfyanonymous/ComfyUI), [server.py](https://raw.githubusercontent.com/comfyanonymous/ComfyUI/master/server.py)
- Chrome requires a user-granted `loopback-network` permission from https pages; Firefox 151+ rolling out a similar prompt; Safari blocks https-to-http-localhost (WebKit bug open since 2017-era). — [Chrome guidance](https://developer.chrome.com/docs/modern-web-guidance/guides/security/local-network-access), [Firefox 151 notes](https://www.firefox.com/en-US/firefox/151.0/releasenotes/?redirect_source=mozilla-org), [WebKit 171934](https://bugs.webkit.org/show_bug.cgi?id=171934)
- WebGPU: ~87% global; Safari 26+/macOS 26+ only; Z-Image-Turbo ONNX (Apache-2.0) 5.99 GB core; SD-Turbo ONNX 2.58 GB with licence ambiguity. — [caniuse](https://raw.githubusercontent.com/Fyrd/caniuse/main/features-json/webgpu.json), [HF Z-Image-opt](https://huggingface.co/lwanming/Z-Image-Turbo-opt), [SD-Turbo mirror licence](https://huggingface.co/schmuell/sd-turbo-ort-web/raw/main/LICENSE)
- Ollama image generation macOS-only and no images endpoint; LM Studio none; Fooocus LTS/SDXL-only; A1111 API docs unmaintained. — [Ollama](https://ollama.com/x/z-image-turbo), [Ollama OpenAI docs](https://docs.ollama.com/api/openai-compatibility), [Fooocus](https://github.com/lllyasviel/Fooocus), [A1111 API wiki](https://github.com/AUTOMATIC1111/stable-diffusion-webui/wiki/API)
- Commercially clean model set: FLUX.2 klein 4B (Apache-2.0, editing), Z-Image-Turbo (Apache-2.0), Qwen-Image-Edit-2511 (Apache-2.0), FLUX.1 schnell (Apache-2.0), MOSS-Image (Apache-2.0). Sources in section 3.

### Inferences
**Recommended build order (my judgement; effort estimates are NOT from sources, they are solo-developer person-days for someone who already has the canvas, asset store and image-element model in place):**

1. **Shared foundation (5-7 days)** — `ImageBackend` interface (`capabilities()`, `listModels()`, `submit(job)`, `cancel(id)`, `onProgress`), job store + history in IndexedDB (prompt, negative, seed, model, params, thumbnail), AI-image panel (prompt, size presets, count, seed lock), placeholder-with-progress element, "insert into frame/replace image". Plus **connection manager (2-3 days)**: probe known ports on user click, `loopback-network` permission query (try/catch, never `local-network-access`), `targetAddressSpace:'loopback'`, per-server CORS snippets, Safari/mixed-content explainer.
2. **Adapter A: sd.cpp native + A1111-compatible (4-6 days)** — txt2img, img2img, inpaint via mask, `/sdapi/v1/progress`, native job polling with preview/cancel, upscale endpoint; test on Windows with the 30 MB Vulkan build. Recipe in docs: download `sd-*-bin-win-vulkan-x64.zip`, Z-Image-Turbo GGUF (Q4_K 3.86 GB) + Qwen3-4B Q4_K_M (2.50 GB) + VAE, start the server, click Connect. Works on 4 GB-VRAM GPUs per sd.cpp's claim.
3. **Mask/outpaint canvas tooling (6-10 days, shared by all backends)** — brush mask layer, expand handles, context crop + feathered composite, undo, before/after.
4. **Adapter B: ComfyUI (8-12 days for two model families; +1-2 days per extra family)** — workflow templates (txt2img, img2img, inpaint, outpaint, upscale) for SDXL-class and one modern DiT (Z-Image-Turbo or FLUX.2 klein), `object_info`/`models` validation to disable unavailable features, WS progress + previews, `/upload/image`, `/upload/mask`, `/interrupt`, `/history` fetch; ship a "how to start ComfyUI" card with `--enable-cors-header https://<craftly-origin>` (Krita AI Diffusion is the precedent for this backend choice).
5. **"Instant" in-browser mode (6-10 days)** — ORT Web worker, adapter-limit negotiation, WebGPU feature detection, model manager (chunked download with progress, Cache Storage/IndexedDB, `navigator.storage.persist()`, purge UI, resume), licence/NOTICE screen; start with Z-Image-Turbo ONNX at 512x512 (Apache-2.0, ~6 GB) or SD-Turbo if its licence is cleared (Stability Community License needs registration and "Powered by Stability AI"); show an honest "needs a recent GPU; ~6 GB download" gate; roughly +3-5 days if both tiers are built.
6. **Safety/provenance layer (3-5 days)** — preview-before-insert, optional client-side NSFW classifier, AI-provenance metadata on export, per-model licence badge; legal review of EU Art. 50 posture.
7. **Later: managed "Craftly Engine" (10-15 days)** — Tauri sidecar around sd.cpp, per-session token + pinned CORS, model downloader with resume/SHA256/gated-repo flow, auto-update, code signing.

**Rough totals**: MVP with sd.cpp/A1111 adapter + inpaint/outpaint + safety layer ≈ 4-5 weeks; adding ComfyUI ≈ +2 weeks; adding in-browser Instant ≈ +1.5-2 weeks; managed engine ≈ +2-3 weeks.

**Why this order**: (a) the sd.cpp/A1111 path has the fewest moving parts and no user-side flags; (b) ComfyUI has the broadest model coverage and an audience that already runs it; (c) in-browser is the only route for Safari/Mac and for users who won't install anything, but is the slowest/lowest-quality and has the heaviest download; Ollama/LM Studio/Fooocus/Invoke can wait (Invoke has its own API and `allow_origins` setting and could be added later).

**Default presets (licence-clean)**: Tiny (<=6 GB VRAM): Z-Image-Turbo GGUF Q2_K-Q4_0; Standard (8-12 GB): Z-Image-Turbo Q8/fp8 or FLUX.2 klein 4B; Edit: FLUX.2 klein 4B or Qwen-Image-Edit-2511 (24 GB class); avoid auto-recommending FLUX.2 dev, klein 9B, FLUX.1 dev/Kontext, Qwen-Image-2.1 (NC), Fibo, Krea 2 (terms unclear), SDXL-Turbo (NC tag).

### Gaps
- All effort numbers are judgement estimates; no velocity data for this codebase was available.
- Whether Tauri/Electron requests bypass LNA/CORS/mixed-content as assumed was not verified.
- No tested end-to-end run of any backend from a real https origin was done (research only): verify Chrome's prompt UX, Firefox 151+ behaviour and Safari failure mode on real machines before committing UX copy.
- Draw Things HTTP API compatibility, InvokeAI API shape and a clean redistributable SD-Turbo ONNX source remain open; resolve before promising them in the UI.
